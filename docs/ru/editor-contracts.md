# Планируемые контракты редактора {#editor-contracts-ru}

[English version](../editor-contracts.md)

**Статус: PLANNED.** Страница описывает предлагаемый контракт многострочного
редактора. Она не документирует реализованные `Document`, `TextArea`, API
языкового провайдера или принятую синтаксическую зависимость. Направление
первой реализации и границы проверки описаны ниже. Семантические язык,
контекст и среда исполнения выделены в отдельный отложенный gate G0S.

Предложение сохраняет C++23, текущие UI runtime и renderer, а также действующие
контракты [LineEdit](line-edit.md) и [Undo/Redo](editor-history.md). Имена ниже
обозначают понятия; это не объявления доступных функций.

## Владение документом и представлением

Документ владеет исходником UTF-8, метаданными переводов строк, стабильной
идентичностью, `documentRevision` и одной общей историей undo/redo. Представление
удерживает владеющий handle документа и хранит собственные курсор, выделение,
viewport, фокус и кэши отображения. Закрытие одного представления не закрывает
другое представление того же документа. Языковые аннотации и состояние
публикации не владеют исходным текстом.

Все изменения документа, разрешение представлений и доставка уведомлений
выполняются на UI owner. Worker получает неизменяемые владеющие snapshots и
никогда не обращается к widget, binding, изменяемому документу или заимствованной
UI-памяти. Snapshot может пережить представление и документ; его освобождение
не вызывает UI callbacks.

Принятая транзакция атомарно устанавливает текст, метаданные переводов строк,
историю и отображённые позиции представлений до уведомлений.
`documentRevision` продвигается при каждой принятой транзакции исходника,
включая undo, redo и принятие внешнего baseline; восстановление прежних байтов
не возвращает старую ревизию. Обычная замена с равными байтами и метаданными
переводов строк ничего не меняет.
Явный новый baseline, в том числе равные байты новой внешней ревизии значения,
продвигает ревизию и сбрасывает историю. Исчерпание идентичностей или поколений
отклоняет операцию до изменения состояния.

Публикация модели имеет отдельные baseline/ревизию и результат. Успешная
публикация той же ревизии документа не редактирует документ и не сбрасывает
историю. Публикация результата провайдера имеет отдельное поколение;
применение токенов не продвигает `documentRevision`. Эти значения нельзя
подменять одним счётчиком.

## Транзакции, внешние значения и общий undo

Изменение содержит непересекающиеся полуоткрытые диапазоны исходника одной
зафиксированной ревизии и владеющие байты замены. Все диапазоны проверяются
до изменения; транзакция принимается целиком и входит в одну группу undo при
включённой истории, возможно продолжая текущую группу ввода/удаления.
Вставка, вырезание и completion — явные границы группировки. Соседние ввод
или удаление объединяются только в одном живом инициирующем представлении;
навигация, выделение, смена фокуса, внешние изменения и редактирование другим
представлением завершают группу. Новое принятое изменение после undo удаляет
redo; обычная операция без изменения сохраняет его.

Пустые диапазоны требуют дополнительной проверки: anchor вставки не должен
попадать в замкнутый интервал любого другого изменения той же транзакции.
Несколько вставок в одном смещении и вставка внутрь либо на любой конец другой
замены атомарно отклоняются с типизированным invalid-operation result.
Вызывающий код должен явно объединить задуманные упорядоченные вставки в одну
владеющую замену до отправки. Соседние непустые замены допустимы; они вместе
интерпретируются в порядке исходника относительно зафиксированной ревизии.
Их общая граница исходника отображается в границу результата между двумя
строками замены. Подготовка истории объединяет порождённые обратные вставки
по тем же правилам и сохраняет проверенный обратный mapping для undo.

По умолчанию явное внешнее значение становится **новым baseline**, а не
записанным пользовательским изменением: целое значение принимается, обе истории
очищаются. Инициализация также задаёт новый baseline; обычные программные
edit/append по умолчанию записывают транзакцию (`RECORD`), а инициализация/внешний
baseline используют `RESET_BASELINE`. Явный override отдельной операции может выбрать
другую политику. Если
обнаружен новый baseline модели при изменённом документе, возникает конфликт:
ни одна сторона не перезаписывается молча. Явное принятие baseline разрешает
конфликт осознанно и атомарно. Будущий binding API должен выражать этот выбор,
не перенося клавиши подтверждения LineEdit в многострочное редактирование.

Документ имеет один draft/history и один model bridge/commit policy для всех
представлений: разные `EditMode` для одного документа недопустимы. Подтверждение
публикует текущий draft и сохраняет историю. Предлагаемый `ON_COMPLETION`
делает одну попытку commit при blur инициирующего представления, в том числе
при переходе фокуса в другое представление того же документа; новое
представление видит те же draft и успешный baseline. Чистый неизменённый draft
не публикуется повторно. Reentrant focus events не повторяют попытку.
Явный cancel осознанно принимает актуальное значение модели как новый baseline
для всех представлений и сбрасывает общую историю; ошибка получения/подготовки
значения сохраняет текущий draft. Это планируемые многострочные правила;
поведение LineEdit сохраняется.

До вызова model publisher мост владеет отдельной попыткой публикации с
уникальной идентичностью, зафиксированными `documentRevision`, точным значением
(включая нужные метаданные переводов строк/экспорта) и ожидаемыми baseline/ревизией
модели. Publisher обязан обусловить запись этим ожидаемым baseline; посторонняя
внешняя ревизия даёт типизированный конфликт вместо слепой перезаписи. У документа
одновременно активна одна попытка. Reentrant confirmation нового draft ожидает
её завершения, не вызывая рекурсивную публикацию по незавершённому baseline.

Успешный receipt завершает только зафиксированную попытку/значение. Текущий draft
становится clean только если его ревизия документа всё ещё совпадает с
зафиксированной, а успешный baseline модели ещё применим. Более новое reentrant
изменение остаётся dirty до собственной публикации или явного разрешения
baseline даже при совпадении байтов и сохраняет собственные историю, выделение
и ревизию. Завершение попытки не меняет состояние более нового явного принятия
baseline и не восстанавливает snapshot в текущий
документ. Если до завершения обнаружен несовместимый внешний baseline,
сообщается конфликт с сохранением более новых draft/model state; значение
попытки не записывается поверх этого baseline. Известный успешный receipt записи
модели сообщается отдельно от такого settlement conflict; откатить его нельзя.

Отказ до вызова publisher не меняет документ или модель этой попыткой. Отказ
или исключение callback после reentry сохраняет все независимо принятые
изменения, не помечает новый draft чистым и не сбрасывает его историю/выделение.
Без достоверного write receipt возвращается типизированная техническая ошибка
публикации с неподтверждённым исходом; до явного retry нужно получить актуальный
baseline, не предполагая, что записи не было. Ошибка callback после известного
успешного receipt — observation failure этой попытки, не разрешение опубликовать
её значение повторно. Точные result types остаются открытыми.

Группа истории владеет текстом и метаданными переводов строк до/после операции,
проверенными прямым и обратным mapping позиций для своих изменений,
идентичностью времени жизни исходного инициирующего представления и его
курсор/выделением до/после. Она не хранит сырой указатель и не удерживает закрытое
представление. Undo/redo из любого присоединённого представления восстанавливает
общий документ. Сохранённые курсор/выделение инициатора восстанавливаются только
если та же его жизнь ещё присоединена к тому же документу. Позиции всех остальных
живых представлений отображаются через обратное/прямое изменение, включая
вызвавшее undo представление, если оно не инициатор. Undo не переводит фокус
к инициатору и не восстанавливает viewport другого представления. Закрытого
инициатора просто больше нет.

Позиция имеет левую/правую affinity при вставке. При замене `[a,b)` на `n`
байтов позиции до `a` сохраняются, после `b` сдвигаются на `n-(b-a)`; позиция
на `b` непустого удаляемого диапазона переходит в `a+n`. Позиции внутри
диапазона, включая `a`, схлопываются в `a` при левой affinity или в `a+n` при
правой. При чистой вставке affinity выбирает сторону. Схлопнутый курсор имеет
правую affinity; непустое выделение — левую у нижней границы и правую у верхней,
с сохранением направления active/anchor. После отображения концы смещаются
наружу к допустимым границам расширенной графемы (EGC) согласно той же affinity.
Инициирующее изменение явно задаёт своё итоговое выделение. Остальные viewport
сохраняют отображённый верхний anchor исходника и ограничивают прокрутку
допустимой геометрией. Изменение текста не подразумевает смену фокуса.

## Исходник, переводы строк и координаты

Предлагаемый канонический исходник — UTF-8 с LF между строками, без Unicode
normalization. Импорт распознаёт LF, CRLF и одиночный CR, сохраняя владеющий вид
разделителя для каждого канонического LF. Неизменённый смешанный файл можно
экспортировать побайтно. Завершающий перевод строки — настоящий последний
разделитель с пустой логической строкой после него; пустой ввод отличается
от ввода с завершающим переводом строки.

Экспорт по умолчанию сохраняет виды оставшихся разделителей. Новый ввод
использует настраиваемый preferred newline документа: самый частый вид импорта,
первый встретившийся при равенстве, LF для нового документа. Вставленные или
импортированные сырые диапазоны сохраняют явные виды своих разделителей;
программная каноническая замена использует preferred newline, если вызывающий
код не передал проверенные метаданные. Удаление разделителя удаляет метаданные;
undo/redo восстанавливает их. Явный нормализованный экспорт может выбрать LF
или CRLF без изменения документа. Смена preferred newline влияет только на
будущие вставки. Перезапись существующих метаданных — отдельная явная транзакция
исходника с undo.

Табуляция сохраняется как U+0009. Предлагаемый default — вставка настоящего tab
и tab stops через четыре ячейки; режим spaces-on-Tab настраивается.
Существующие tab не преобразуются молча. Tab stops вычисляются от начала
логической строки до viewport clipping. Мягкий перенос выключен по умолчанию;
при его включении визуальная строка становится отдельной координатой, не
логической строкой исходника.

| Координата | Значение и правило преобразования |
|---|---|
| Смещение UTF-8 в байтах | Смещение канонического исходника с явной ревизией документа; диапазоны полуоткрытые. |
| Граница Unicode scalar | Граница декодированного UTF-8, вне многобайтной последовательности. |
| Граница/индекс EGC | Единица редактирования и выделения по поддерживаемым проектом таблицам; длина в байтах и ширина различаются. |
| Логическая позиция | Строка от нуля и явно названная колонка в UTF-8 bytes, UTF-16 units или EGC; просто «колонка» недостаточно. |
| Позиция сервиса UTF-16 | Строка от нуля и code units UTF-16 внутри строки; surrogate pair занимает две единицы. |
| Визуальная позиция | Колонка терминальных ячеек/визуальная строка после tab expansion, width policy и возможного переноса; это не смещение сервиса. |
| Байт импорта | Смещение сериализованного исходника через метаданные переводов строк; CRLF занимает два импортированных байта и один канонический LF. |

Преобразования проверяют snapshot, границы строк, кодировку, диапазон целого
числа и требуемый вид границы. Позиции вне диапазона, внутри UTF-8 sequence,
surrogate pair UTF-16 или обязательной EGC отклоняются без тихого clamp.
Hit testing внутри tab или широкой EGC использует явную левую/правую affinity
и возвращает границу EGC. Диапазоны токенов могут иметь scalar boundaries;
отрисовка может покрыть содержащую EGC, но изменение всё равно проверяет EGC.
Адаптер явно объявляет кодировку сервиса UTF-8 или UTF-16; неявный cast между
видами координат не допускается.

Смена width policy, ширины tab, viewport, темы или переноса инвалидирует нужные
layout caches; она не редактирует исходник, не продвигает `documentRevision`
и не создаёт историю undo. Реализация должна закрепить поддерживаемую версию
Unicode; предложение не обновляет существующие таблицы. См.
[Unicode text segmentation](https://www.unicode.org/reports/tr29/) и
[контракт позиции LSP](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#position).

## Области Markdown и обратимое отображение

Языковая область имеет идентичность/ревизию документа, стабильную внутри
поколения идентичность области, поколение mapping, идентификатор языка и
поколение контекста. Fence delimiters и info strings принадлежат Markdown;
вложенный провайдер получает тело fence. Aliases определяются явным реестром;
неизвестный alias даёт plain text. Изменение fence, вложенности, prefix,
deindent или языка инвалидирует прежнюю идентичность/mapping до применения
результатов провайдера.

Адаптер владеет кусочным отображением вложенного исходника в host. Каждый
source-backed segment хранит оба диапазона и данные преобразования координат;
удалённые отступы, blockquote/list prefixes и синтетические символы отмечены
как явные разрывы. Одного численного сдвига недостаточно. Подсветка отдельно
отображает source-backed части и не окрашивает удалённые prefixes как вложенный
исходник.

В первой реализации вложенное изменение допустимо только когда весь диапазон
и границы вставки однозначно отображаются в один непрерывный source-backed
segment. Диапазоны через удалённые prefixes, deindent gaps, синтетический или
неотображённый текст, неоднозначные концы и границы области отклоняются.
В преобразованной области также отклоняются вставляемые переводы строк,
требующие синтеза host prefixes. Прямое редактирование исходника доступно.
Все дополнительные изменения completion должны пройти проверки и остаться
непересекающимися в host до **любого** изменения; один отказ отклоняет весь
completion. Возвращается типизированная ошибка mapping без угадывания места
вставки. Более богатое обратное отображение требует своего проверенного
контракта и fixtures.

## Асинхронные провайдеры и время жизни callbacks

Синтаксис, semantic tokens и completion — независимые capabilities. Каждый
запрос владеет snapshot исходника, картой области, параметрами и snapshot
контекста либо его неизменяемым владеющим handle. Envelope фиксирует
идентичность/ревизию документа, идентичность области/поколение mapping,
поколение контекста, провайдера/сессии и запроса. Completion дополнительно
фиксирует generation-safe token жизни представления, исходные курсор/выделение
и поколение навигации. Владеющий результат повторяет envelope и объявляет
кодировку координат.

Worker публикует ограниченные владеющие сообщения через существующий
mailbox/routing. Он не создаёт второй event loop/runtime, не захватывает сырые
widgets и не вызывает UI callbacks напрямую. Остановка worker рекомендательная;
право UI admission — нет. Явный cancel немедленно и безвозвратно отзывает право
запроса на публикацию, включая производное completion proposal, даже без нового
запроса. Уже поставленные в очередь или конкурирующие ответы не восстанавливают
это право. Retry всегда требует нового поколения запроса.

На UI owner разрешается документ и, для completion, жизнь представления, затем
сравниваются все guards. Представление должно всё ещё показывать тот же
документ. Навигация, включая уход и возврат к тому же курсору, инвалидирует
completion, продвигая поколения запроса и навигации. Закрытие/remount,
изменение текста/контекста/области или новый
запрос отклоняют старый результат. Первая реализация не переносит устаревшие
ответы на новую ревизию. Синтаксис/семантика публикуются для документа и не
требуют живого запросившего представления, но требуют живого документа и всех
document/region/context/provider/request guards. После закрытия последнего
владельца остаётся только освобождаемый worker snapshot, не доступный для
действий документ.

Каждый запрос имеет одноразовое состояние UI admission. Для всех видов ответа,
включая синтаксис, проверяются pending/unrevoked и зафиксированные guards.
Допущенный ответ помечается consumed до публикации результата или любого
callback: повторная/reentrant доставка получает типизированный consumed/stale
result. Отозванный запрос получает типизированный cancelled/stale result.
Ошибка обработки не открывает consumed запрос заново; явный retry использует
новое поколение. Consumed completion reply может создать отдельное живое
одноразовое proposal с теми же зафиксированными guards. Потребление ответа не
разрешает дальнейшее принятие после отмены, навигации или инвалидации.

Принятие completion снова проверяет живое proposal и guards непосредственно
перед одной транзакцией и помечает proposal consumed до изменения или доставки
callbacks. Между финальной проверкой guards и установкой состояния нет
прикладного validation callback, уведомлений или других произвольных callbacks.
После установки владеющие observations
доставляются в принятом UI callback ordering. Callback может выполнить reentry
или удалить представление/документ; перед следующей доставкой жизнь разрешается
снова. Ошибка уведомления не требует повторять изменение. Устаревший ответ
отбрасывается с доступным приложению типизированным статусом; временная ошибка
провайдера сохраняет текст и fallback syntax, допускает явный retry с новым
поколением запроса. Переполнение очереди отклоняет работу или объединяет
заменяемые запросы; оно не блокирует ввод и не создаёт неограниченный backlog.

## Ошибки, бюджеты и видимая работа

Read-only представление запрещает пользовательское изменение, cut, принятие
completion и undo/redo; копирование, навигация и выделение доступны. Другое
записываемое представление может менять тот же документ; позиции read-only
представления отображаются. Явные программные изменения документа допустимы,
если отдельная document-level write policy их не запрещает. Сам запрос/ответ
не предоставляет право записи.

До принятия подготавливаются UTF-8 validation, EGC boundaries, метаданные
переводов строк, все mapping, допуск истории и выделение памяти. Неверный
текст/координаты, invalid operations, устаревшие identity/revision,
consumed/revoked requests, read-only, неоднозначный mapping,
лимиты, ёмкость истории, исчерпание поколений и OOM — разные типизированные
категории ошибок. Отказ до принятия сохраняет текст, метаданные, ревизию,
позиции всех представлений, историю и redo. Нельзя обрезать целую операцию или
молча удалить её запись истории. Целые старые группы могут вытесняться только
при успешном допуске; явно выключенная история допускает незаписанные
изменения. Ошибка публикации/callback после принятия отдельно сообщает уже
принятое изменение без отката или повторного применения. Точные C++ result
types остаются открытыми.

Ниже — **предлагаемые настраиваемые defaults и бюджеты оценки**, а не измерения,
реализованные лимиты или обещание производительности. Для G0 нужны модель учёта
хранилища и самостоятельные provider measurements; будущая реализация
Document/TextArea не требуется. Фактические гарантии edit/OOM/view-render и
UI timing targets относятся к приёмочным проверкам последующей реализации
TextArea/синтаксиса. Лимиты однострочного редактора сохраняются.

| Настройка | Предложение | Причина / поведение на границе |
|---|---|---|
| Канонические байты документа | 1 MiB | Ограниченный первый многострочный workload; слишком большое изменение отклоняется. |
| Логические строки | 65,536 | Индексация ограничена отдельно от байтов, включая последнюю пустую строку. |
| Одна логическая строка | 256 KiB UTF-8 | Проверка длинной строки без неограниченного line scan. |
| История | 128 групп, 32 MiB retained storage | Два полных snapshot по 1 MiB не помещаются в текущий однострочный бюджет истории 1 MiB; учитывать metadata, entry overhead и retained capacities. Слишком большая целая группа отклоняется. |
| Ожидающая работа провайдера | 1 active + 1 заменяемый newest request на документ/capability | Ограничить всплески; cancellation не разрешает безграничный backlog. |
| Один ответ провайдера | 4 MiB со всеми владеющими ranges/strings | Ограничить validation/publication allocation; слишком большой ответ отклоняется целиком. |
| Completion list | 256 кандидатов в пределах byte budget | Ограничить работу popup/model; усечение требует явного incomplete-list flag. |
| Syntax debounce ввода | 50 ms | Объединять всплески; явный completion запускается сразу. |
| UI edit preparation p95 | ≤ 8 ms на объявленном evaluation workload | Цель последующей приёмки TextArea с оценочным кадром 60 fps / 16.7 ms; это не default frame profile Portals. |
| Incremental syntax p95 | ≤ 50 ms на объявленном workload | Цель оценки отзывчивости отдельно от debounce. |
| Syntax worker scratch | ≤ 32 MiB сверх владеющих document/result storage | Бюджет оценки; peak native и WASM memory измеряются отдельно. |
| Добавленный compressed WASM | ≤ 2 MiB для syntax runtime и всех требуемых grammars | Бюджет выбора кандидата относительно той же сборки без синтаксиса. |

Отрисовка передаёт видимые строки/runs существующему renderer без widget на
каждый токен. Скрытые представления пропускают подготовку видимого layout/render
и не запрашивают постоянную перерисовку. Нужные для корректности mapping позиций
и инвалидация кэша сохраняются. Document-level provider work может продолжаться
для активного потребителя; скрытие представления не редактирует документ.
Rope/piece-table, delta history и новый renderer range API требуют измеренной
необходимости, а не являются предпосылками этого контракта.

## Выбор провайдера и оставшиеся gates

Нужно сравнить lexer со состоянием между строками и Tree-sitter для Pascal,
Markdown и C++: корректность edits/recovery, extent инвалидации, latency,
retained/peak memory и полный native/WASM size на одинаковых закреплённых
fixtures/toolchain. Документированные incremental trees и included ranges
Tree-sitter полезны, но не являются измерениями Portals; см.
[advanced parsing guide](https://tree-sitter.github.io/tree-sitter/using-parsers/3-advanced-parsing.html).
Разделение Markdown на block/inline grammar и документированное ограничение
WASM integration требуют проверки; см.
[upstream README](https://github.com/tree-sitter-grammars/tree-sitter-markdown/blob/a0a00f817d02412bd92c54d316f164d827b57b5c/README.md).

**Первое направление реализации — встроенный инкрементальный лексер с состоянием
между строками**, без внешних зависимостей, с обычным текстом для неподдержанных
областей. Это решение о разработке, а не готовый токенизатор. Tree-sitter остаётся
отложенным кандидатом; контракт не добавляет runtime или грамматики в зависимости.

В закреплённой версии Tree-sitter документирован вызов `abort` при ошибке
штатного аллокатора. Возврат null из собственного аллокатора не обеспечивает
восстановление: создание парсера и копирование поддеревьев содержат обращения
к выделенной памяти без проверки. Это несовместимо с предложенным контрактом
типизированных ошибок. Для пересмотра нужны доказательства ограниченной памяти,
безопасной обработки сбоев и передачи типизированной диагностики, включая
аллокации сканеров. См. закреплённые
[контракт аллокатора](https://github.com/tree-sitter/tree-sitter/blob/7f877d3c080f7f8c7764ee1f68002fc52636cacb/lib/include/tree_sitter/api.h#L1498)
и [реализацию](https://github.com/tree-sitter/tree-sitter/blob/7f877d3c080f7f8c7764ee1f68002fc52636cacb/lib/src/alloc.c).
Проверка исходников не означает, что выполнялись аварийные запуски или
искусственные отказы памяти.

Неизвестные и ошибочные синтаксические области показываются обычным текстом;
отсутствие семантики сохраняет текущую синтаксическую подсветку. Токены старой
ревизии не применяются к изменённому тексту. Отсутствие или ошибка провайдера
не должны блокировать редактирование.

### Ограниченное сравнение

Стенд использовал runtime из ссылок выше, грамматики Pascal
`042119eca2e18a60e56317fb06ee3ba5c32cb447`, Markdown
`a0a00f817d02412bd92c54d316f164d827b57b5c` и C++
`c009222808634c1014f82438d4883753516a2c24`. Использованы MSVC 19.51 Release
и Emscripten 6.0.12 с Node 24.21.0, уровень оптимизации 2. Для каждой платформы
выполнены три отдельных процесса измерения задержек: 3 прогрева и 15 отсчётов
на сценарий. Всего 63 сценария с входами 1 KiB, 64 KiB и 1 MiB: первый разбор,
обычные изменения и изменения состояния лексера. В каждом процессе прошли
также 12 граничных проверок.

В таблице — медиана трёх значений p95 отдельных запусков для обычной замены
одинаковой длины в тексте 1 MiB, в миллисекундах:

| Язык | Native прототип лексера | Native Tree-sitter | WASM прототип лексера | WASM Tree-sitter |
|---|---:|---:|---:|---:|
| Pascal | 0.754 | 11.274 | 0.275 | 6.884 |
| Markdown | 0.698 | 284.747 | 0.552 | 206.113 |
| C++ | 0.157 | 10.436 | 0.190 | 5.219 |

Для 15 отсчётов p95 по ближайшему рангу совпадает с максимальным отсчётом.
Это описание запусков, не устойчивая оценка хвоста распределения. Прототип
лексера вычисляет состояния и отпечатки строк, а не синтаксические токены.
Сравнение каждого движка с его собственным полным пересчётом прошло, но оно
не доказывает одинаковые языковые возможности или грамматическую корректность.
Замены имели одинаковую длину и не меняли число строк. Время не включает
замену текста, преобразование координат, создание парсера, UI и уничтожение
объектов. Проверки токенов, изменений длины и числа строк, обработки отказов
и полной задержки ввода относятся к реализации.

В отдельных запусках с перехватом аллокаций максимальный наблюдавшийся живой
payload запросов runtime составил 174 589 568 байт native и 167 038 844 байта
WASM. Учёт не включает C++-стенд и непроверенные аллокации сканеров;
реаллокация через выделение-копирование-освобождение изменяет временный расход.
Это не peak RSS процесса и не подтверждение бюджета scratch в 32 MiB.
Задержки инструментированных запусков в таблицу не включены. Временный WASM
с runtime, грамматиками и стендом занимал 4 116 577 байт (901 646 байт gzip),
модуль сравнения лексера — 207 883 байта (71 676 байт gzip). Это размеры
отдельных стендов, не изменение размера приложения Portals и не дополнительные
поставляемые модули.

Корневые лицензии runtime и грамматик — MIT. У runtime отдельно имеется
[уведомление для данных Unicode](https://github.com/tree-sitter/tree-sitter/blob/7f877d3c080f7f8c7764ee1f68002fc52636cacb/lib/src/unicode/LICENSE),
которое необходимо сохранять при распространении этих исходников. Проверка
не означает принятия или распространения зависимостей.

### Проверка контрактов и этапы реализации

Самостоятельная эталонная модель выполнила 76 трасс из 227 шагов: обращение
транзакций, повторный вход при публикации, устаревшие ответы и отмену.
Все 46 ограниченных модельных проекций совпали с ожидаемым результатом;
32 полных модельных сценария прошли, у 14 остаются невыполненные требования
к настоящей реализации. Пять проверок учёта памяти прошли для заданных
ёмкостей и накладных расходов, без измерения аллокаций C++. Четыре намеренно
сломанных варианта были обнаружены. Это проверка предложенных правил,
а не будущей реализации сегментации Unicode, отказов памяти, callbacks,
уничтожения workers, layout или отрисовки. Независимое ревью охватило владение,
повторный вход, допуск ответов и границу отказов провайдера.

**G0S: DEFERRED.** Минимальные semantic language, project/context inputs и среда
исполнения не выбраны. Recovery action — выбрать и проверить настоящий
backend/context/environment до начала семантической реализации. Это блокирует
PRTLS-161; синтаксическая реализация допустима после базового контрактного этапа.
Приведённые доказательства позволяют перейти к ней, но не фиксируют новые
публичные сигнатуры API. Последующая реализация должна проверить эти правила
как runtime regressions, реальные аллокации, работу представлений и UI timing.
Эти проверки настоящей реализации пока не выполнены.
