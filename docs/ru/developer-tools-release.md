# Инструменты упаковки и выпуска {#developer-tools-release-ru}

[Английская версия](../developer-tools-release.md) · [Инструменты разработчика](developer-tools.md) · [Порядок выпуска (англ.)](../releasing.md)

Здесь описаны поддерживаемые точки входа из `tools/package` и `tools/release`.
Команды репозитория выполняются из корня рабочего каталога. Создание веток,
загрузка артефактов и публикация требуют разрешения на выпуск.

`bundle.cmake` и `tools/release/package.cmake` принимают `-DHELP=ON`
(по умолчанию `OFF`): выводят встроенную справку и завершаются с кодом `0`
до проверки путей и записи файлов. Для PowerShell используйте
`Get-Help <путь-к-скрипту> -Full`; Python поддерживает `--help` и `-h`.

## Выбор инструмента

| Задача | Точка входа | Результат и действия |
| --- | --- | --- |
| Собрать запускаемый архив из коммита | `tools/package/bundle.ps1` или `cmake -P tools/package/bundle.cmake` | Локальная Release-сборка, SDK, пять примеров, HTML, проверки и архив |
| Запустить пример из распакованного архива | Копия `run.ps1` или `run.sh` в архиве | Запуск выбранного терминального приложения |
| Подготовить PR выпуска | `tools/release/start.ps1` или `start.py` | Версия и примечания во временном worktree; коммит, push и PR |
| Подготовить метаданные | `tools/release/metadata.py prepare` | Локальные JSON и примечания к выпуску; без сети |
| Собрать артефакты выпуска | `tools/release/package.cmake` | Помощник CI, использующий проверенные сборки и подтверждения проверок |
| Опубликовать проверенные артефакты | `tools/release/publish.py` | Публикация из CI: черновик GitHub, загрузка, проверка, выпуск |
| Общие функции CMake | `tools/package/common.cmake` | Внутренний подключаемый файл без самостоятельного CLI |

Перед подготовкой зарезервируйте ID задачи выпуска. Используется компонент
`BUILD`: для задачи `PRTLS-143` и тега `v0.3.1` ветка имеет имя
`task/PRTLS-143-BUILD-prepare-release-v0.3.1`, коммит и PR — заголовок
`[PRTLS-143][BUILD] Prepare release v0.3.1`. Передавайте настоящий зарезервированный ID.
CLI проверяет синтаксис ID; общий реестр задач он не проверяет.

## Сборка запускаемого пакета

Исходники: [реализация CMake](../../tools/package/bundle.cmake),
[обёртка PowerShell](../../tools/package/bundle.ps1).

Требования: CMake 3.24+, Git, x64-хост Windows или Linux, компиляторы C++23 и C.
На Windows нужны MSVC для обоих языков и `dumpbin` в окружении компилятора;
на Linux — `ldd`. Генератор по умолчанию требует Ninja. Для цели документации
нужны Doxygen 1.18+, Python 3.10+ и Mermaid CLI (`mmdc`/`mmdc.cmd` с Node.js)
в `PATH`. Выбранный коммит должен содержать инструменты упаковки.

Выберите новые абсолютные пути для рабочего каталога и архива. Пример пишет
вне репозитория; замените пути подходящими для вашей машины:

```powershell
pwsh -NoProfile -File tools/package/bundle.ps1 `
  -WorkDir C:/artifacts/portals-build-001 `
  -OutputArchive C:/artifacts/portals-001.zip `
  -PythonExecutable python
```

`bundle.ps1` принимает относительные пути и преобразует их в абсолютные перед
вызовом CMake. При прямом вызове CMake пути уже должны быть абсолютными:

```powershell
cmake -DSOURCE_DIR=C:/src/portals -DSOURCE_REVISION=HEAD `
  -DWORK_DIR=C:/artifacts/portals-build-002 `
  -DOUTPUT_ARCHIVE=C:/artifacts/portals-002.zip `
  -DPYTHON_EXECUTABLE=python -P tools/package/bundle.cmake
```

На Linux используйте расширение `.tar.gz` и те же параметры CMake. Если значение
содержит пробелы, заключите весь аргумент `-DNAME=value` в кавычки. Все `-D`
указываются перед `-P`.

### Параметры пакета

Параметры CMake передаются как `-DNAME=value`. Прочерк в колонке PowerShell
означает, что параметр доступен только через точку входа CMake.

| Параметр CMake | Параметр PowerShell | По умолчанию | Назначение и ограничения |
| --- | --- | --- | --- |
| `SOURCE_DIR` | `-SourceDir` | Обязателен напрямую; обёртка использует репозиторий со скриптом | Существующий абсолютный путь к Git-репозиторию |
| `SOURCE_REVISION` | `-Revision` | `HEAD` | Ревизия, разрешаемая в коммит; архивируются только закоммиченные файлы |
| `WORK_DIR` | `-WorkDir` | Обязателен | Новый абсолютный путь вне исходников; файл, каталог и символическая ссылка по этому пути должны отсутствовать; `;` запрещён |
| `OUTPUT_ARCHIVE` | `-OutputArchive` | Обязателен | Новый абсолютный путь вне рабочего каталога; файл, каталог и символическая ссылка должны отсутствовать; `;` запрещён; Windows `.zip`, Linux `.tar.gz` |
| `GENERATOR` | `-Generator` | `Ninja` | Генератор CMake для сборки и проверки потребителя SDK |
| `PARALLEL` | `-Parallel` | `2` | Целое `>=1`; обёртка дополнительно ограничивает диапазоном 1–1024 |
| `MSVC_RUNTIME_LIBRARY` | `-Runtime` | `MultiThreaded` | Windows: `MultiThreaded` (`/MT`) или `MultiThreadedDLL` (`/MD`); на Linux записывается `not-applicable` |
| `CXX_COMPILER` | `-CxxCompiler` | Поиск CMake | Явный компилятор C++ |
| `C_COMPILER` | `-CCompiler` | Поиск CMake | Явный компилятор C |
| `MAKE_PROGRAM` | — | Поиск CMake | Значение `CMAKE_MAKE_PROGRAM`, например путь к Ninja |
| `PYTHON_EXECUTABLE` | `-PythonExecutable` | Не задан | Запускает проверку HTML-ссылок и передаёт интерпретатор проверке после распаковки; отдельный параметр от поиска Python при сборке справки |
| — | `-CMake` | `cmake` | Исполняемый файл CMake для обёртки |

Без `PYTHON_EXECUTABLE` явная дополнительная проверка HTML-ссылок отмечается
как `linkStatus=not_run`. Упаковка релиза требует `passed`, поэтому для релизного
пакета задайте этот параметр. Требование Python для сборки справки сохраняется.

### Результат и восстановление после ошибки

Скрипт экспортирует коммит через `git archive`; незакоммиченные и игнорируемые
файлы исключены. Он конфигурирует Release с тестами, примерами и справкой,
отключает инструменты и фаззеры, собирает пять примеров и документацию,
устанавливает SDK. Проверка импортов зависимостей отвергает динамический CRT,
если запрошен `/MT`.

В рабочем каталоге остаются `source.tar`, `source/`, `build/`, содержимое пакета
`portals-mvp-<platform>-x64-release/`, промежуточный архив, результаты проверок
после распаковки и, при успехе, `bundle-receipt.txt`. Итоговый архив содержит:

- `bin/`: dashboard, gallery, custom widget, editor history и click handlers;
- `install/`: SDK; `examples/`: исходники и внешний проект-потребитель SDK;
- `docs/html/`, `themes/`, `data/`, `licenses/`, скрипты запуска и `manifest.json`;
- `verify/`: проверку CMake после распаковки, общие функции и проверку HTML-ссылок.

Перед копированием архива на файловую систему результата и созданием итогового
файла без перезаписи проверяются новая распаковка и перенесённый SDK с проектом-
потребителем. SHA-256 фиксирует байты исходников, содержимого и архива; это
проверки целостности, не цифровые подписи. Интерактивная проверка в настоящем
терминале выполняется отдельно.

CMake возвращает 0 при успехе и ненулевой код при ошибке проверки или сборки.
Обёртка выбрасывает исключение при ошибке CMake; `pwsh -File` завершается
с ненулевым кодом. Рабочие файлы сохраняются для диагностики. Для повторной
попытки выберите новые пути: скрипт не очищает прежний рабочий каталог.

## Запуск распакованного примера

Исходники: [PowerShell](../../tools/package/run.ps1),
[POSIX shell](../../tools/package/run.sh).
Скрипты копируются рядом с `bin/` в архиве. Запускайте эти копии; экземпляры
в репозитории не ищут программы в каталоге вашей сборки.

```powershell
pwsh -NoProfile -File C:/artifacts/unpacked/portals-mvp-windows-x64-release/run.ps1 -Example gallery
```

```sh
./run.sh gallery
```

`run.ps1` принимает `-Example` (по умолчанию `dashboard`) и оставшиеся позиционные
`ExampleArguments`. В `run.sh` первый позиционный аргумент выбирает пример
(при отсутствии — `dashboard`), остальные аргументы передаются программе.
Допустимы `dashboard`, `gallery`, `custom_widget`, `editor_history`, `click_handlers`.
Оба скрипта находят `bin/` относительно своего расположения и возвращают код
приложения. PowerShell отклоняет неизвестный пример и выбрасывает исключение,
если исполняемый файл отсутствует. Shell сообщает неизвестное имя в stderr
и возвращает 2; ошибки запуска обрабатываются по правилам оболочки. Скрипты
не меняют настройки среды выполнения и не ищут компилятор. Совместимость
бинарных файлов описана в манифесте и [руководстве по пакетам](package.md).

## Подготовка pull request выпуска

Исходники: [PowerShell](../../tools/release/start.ps1),
[Python](../../tools/release/start.py). Выберите один вариант. Первый работает
в Windows PowerShell 5.1/PowerShell 7, второй — в Python 3.10+.
Оба требуют Git, чистого рабочего каталога с учётом отслеживаемых и неотслеживаемых
файлов, GitHub `origin` с одним push URL того же репозитория и доступа к сети.
Обычный запуск также требует авторизованного GitHub CLI (`gh`). Автор коммитов
Git и права push/создания PR должны быть настроены заранее. Игнорируемые файлы
начального рабочего каталога в проверку чистоты не входят.

Начните с просмотра; замените тег на планируемый:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/release/start.ps1 -Tag v0.3.1 -TaskId PRTLS-143 -DryRun
python tools/release/start.py v0.3.1 --task-id PRTLS-143 --dry-run
```

Для разрешённой подготовки уберите `-DryRun` / `--dry-run` из одной команды.
Параметр политики выполнения PowerShell действует только в этом процессе.

| PowerShell | Python | По умолчанию и контракт |
| --- | --- | --- |
| `-Tag` (также позиционный аргумент 0) | Позиционный `tag` | Обязателен при подготовке; `vX.Y.Z` или `vX.Y.Z-rcN`, без ведущих нулей, `N` больше нуля |
| `-TaskId` | `--task-id` | Обязателен `PRTLS-N` или `PRTLS-N.N`; каждая числовая часть больше нуля и без ведущих нулей; компонент — `BUILD` |
| `-DryRun` | `--dry-run` | Выключен; JSON-поля `tag`, `task_id`, `branch`, `commit_title`, `pr_title`, `base`, `main_commit`, `changed_files`, `dry_run=true` |
| — | `--dispatch-merged EVENT_JSON` | Только Actions; несовместим с аргументами подготовки |

Dry run выполняет `git ls-remote` и требует сети. Он не пишет файлы/ссылки Git
и не загружает объекты через fetch. Коммит удалённого main уже должен присутствовать
локально. Если подготовительная ветка или тег существуют, просмотр завершится
ошибкой; обычная команда проверяет и продолжает существующую подготовку.

Обычная команда получает main, подготавливает только `CMakeLists.txt` и
`ReleaseNotes.md` во временном worktree, создаёт коммит, отправляет ветку и создаёт
PR, выводя его URL. Нужен один первый непустой раздел `Unreleased`.
Стабильный выпуск датирует этот раздел и оставляет пустой общий `Unreleased`;
RC копирует рабочие записи в датированный раздел RC. Версия CMake остаётся
числовой. Существующие ветки, теги и PR проверяются перед использованием;
конфликтующее состояние или закрытый PR требуют разбора. Заголовки коммита и PR
должны соответствовать задаче и выпуску. Другая подготовительная ветка с тем же
ID задачи или тегом отвергается. Прежняя ветка `task/release-<tag>` для выбранного
тега требует явной миграции; скрипт её не переименовывает. Force push и замена
тегов не выполняются.

Чистый временный worktree удаляется. Если в нём остаются изменения или
игнорируемые файлы, каталог сохраняется, а его путь выводится в stderr.
Дочерние процессы Git/gh получают `GIT_OPTIONAL_LOCKS=0`. Обе точки входа
возвращают 0 при успехе и 1 при обработанной ошибке подготовки; ошибки аргументов
argparse возвращают 2. Ошибки привязки параметров PowerShell происходят до
обработчика скрипта.

Слияние подходящего PR из того же репозитория в main разрешает настроенную
автоматизацию выпуска. Режим Python `--dispatch-merged` читает доверенное событие
слияния, требует `GITHUB_REPOSITORY=owner/name`, проверяет коммит checkout,
версию, примечания и предка в `origin/main`, создаёт аннотированный тег, если он
отсутствует, и запускает `release.yml` с публикацией. Нужен авторизованный `gh`
с правами записи contents/actions. Старые ветки `task/release-*` диспетчер
не принимает и автоматически не публикует. Это внутренняя точка входа Actions;
восстановление описано в [порядке выпуска (англ.)](../releasing.md).

## Локальная подготовка метаданных

Исходник: [metadata.py](../../tools/release/metadata.py). Python 3.10+;
GitHub CLI и сеть не нужны.

```powershell
python tools/release/metadata.py prepare --tag v0.3.0 `
  --repository ttldtor/portals --source . --output-dir C:/artifacts/portals-metadata
```

Тег должен соответствовать версии исходников и разделу примечаний.

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `prepare` | Обязательная подкоманда | Создание метаданных и примечаний |
| `--tag` | Обязателен | Стабильный/RC-тег; числовая основа совпадает с единственной версией проекта CMake |
| `--repository` | Обязателен | `owner/name`, буквы, цифры, `_`, `.`, `-`; используется в ссылках |
| `--source` | Обязателен | Каталог с `CMakeLists.txt` и `ReleaseNotes.md` |
| `--output-dir` | Обязателен | Создаётся с родителями; существующие `release.json` и `release-notes.md` перезаписываются |
| `--github-output` | Не задан | Добавляет `tag`, `version`, `prerelease` в файл; родительский каталог должен существовать |

Повторяющиеся выбранные разделы, пустые примечания и `Unreleased` стабильного
выпуска отвергаются. Для RC используется точный раздел или раздел базовой версии.
Относительные ссылки превращаются в GitHub-ссылки на тег; выход за корень
исходников запрещён. В примечания RC добавляется сообщение о тестовом выпуске.
Коды: 0 — успех, 1 — обработанная ошибка метаданных, файлов или кодировки,
2 — ошибка аргументов argparse. `GITHUB_OUTPUT` автоматически не читается:
при необходимости передайте путь явно.

## Сборка артефактов выпуска в CI

Исходник: [package.cmake](../../tools/release/package.cmake). Внутренний
помощник CMake 3.24+/Git, вызываемый [release.yml](../../.github/workflows/release.yml).
Он использует проверенные сборки и сам не запускает полные наборы тестов
Debug/Release. Workflow передаёт подтверждения после этих проверок. Не создавайте
фиктивные подтверждения для упаковки непроверенной сборки.

| Параметр `-D` | Обязательность | Контракт |
| --- | --- | --- |
| `SOURCE_DIR` | Обязателен | Абсолютный существующий checkout; HEAD и тег равны `SOURCE_REVISION` |
| `SOURCE_REVISION` | Обязателен | Полный коммит: 40 строчных шестнадцатеричных символов |
| `RELEASE_TAG` | Обязателен | Стабильный/RC-тег по правилам выше |
| `PLATFORM` | Обязателен | `windows` или `linux` |
| `PAYLOAD_DIR` | Обязателен | Распакованное содержимое пакета; проверяются манифест, хеши и `bundle-receipt.txt` в родительском каталоге |
| `OUTPUT_DIR` | Обязателен | Существующий каталог, изначально содержащий только `portals-<tag>-<platform>-x64-release.zip` (Windows) либо `.tar.gz` (Linux) |
| `WORK_DIR` | Обязателен | Новый абсолютный путь без `;`, отдельно от исходников, пакета и результата |
| `CONFIGURATION` | Обязателен | Строго `Release` |
| `PARALLEL` | Обязателен | Целое больше нуля; для сборки Linux-потребителя исходников |
| `TOOLCHAIN` | Обязателен | Идентификатор, совпадающий в обоих подтверждениях проверок |
| `DEBUG_GATE_RECEIPT`, `RELEASE_GATE_RECEIPT` | Обязательны | Абсолютные пути к обычным JSON-файлам без символических ссылок: schema 1, тег, коммит, платформа, конфигурация, toolchain и `headless=passed` должны совпадать |
| `C_COMPILER`, `CXX_COMPILER`, `GENERATOR` | Обязательны на Linux | Явные инструменты для автономной сборки потребителя исходников; на Windows не используются |
| `PAGES_DIR` | Не задан | Только Linux: новый отдельный абсолютный каталог для HTML и `.nojekyll` |

Исходники, содержимое пакета и результат должны быть абсолютными существующими
каталогами без `;` и без символической ссылки в последнем компоненте пути.
Результат находится вне исходников и отдельно от содержимого пакета.
Рабочий каталог и необязательный каталог Pages не должны содержать другие пути
или находиться внутри них. Существующие предки разрешаются для обнаружения
выходов через символические ссылки. Внутри пакета ссылки запрещены.

Помощник сравнивает архив с манифестом и подтверждением сборки. На Linux
добавляет исходники ZIP/tar.gz, собирает и запускает потребителя распакованных
исходников без загрузки зависимостей, добавляет HTML ZIP и при необходимости
копирует HTML для Pages. Обе платформы пишут `release-manifest-<platform>.json`
с размерами, хешами, инструментами и результатами проверок. Создаются локальные
файлы; развёртывание Pages выполняет следующий этап Actions.
При ошибке CMake возвращает ненулевой код; частичные файлы могут сохраниться.
Перед повтором восстановите ожидаемое содержимое входного каталога: команды
архивирования могут перезаписать прежние архивы исходников/HTML. Код 0 означает
успех проверок упаковки; проверка настоящего терминала остаётся отдельной.

## Проверка и публикация полного набора

Исходник: [publish.py](../../tools/release/publish.py). Python 3.10+.
Для публикации нужен авторизованный `gh` с чтением/записью релизов. Workflow
передаёт `GH_TOKEN`; скрипт использует окружение и настройки авторизации gh.
Локальная проверка не обращается к GitHub:

```powershell
$releaseCommit = (Get-Content C:/artifacts/release-candidate/release-manifest-windows.json -Raw | ConvertFrom-Json).commit

python tools/release/publish.py --directory C:/artifacts/release-candidate `
  --repository ttldtor/portals --tag v0.3.0 `
  --commit $releaseCommit --dry-run
```

Команда читает коммит из манифеста Windows-сборки. Оба платформенных
манифеста должны указывать этот коммит.

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `--directory` | Обязателен | Каталог с метаданными, примечаниями, Windows/Linux-манифестами и всеми перечисленными артефактами |
| `--repository` | Обязателен | GitHub `owner/name`; проверяется при создании клиента GitHub в режиме публикации |
| `--tag` | Обязателен | Стабильный/RC-тег, совпадающий с метаданными и обоими манифестами сборок |
| `--commit` | Обязателен | Коммит обоих манифестов; публикация дополнительно требует полный SHA из 40 строчных hex-символов и совпадение удалённого тега |
| `--github-output` | Не задан | После публикации добавляет `latest` и `pages_deploy`; при dry run игнорируется |
| `--dry-run` | Выключен | Только локальная проверка и перечень файлов; перезаписывает `release-manifest.json` и `SHA256SUMS` |

Обязательные проверки: `debug_headless`, `release_headless`, `bundle_smoke`,
`html_links`, все со значением `passed`. Набор включает оба платформенных
пакета, исходники ZIP/tar.gz и HTML ZIP. Неперечисленные артефакты, отсутствующие
или изменённые файлы, небезопасные имена и символические ссылки отвергаются.
Метаданные и примечания не загружаются как вложения; платформенные манифесты,
итоговый манифест и список хешей загружаются.

Публикация проверяет удалённый тег, создаёт или продолжает черновик, проверяет
его метаданные/вложения, загружает недостающие файлы, скачивает их для проверки
хешей и публикует выпуск. Конфликтующие вложения не перезаписываются.
После прерывания черновик остаётся для проверенного повтора. RC никогда
не становится latest; стабильная версия становится latest, если численно
новее текущей. `pages_deploy=true` означает, что тег оказался актуальным
стабильным выпуском; развёртывание выполняет следующий job. Скрипт не создаёт
теги и не сливает PR. Коды: 0 — успех, 2 — ошибка argparse, остальные ошибки
дают сообщение Python и ненулевой код (обычно 1).

## Общие функции пакета

Исходник: [common.cmake](../../tools/package/common.cmake). Подключается
созданием пакета, проверками распаковки и упаковкой релиза. Пользовательских
параметров, отдельного контракта окружения и самостоятельного запуска нет.

| Функция | Назначение |
| --- | --- |
| `bundleStageConsumer(source, destination)` | Скопировать внешний проект-потребитель, примеры и поддержку тестов |
| `bundlePublishArchive(pendingArchive, outputArchive, outputHash)` | Проверить копию на файловой системе результата, переименовать без перезаписи, вернуть SHA-256 |
| `bundleRun(...)` | Запустить команду и остановить CMake при ненулевом коде |
| `bundleJsonQuote(output, value)` | Экранировать строку для JSON |
| `bundleRequireNewPath(variable)` | Нормализовать и проверить новый абсолютный путь в переменной, вернуть вызывающему коду |
| `bundleValidateRelativePath(path)` | Отвергнуть небезопасный относительный путь пакета |
| `bundlePathIsInside(parent, child, output)` | Разрешить пути и вернуть признак вложенности; на Windows регистр игнорируется |
| `bundleRejectSymlinks(root)` | Отвергнуть символические ссылки в дереве пакета |
| `bundleWriteHashes(root, output)` | Сформировать отсортированный перечень хешей без `manifest.json` |
| `bundleVerifyHashes(root)` | Проверить схему 1, полный перечень файлов и хеши |

Общих флагов `--verbose`, очистки и перезаписи у этих инструментов нет.
Для диагностики используйте журналы вызывающей команды и сохранённые рабочие
каталоги. Унаследованные настройки (`PATH`, поиск компиляторов, настройки Git
и авторизация gh) продолжают действовать.


Точки входа Python также поддерживают `-h` / `--help` для справки. Скрипты
PowerShell с `[CmdletBinding()]` принимают стандартные общие параметры;
их показывает `Get-Help <script> -Full`.
