# Стили сцены {#styling-guide-ru}

Примеры существующего API ниже относятся к базовой версии `84b865e`; разделы **TBD** описывают будущую работу.

[English original](../styling-guide.md)

Используйте PSS для оформления, а C++-рецепт — для контролов, раскладки и действий.
PSS v0 уже доступен, как и загрузка стилей для всей сцены из файла.
Применение стилей в области конкретного контрола через `Ref` — **TBD — M1, U127**.

## Начните с одного правила

Этот фрагмент предполагает существующую бездействующую `ui::Scene` с именем
`scene` и подключённый `<portals/ui_style.hpp>`. Селектор определяет, какие
контролы изменить; декларации — какие свойства изменить.

```cpp
scene | ui::style("Button { bold: true; }");
```

Стадия владеет разобранным входом. Исходную строку можно освободить после
создания стадии. Если последующая установка должна заменять слой, а не добавлять
ещё один, дайте прикладному слою имя:

```cpp
scene | ui::style("Button { foreground: #4bb4dc; bold: true; }",
                  {.name = "buttons"});
```

## Зачем слою имя и как его использовать

`.name = "buttons"` именует **слой правил**, а не кнопку, селектор или ID контрола.
Никакой отдельной команды «применить стиль buttons» не требуется: при установке
слоя его правила сразу участвуют в оформлении всех подходящих контролов.
Здесь `Button` выбирает кнопки, а `buttons` позволяет позднее заменить слой.
Для однократной независимой установки имя необязательно.

Две отдельно созданные стадии с одинаковыми уровнем и именем выполняют именованную
установку с заменой: вторая заменяет первую, сохраняя положение слоя в каскаде.
По умолчанию уровень — `APPLICATION`:

```cpp
scene | ui::style("Button { foreground: #4bb4dc; bold: true; }",
                  {.name = "buttons"});
scene | ui::style("Button { foreground: #ffc855; bold: true; }",
                  {.name = "buttons"});
```

Теперь прикладной слой `buttons` задаёт янтарный цвет вместо голубого.
Замена устанавливает всю новую таблицу правил слоя, а не исправляет отдельные
объявления старой таблицы. Поэтому повторите в новой таблице правила, которые
нужно сохранить. Остальные слои остаются установленными.
Имя определяется **в пределах уровня**: `USER` с тем же именем — независимый
слой, и его объявленные свойства имеют более высокий приоритет:

```cpp
scene | ui::style("Button { bold: true; }",
                  {.tier = StyleTier::USER, .name = "buttons"});
```

Повторное использование одной стадии, в том числе её копии, сохраняет её общую
идентичность. Оно проверяет исходный настоящий handle слоя; после удаления слоя
такая стадия считается устаревшей. Это отличается от новой стадии с теми же
уровнем и именем, которая явно выполняет именованную установку с заменой.
Отдельные безымянные стадии добавляют независимые слои.

Именованная замена пригодна и во время работы: устанавливайте новую стадию
между кадрами в UI-потоке, когда сцена бездействует или из разрешённого UI callback.
Ошибка установки поступает в сборщик сцены и доступна через `checked()` или
политику отчётности runner. Конструирование аргументов до проверяемого входа
всё ещё может бросить исключение. Отклонённое обновление сохраняет прежние стили;
это не обещание отката произвольных побочных эффектов пользовательского callback.
Имя не вводит API поиска стиля или удаления слоя по имени. Для явной замены и
удаления по handle смотрите [слои стилей](style-layers.md).

### Независимые группы правил в одном tier

Несколько слоёв внутри одного `APPLICATION` позволяют обновлять отдельные
группы правил, не пересобирая все прикладные стили:

- `layout` — правила размеров;
- `validation` — оформление результатов проверки;
- `branding` — цвета приложения.

Этот фрагмент предполагает открытую сцену и успешные установки. У всех стадий
по умолчанию один tier — `APPLICATION`. Правила здесь только меняют оформление;
они не выполняют проверку данных.

```cpp
scene | ui::style("Button { min-width: 12; }", {.name = "layout"});
scene | ui::style("LineEdit { foreground: #ff5555; }", {.name = "validation"});
scene | ui::style("Button { background: #181c24; }", {.name = "branding"});

scene | ui::style("LineEdit { foreground: #55ff55; }", {.name = "validation"});
```

Последняя установка заменяет только таблицу правил слоя `validation`.
Слои `layout` и `branding` сохраняются. Положение `validation` тоже сохраняется:
замена не переставляет его в конец и не меняет порядок разрешения конфликтов
между слоями одного tier. При этом обычная специфичность селекторов продолжает
учитываться; позиция слоя разрешает равную специфичность.

**Имя необязательно, если заменять отдельные группы правил не нужно.**
Для простой установки достаточно `scene | ui::style("Button { bold: true; }")`.
Безымянные стадии тоже могут создавать независимые слои; имя нужно для явно
адресованной замены новой стадией, а не для самого разделения правил.

## Выберите конкретный контрол

Метод рецепта `.id()` задаёт принадлежащую контролу идентичность для селектора
с учётом регистра. Здесь кнопка получает ID `save` до монтирования рецепта:

```cpp
ui::Ref<Button> save;
auto scene = ui::scene(ui::vbox(
  ui::label("Ready"),
  ui::button(save, "Save").id("save")));

scene | ui::style(R"(
  Button#save { min-width: 12; bold: true; }
  Button#save:focused { background: #4bb4dc; foreground: #181c24; }
)", {.name = "form"});
```

Это фрагмент настройки, а не полная программа. Он устанавливает оформление;
добавьте действие и runner по примеру [декларативной композиции (EN)](../declarative-ui.md).
Стандартные контролы получают тип для стилей автоматически. Собственному виджету
нужны явные метаданные, а рисовать он должен с вычисленным стилем; см. [стили (EN)](../styles.md).

## Синтаксис

Это схема, а не грамматика парсера. Квадратные скобки обозначают необязательные
части и не являются буквальными символами PSS.

```text
stylesheet  := rule ...
rule        := selector { property: value; ... }
selector    := [Type or *] [.class ...] [#id] [:state]
```

Условия ID, класса и состояния могут идти в другом порядке. У селектора не
больше одного ID и одного состояния; совпасть должны все условия. Если типа нет,
начните с `.`, `#` или `:`. Идентификатор начинается с ASCII-буквы или подчёркивания,
затем допускает буквы, цифры, подчёркивания и дефисы. Комментарии: `/* ... */`.

| Свойство | Допустимое значение | Влияние |
| --- | --- | --- |
| `foreground`, `background` | `#RRGGBB` | Отрисовка |
| `bold`, `italic`, `underline` | `true`, `false` | Отрисовка |
| `min-width` | Целое от 0 до INT32_MAX, в ячейках терминала | Раскладка и отрисовка |

После каждого значения обязательна точка с запятой. `min-width` требует селектор
без условия состояния: смена фокуса не должна незаметно менять геометрию.
Ноль сохраняет измерение по содержимому. Политика размеров раскладки и обрезка
по-прежнему действуют.

Состояния оформления: `normal`, `focused`, `disabled`, `selected`, `header`
и `caret`. Они выбирают варианты вычисленного оформления, а не произвольные
имена событий. Селектор без состояния подходит ко всем вариантам; `:normal` —
только к обычному оформлению. Селектора `:hover` или левого/правого модификатора нет.

## Какая декларация победит

Каждое свойство разрешается независимо. В одной таблице специфичность сравнивается
по `(есть ID, число классов + число состояний, есть тип)`; при равной специфичности
побеждает более позднее правило. Пропущенное свойство сохраняет значение с меньшим
приоритетом. Явное `false` может переопределить `true`. Наследование от родителя
к потомку из этих правил не следует.

Стадии источников сцены включают [каскад слоёв](style-layers.md):

```text
widget defaults < DEFAULTS < THEME < APPLICATION < USER
```

Более высокий уровень побеждает раньше сравнения специфичности. В пределах уровня
при равенстве учитывается стабильный порядок установки слоёв, затем порядок правил.
Замена именованного слоя сохраняет его позицию. Уровень источника по умолчанию —
`APPLICATION`; `USER` задаётся явно. Установите прикладные и пользовательские слои
до подключения контроллера живой темы.

## Загрузите файл

```cpp
scene | ui::style(ui::file("themes/modern.pss"), {.name = "palette-file"});
```

Путь принадлежит стадии; файл читается, когда сцена принимает стадию. Обычная строка
считается содержимым PSS: имя файла из неё не угадывается. Включений других файлов,
наблюдателей за файлами и автоматической перезагрузки нет.
Сам `parsePssDocument(bytes, sourceName)` не выполняет файловый ввод-вывод.
Для независимо заменяемой палитры используйте таблицу `THEME` или живую тему,
а не прикладное переопределение, установленное выше неё.

## Отличия от CSS и QSS

Фигурные скобки и запись селекторов знакомы, но PSS — отдельный язык.
[Синтаксис QSS в Qt](https://doc.qt.io/qt-6/stylesheet-syntax.html) включает селекторы
потомков и детей, селекторы свойств и подконтролы. В PSS v0 их нет; также нет
списков селекторов, цепочек состояний, наследования и единиц длины.
Используйте `foreground`, а не CSS/QSS `color`; ячейки, а не `px`.

[Пользовательские свойства CSS](https://www.w3.org/TR/css-variables/) используют
`--name` и `var(...)`. PSS v0 не принимает ни то, ни другое. Существующие типизированные
параметры C++ и ограниченные выражения `mix(...)` описаны в [темах](themes-guide.md)
и отдельном [документе о compile-time стилях](compile-time-styles.md).

## Ошибки и дальнейшее чтение

Ошибки разбора, допуска и установки сохраняют типизированную диагностику.
Отклонённое обновление слоя сохраняет прежнюю таблицу и вычисленные стили;
проверяйте `scene.checked()` или используйте политику отчётности runner.
Обновления выполняются между кадрами в UI-потоке. Конструирование до проверяемого
входа всё ещё может бросить исключение. Диагностика источника хранит смещения
в байтах и координаты «строка/байтовый столбец» с отсчётом от единицы.

Полная replay-программа со строковыми источниками, слоями, живыми обновлениями
и обработкой отказа — [PSS consumer](../../tests/package_consumer/style_pss_after.cpp)
и [его общая настройка](../../tests/package_consumer/style_pss_support.hpp).
Именно исполняемый пример, а не этот фрагмент, определяет очистку и политику ошибок.

## Будущие параметры стилей {#future-style-parameters-ru}

**TBD — M5, U65/U128; invalidation U66, provenance U62:** направление записано,
но runtime PSS v0 не принимает переменные, функции или единицы измерения.
У пространств имён разные роли:

| Форма | Будущее значение |
| --- | --- |
| `$name` | Типизированное значение, назначенное или связанное с кодом, в том числе вычисляемое |
| `theme.text` | Семантический параметр активной PSS-темы |
| `this.text` | Разрешённое свойство текущего контрола |

Автоматической подстановки одноимённого `theme.text` вместо `$text` нет:
альтернативу задают явно правилом/политикой fallback. Перед `theme` и `this`
не нужен доллар.

Это **TBD — M5, U65/U128 эскиз синтаксиса**, а не исполняемый PSS:

```css
/* Proposed syntax; runtime PSS v0 does not accept it. */
Button {
  foreground: $text;
  background: theme.surface;
  min-width: len(this.text) + 2;
}
```

`this.text` означает разрешённый и отформатированный локализованный текст,
а не ID ресурса или последовательность UTF-8 байтов. `len` в размерном выражении
измеряет терминальные ячейки с той же WidthPolicy, что раскладка. Изменение
аргументов текста или языка инвалидирует зависимые измерения. Обычная кнопка
сохраняет intrinsic-размер без обязательной формулы; формула настраивает
ограничение. Рамку и padding нельзя учитывать дважды. База, диапазон и округление
процентов ещё не определены; CSS-единицы `px`, `em`, `vh`, `vw` не обещаны.

### Назначение из обработчика события

**TBD — M5, U65/U128:** запрошенная короткая запись — эскиз API; сигнатура
возврата и explicit-result overload ещё не зафиксированы:

```cpp
// API sketch; this is not currently compilable Portals API.
ui::currentScene.setParam("width", value);
```

По умолчанию предполагается checked-валидация всех затронутых consumers до
атомарной публикации. Отклонённый candidate сохраняет прежние параметры engine
и вычисленные стили, сообщая типизированную диагностику; обычному обработчику
не нужна ручная обвязка `changed` или `.result()`. Rollback не отменяет изменение
внешней Property/model или побочные эффекты callback.

Назначение относится к верхнему runtime-контексту переопределений сцены,
где значения темы уже доступны. Смена темы сохраняет явные runtime-переопределения
и пересчитывает зависимости. Изменяются только выражения, использующие параметр;
назначение не переписывает все одноимённые конкретные свойства. Согласование
с `USER`-уровнем — **TBD — M5, U65/U128**, без неявной смены существующего
приоритета правил. Scoped currentScene не должна удерживать глобальную владеющую
сцену или использовать предыдущую сцену вне допустимого контекста.

**TBD — M5, U65/U128:** optional fall-through — отдельно выбранная явная политика,
а не default. При ней неприменимое значение данных отводит декларацию к следующей
применимой нижней декларации/default, а не навсегда оставляет старое успешное
переопределение. Применимость проверяется для каждого consumer. Отсутствующий
параметр остаётся видимым в диагностике; checked-назначение в неизвестный параметр
отклоняется, а не создаёт его молча. Ошибки синтаксиса, неизвестные функции/поля,
ошибки памяти, неправильный поток, закрытая сцена и ошибки lifecycle
не маскируются под успешный optional fallback.

**TBD — M5, U65/U128:** `ui::Params`, `ui::params`, обновляемый по уведомлениям
`ui::bind(source, transform)`, оператор fallback `??` и функция вроде `grayScale`
— кандидаты, а не опубликованные API или утверждённая полная грамматика.
Обычные захваченные переменные C++ автоматически не наблюдаются: нужны
существующие уведомления Property/model, доставка на UI и очистка сцены.
Владеющие типизированные значения не вставляются как исполняемые фрагменты PSS.
Пересчитываются зависимости, а не все callbacks в каждом кадре: цвет запрашивает
PAINT, размер LAYOUT, равный результат не требует лишней перерисовки.
Дополнительный бюджет API/optional-политики отдельно пока не оценён.

**TBD — M1, U127:** допуск источника в области контрола через Ref остаётся отдельно.
Существующие [compile-time стили](compile-time-styles.md), типизированные tokens
и ограниченный `mix` — экспериментальные C++ API, а не возможности runtime-парсера.
