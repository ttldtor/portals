# Запуск приложения {#application-ru}

[Английская версия](../application.md)

Фасад [сцены](glossary.md#glossary-scene-ru) из [`<portals/ui.hpp>`](../../include/portals/ui.hpp)
создаёт контролы, подключает действия и запускает приложение в системном терминале.
**Apply** меняет надпись. **Exit** и F10 закрывают приложение.

```cpp
#include <portals/ui.hpp>

int main() {
  using namespace portals;

  ui::Ref<Label> status;
  ui::Ref<Button> exit;

  return ui::scene(ui::vbox(
    ui::label(status, "Ready"),
    ui::button("Apply", [status] {
      status.text() = "Applied";
    }),
    ui::button(exit, "Exit")))
    | ui::onClick(exit, ui::quit)
    | ui::onKey("F10", ui::quit)
    | ui::runApp();
}
```

Полный [исходник](../examples/guide_application.cpp) связывается с `portals::core`:
[подключение пакета](package.md). При запуске сцена создаёт контролы по описанию,
открывает терминал, обслуживает ввод и перерисовывает изменения. `ui::runApp()`
пытается восстановить терминал и очистить сцену, затем возвращает 0 при успехе
или 1 при ошибке. Стандартный отчёт об ошибке поступает в stderr после очистки.

`ui::Ref<Label>` наблюдает за надписью; контролом владеет сцена. Обработчик
захватывает ссылку по значению, а действия с контролом выполняются в UI-потоке. Присваивание текста само
запрашивает обновление. Подробности: [текстовые свойства](text-property.md),
[события](input.md), [корутины](ui-coroutines.md) для ожидания без блокировки ввода
и [диагностика](diagnostics.md) для настройки обработки ошибок.

## Настройка запуска

### Создание сцены внутри границы обработки ошибок

Передайте фабрику в `ui::runApp`, если создание ссылок, данных приложения или
сцены может завершиться ошибкой. Фабрика возвращает владеющую сцену, а обработчики
захватывают её локальные ссылки по значению. Полная программа без внешнего
`try`/`catch`:

\include{lineno} guide_application_factory.cpp

Полный [исходник](../examples/guide_application_factory.cpp). Эквивалентная форма
вызова — `ui::runApp(factory)`. Фабрика вызывается один раз внутри проверяемой
границы; она может вернуть и `std::expected<ui::Scene, ManagedError>`.
Прежние фабрики описаний также поддерживаются. Ошибки выделения памяти становятся
`NO_MEMORY`, остальные исключения фабрики — `CALLBACK_FAILED`.

Возвращайте новую холодную сцену текущего UI-потока. Уже подготовленная, но ещё
не запущенная сцена также допустима: её подготовка используется повторно.
Завершённая, закрытая или оставшаяся без состояния после перемещения сцена
отклоняется до обращения к терминалу: сохраняется прежняя ошибка, если она была,
иначе возвращается `CLOSED`.
Прежние ограничения перемещения активной или чужепоточной сцены сохраняются.

Если фабрика уничтожает локальную сцену и её очистка завершается ошибкой, runner
сохраняет и эту причину. Основная ошибка исключения или возвращённого результата
сохраняет причину очистки; дополнительные причины сверх единственного места
для cleanup учитываются в итоговом отчёте. Если фабрика вернула успешный результат,
но очистка промежуточной сцены завершилась ошибкой, терминал не открывается.

Возвращённая сцена сохраняет свои настройки и обработчик отчётов. Явный
`RunAppOptions::report` заменяет этот обработчик и получает ошибки, возникшие до
создания сцены. Сначала runner создаёт владеющую копию явного обработчика; если
копирование не удалось, ошибка поступает в stderr, а фабрика не вызывается.
Итоговый отчёт выполнения поступает после очистки. Создание аргументов и захватов
лямбды до входа в `runApp` остаётся за пределами этой границы.

Для приложения с командной строкой используйте
`factory | ui::runApp(argc, argv, ui::lyra::cli(lyraCli))` с
[`<portals/ui_lyra.hpp>`](../../include/portals/ui_lyra.hpp). Сначала разбираются
аргументы: справка возвращает 0, ошибка аргументов — 2; фабрика и терминал при
этом не запускаются. Ошибка создания или выполнения возвращает 1. Храните опции
до завершения синхронного вызова, а контролы создавайте по разобранным опциям
внутри фабрики. Подробнее — [разбор командной строки](cli.md).

### Настройки приложения

`ui::applicationOptions(...)` возвращает `ApplicationOptions` до создания приложения.
Здесь задаются частота кадров, ограничения ввода/вывода и политика экрана.
По умолчанию используется альтернативный экран с восстановлением экрана вызывающего
процесса при закрытии. Явная настройка `NativeScreenMode::MAIN_SCREEN` позволяет
оставить последний кадр на основном экране. Изменением размера окна управляет терминальный хост.

`ui::scene(factory)` позволяет создать состояние сцены или использовать `Application`
при построении контролов; `ui::configure(...)` выполняется после их создания.
`scene.onStop(...)` регистрируется до подготовки. В нём требуется отменить
внешних производителей и дождаться их завершения, а также освободить сервисы,
заимствующие приложение, до удаления managed-узлов.
Обработчики не должны уничтожать или повторно запускать сцену и runner.

## Собственная сцена или транспорт

Прямой [`Application`](../../include/portals/application.hpp) нужен для хуков
`ApplicationScene::input`, `prepare`, подготовки собственных виджетов и собственного
`ApplicationTerminal`. Этот runner возвращает `expected<ApplicationStats,
ApplicationError>`; вызывающий код проверяет результат и сообщает об ошибке после
очистки терминала. В обычном приложении этим runtime уже владеет фасад сцены.

**Подготовка кадра**

`prepare(application, size)` вызывается после единственной диспетчеризации цикла,
вне `tree.frame`, только когда изменённый кадр можно отправить. Синхронизируйте
привязки и фокус, получите один [фиксированный снимок](glossary.md#glossary-model-pin-ru)
`ModelFrame<T>` каждой модели: он сохраняет данные и доступность диапазонов.
Подготовьте все соседние представления с окончательными размерами по этим снимкам. VirtualTable и Chart хранят свои копии
снимка и подготовленных данных. ModelRequest передавайте поставщику явно вне рисования.

[Подготовка по компоновке](virtual-preparation.md) включает
`prepareViews(application, snapshot)` после предварительного прохода, вне кадра.
Представления используют общий владеющий снимок геометрии и уже закреплённые
модели; ограниченные повторные проходы не закрепляют модель заново.
Обычная подготовка с явным размером остаётся по умолчанию.

Цикл компонуёт и обходит видимые узлы, переносит локальные команды в координаты поверхности (`surface`)
и применяет отсечение (`clip`), собирает `CellBuffer` с собственным хранением данных до выхода из кадра. Пользовательский
виджет реализует `measure/arrange/paint`. Рисование выполняется без I/O,
изменения моделей, диспетчеризации и асинхронной работы. Инвалидация рисования
от новой геометрии поглощается текущим кадром; в простое периодических кадров нет.

**Пределы обслуживания и ошибки**

Между циклами удерживается один пакет терминала или сырой хвост и один отклонённый
CONTROL. Windows-события повторно не декодируются; POSIX-хвост сохраняет время
прихода. Сроки декодера сокращают ожидание. Заполнение ограниченного буфера приостанавливает
приём без потери клавиш. Каждый цикл имеет одну ограниченную диспетчеризацию
и не более одной отправки/вывода кадра. Изменения остаются в дереве, пока вывод
занят. Срок следующего кадра отсчитывается от действительной отправки/завершения.

EOF завершает декодер, доставляет принятый CONTROL и выводит переданные данные.
Будущие таймеры, DATA и сроки кадров не ожидаются; последнее изменение может
остаться невидимым. Сценарий воспроизведения ввода должен оставлять время до EOF. Отмена может остановить
цикл раньше без доставки остатка CONTROL.

`inputSlice` — положительный срок чтения. `read(now)` сразу возвращает deadline
без опроса. В простое чтение также проверяет размер; кадр требует инвалидации.
Чтение терминала служит ожиданием и ограничивает задержку рабочих публикаций.
`outputSlice` по умолчанию две секунды. Вывод, который можно продолжить после истечения срока или остановки, остаётся во владении
`FrameWriter`; транспортная ошибка, включая OUTPUT_UNCERTAIN, завершает запуск.
Неопределённые байты не повторяются. Закрытие требует продвижения терминального приложения или драйвера
и не имеет жёсткого общего срока.

ApplicationError сохраняет фазу и исходную ошибку. Поле `restoration` отдельно
содержит ошибку закрытия. Остановка закрывает Scheduler, вызывает `scene.stop`
для отмены и ожидания производителей, затем закрывает терминал. Этот порядок
соблюдается при ошибках и заранее запрошенной отмене. Во время активного
терминала сообщения и статистика в потоки вывода не печатаются.

**Часы и наблюдение**

Собственный терминал требует стандартных монотонных часов. Перегрузка с
ApplicationTerminal заимствует эксклюзивный транспорт до close и допускает
внедрённые монотонные часы; их эпоха должна совпадать с TerminalDeadline.
Сочетание искусственных часов с вводом-выводом системного терминала отклоняется. Транспорт обязан
соблюдать границы пакетов и владеть результатами. Оба запуска одноразовы.


Заимствованный ApplicationObserver получает длительности подготовки/рисования,
кодирования, вывода, остановки и закрытия. Без обработчика часы и память для
замеров не используются. Обработчику запрещены повторный вход и I/O; исключение
прерывает запуск. CONTROL_LATENCY измеряет вход собственного CONTROL в логических
часах; ApplicationStats хранит итоги. Хранилище выборок ограничивает вызывающий код.
Диагностика включается явно у Scheduler; экспорт выполняется после восстановления.

**Экран, мышь и восстановление**

`Application::run(scene)` использует openNativeApplicationTerminal.
По умолчанию `nativeScreen = ALTERNATE_SCREEN`: VT1049 открывает отдельный экран
и возвращает основной при close. Содержимое, позиция курсора и оформление
основного экрана сохраняются терминалом. Windows сохраняет информацию о видимости
курсора через console API; POSIX — сохранённый режим xterm 25.

`nativeScreen = MAIN_SCREEN` рисует прямо в основном экране и оставляет итоговый
кадр при выходе. Собственный транспорт и транспорт воспроизведения ввода управляют экраном самостоятельно.
Низкоуровневый TerminalSession управляет режимами без переключения экрана.
После изменения размера новая величина окна сохраняется. Терминальное приложение может перенести строки,
обрезать экран и ограничить курсор новыми размерами.

`nativeMouseReporting` по умолчанию true. POSIX запрашивает DECRQM для
кодирования 1005/1006/1015/1016, сохраняет tracking 9/1000/1001/1002/1003 через
XTSAVE и включает 1000+1006. Неподдерживаемое или несовместимое кодирование
даёт ошибку до изменения. Посторонние входные байты при старте сохраняются
до первого чтения в пределах max_input_bytes, плюс один фиксированный
незавершённый ответ. Нет ответа, избыток ввода или транспортная ошибка прерывают
подготовку; уже прочитанные данные при таком отказе потреблены.

При закрытии кодирование восстанавливается по ответам, tracking — XTRESTORE.
Это обходит дефект сохранённого кодирования xterm 390. Windows использует
консольные события мыши. Выключение nativeMouseReporting отключает только
мышиный протокол; управление экраном сохраняется.

Смонтированные [scroll-контролы](scroll-controls.md) до открытия нативного терминала
запрашивают профиль движения с удерживаемой кнопкой. POSIX дополнительно проверяет
1002 через DECRQM: статусы 1 (set), 2 (reset) и 3 (permanently set) допускают ввод;
0 (unknown), 4 (permanently reset) или отсутствие ответа явно прерывают подготовку.
Включается 1002+1006 вместо исходного профиля 1000; tracking восстанавливается тем же
XTRESTORE. У обычной сцены запрос выключен; явный `nativeMouseReporting=false`
имеет приоритет. Поздний mount не меняет открытый профиль. Собственный терминальный
host явно объявляет гарантии движения/release через `pointerCaptureCapabilities()`;
по умолчанию они отсутствуют. Потерянную последовательность или внешнюю потерю
фокуса/возможностей host завершает явной отменой capture: несообщённую потерю
фокуса ОС модель ввода не определяет.

Close получает новый modeTimeout независимо от отмены приложения, сначала
пытается завершить вывод, который допускает продолжение после частичного принятия. При ошибке всё равно пытается вернуть экран.
Windows отменяет старый поток записи и ожидает его завершения, синхронизируется с терминальным приложением после
неопределённого вывода и начинает бюджет восстановления. Восстановление начинается
с CAN; неопределённые байты кадра не повторяются. Подтверждённый DECSC защищает
курсор/оформление при частичном входе; неподтверждённый захват использует только
CAN. Остатки неудачного старта отбрасываются. Откат активируется до отправки входа,
обычный выход использует 1049 без дополнительного DECRC. Ёмкость очистки
проверяется заранее. Повторный close вывода не добавляет; деструктор пытается
очистить без гарантии успеха. Системные режимы и дескрипторы очищаются также при отказе VT.

Вложенные владельцы альтернативного экрана, конкурентный вывод и внешняя смена режимов
не поддерживаются. XTSAVE и DECSC перезаписывают одноуровневые сохранённые
состояния; предыдущие кэши сохранить нельзя. Неподдерживаемый VT1049, повреждённый
транспорт или завершение процесса могут оставить альтернативный экран активным.
Байты подготовки/очистки обходят FrameWriter и счётчики кадров; учитывайте их
в длительности жизненного цикла.
