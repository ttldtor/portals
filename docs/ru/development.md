## Проверка изменений

Task preflight помогает рано найти ошибку, затем сохраняются интеграционные
проверки и qualification milestone для применимой области. Локальный subset не
доказывает прохождение пропущенных runtime-контрактов.

| Уровень | Проверки и доказательства |
| --- | --- |
| Task | Явные regression/negative cases изменённого контракта, format/static checks, относящиеся public consumer и docs; чистая документация проверяется strict docs/links без выдуманных runtime targets |
| Integration | Для runtime/API: MSVC и GCC Debug/Release presets, полный настроенный CTest, installed/relocated и standalone consumers, naming/static checks, strict EN/RU docs; применимые sanitizer/lifetime checks |
| Milestone | Integration и supported-platform native terminal smoke, сопоставимые benchmarks и ограничения, SDK qualification, поставленный docs artifact/browser checks и независимое ревью |

[Локальный planner](developer-tools-build.md#tool-check-plan-ru) задаёт проверяемый
порядок focus tests по точным контрактам и настоящему CTest inventory. Пилот не
обосновывает исключение runtime tests: изменения C++ получают full plan.
Только зарегистрированные non-C++ Python fixtures могут сузить task preflight.
Новые, удалённые, переименованные, неизвестные или непокрытые файлы дают full.
Обязанности integration/milestone сохраняются; недоступные проверки остаются
NOT_RUN. Действующая PR policy и hosted MSVC/GCC/docs gates не изменены.

### Итоговая интеграционная проверка

Для итоговой проверки изменений runtime/API настройте и соберите каждый
нативный профиль на соответствующей платформе, затем запустите полный настроенный
набор CTest. Четыре профиля: `windows-msvc-debug`, `windows-msvc-release`,
`linux-gcc-debug` и `linux-gcc-release`:

```powershell
cmake --preset windows-msvc-debug
cmake --build --preset windows-msvc-debug
ctest --preset windows-msvc-debug

cmake --preset windows-msvc-release
cmake --build --preset windows-msvc-release
ctest --preset windows-msvc-release

cmake --preset linux-gcc-debug
cmake --build --preset linux-gcc-debug
ctest --preset linux-gcc-debug

cmake --preset linux-gcc-release
cmake --build --preset linux-gcc-release
ctest --preset linux-gcc-release
```

Запускайте каждую группу команд на соответствующей платформе. Для MSVC требуется
настроенная среда разработчика Visual Studio. Не добавляйте
`-R`, `-E` или другой фильтр к итоговому запуску CTest: `ctest --preset`
выполняет все тесты, зарегистрированные при настройке, включая тест установленного
пакета `portals.package-install`, который перемещает SDK и собирает новое приложение-потребитель.
Выбранный preflight полезен во время работы, но не заменяет полный запуск.

Интеграционная проверка также включает отдельное приложение-потребитель. В Linux
настройте, соберите и запустите его командами:

```powershell
cmake -S examples/consumer -B build/consumer -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/consumer
./build/consumer/portals_consumer
```

В Windows используйте Ninja и конфигурацию Debug:

```powershell
cmake -S examples/consumer -B build/consumer -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/consumer
.\build\consumer\portals_consumer.exe
```

Остальные интеграционные ожидания — проверки имён и static checks, строгая
документация на английском и русском со ссылками, применимые проверки sanitizer и
lifetime — перечислены в [реестре контрактов](../../tools/ci/check_contracts.json).
Сейчас матрица сборки и тестов PR запускает только Windows/MSVC Debug и Linux/GCC
Debug. Для Release нужны отдельные запуски: текущая матрица CI их не проверяет.

[Тестирование без терминала (на английском)](../testing.md) описывает обычный
набор тестов, проверки имён и терминальные фикстуры. [Фаззинг (на английском)](../../fuzz/README.md)
описывает ограниченные входные данные, тестовые цели для текста и настройку
санитайзеров. Автоматические проверки должны завершаться без ручного закрытия окон.

## Расширение UI API

Начните с публичных заголовков [`ui_controls.hpp`](../../include/portals/ui_controls.hpp),
[`ui_layout.hpp`](../../include/portals/ui_layout.hpp) и
[`ui_primitives.hpp`](../../include/portals/ui_primitives.hpp), если меняете создание
виджетов или размещение. Каждый тематический заголовок должен подключаться
самостоятельно. Для приложений, которым нужен широкий UI API, совместимый
umbrella-заголовок — [`ui.hpp`](../../include/portals/ui.hpp). Рецепты зависят от
заголовков, поэтому изменение клиентского обработчика пересобирает его единицу
трансляции; установленный SDK пересобирать не требуется.

Поведение ссылок и свойств сверяйте с [`ui_ref.hpp`](../../include/portals/ui_ref.hpp),
тестами [`property`](../../tests/property.cpp) и [`ui_ref`](../../tests/ui_ref.cpp).
Для фабрик сцен и ресурсов начните с [`ui_scene_resource.hpp`](../../include/portals/ui_scene_resource.hpp),
затем проследите разбор и подготовку в [`ui_scene_resource_parse.cpp`](../../src/widgets/ui_scene_resource_parse.cpp)
и [`ui_scene_resource_prepare.cpp`](../../src/widgets/ui_scene_resource_prepare.cpp).
Разбор и подготовка остаются частью существующего синхронного жизненного цикла сцены.

Дефолты контролов и переопределения рецептов используют общий список полей в
[`ui_control_context.cpp`](../../src/widgets/ui_control_context.cpp). При добавлении
поля сохраняйте оба контракта: слияние контекста сохраняет provenance отдельных
полей, а слияние рецепта заменяет метаданные origin после применения заданных
значений. False и ноль остаются допустимыми переопределениями. Сохраняйте порядок
обхода и потенциально бросающих копирований; дополняйте существующие тесты
контекста и дефолтов контролов.

Дополняйте тесты рядом с проверяемым поведением: например,
[`ui controls`](../../tests/ui_control_defaults.cpp),
[`ui layout`](../../tests/ui_layout.cpp),
[`ui scene resources`](../../tests/ui_scene_resource.cpp) и проверки прямого
подключения заголовков, например [`ui_controls_header.cpp`](../../tests/package_consumer/ui_controls_header.cpp),
[`ui_layout_header.cpp`](../../tests/package_consumer/ui_layout_header.cpp) и
[`ui_scene_pipeline_header.cpp`](../../tests/package_consumer/ui_scene_pipeline_header.cpp).
Эти тесты подтверждают, что публичные заголовки компилируются при использовании
непосредственно потребителем библиотеки.

## Сопровождение документации

### Проверки pull request

CI выбирает режим `docs`, если каждый изменённый файл относится к известным
входным данным документации: Markdown в `docs/`, изображения в `docs/images/`,
`README.md`, `ReleaseNotes.md`, макет документации, таблица стилей и конфигурация
Mermaid. В обоих режимах собирается строгая HTML-справка Doxygen и проверяются
локальные ссылки и якоря.

Остальные изменения выбирают `full`: дополнительно проверяются имена, сборки,
тесты и самостоятельные приложения-потребители в Windows/Linux. Сюда относятся
заголовки, подключённые исходники примеров, сборочные скрипты, инструменты CI
и неизвестные пути. Для удаления учитывается старый путь, для переименования —
оба пути. Пустой diff выбирает `full`.

Итоговый `CI result` выполняется после всех заданий, включая неудачные.
Он отклоняет ошибку выбора режима, а также отказ, отмену или пропуск выбранного
задания. Защита ветки должна требовать `CI result`. При внедрении workflow добавьте
его в обязательные проверки после первого выполнения. Проверки PR не публикуют
Pages и не создают релизы. Блоки кода Markdown отображаются в справке; сама
проверка документации автоматически их не компилирует.

```powershell
python -m unittest discover -s tools/ci -p test_checks.py -v
```

Задание naming кэширует скачанные Debian-пакеты, а не установленные инструменты
или результаты проверок. Оно всегда обновляет подписанные метаданные APT,
сверяет восстановленные архивы с их SHA256 и устанавливает прежний набор
инструментов. Отсутствующие, устаревшие и повреждённые архивы скачиваются заново.
Ключ включает платформу runner, архитектуру и отпечаток package policy.
Доступность кэша необязательна; все единицы трансляции проверяются и при попадании,
и при промахе. См. [валидатор кэша APT](developer-tools-build.md#tool-apt-cache-ru).

`Warm naming package cache` готовит кэш основной ветки, доступный последующим PR.
Задание запускается при изменении его action, workflow или валидатора в `main`,
либо вручную через Actions с выбранной веткой `main`. Оно устанавливает только инструменты и не повторяет
матрицу тестов проекта. Ручной запуск обновляет вытесненный кэш или изменившиеся
версии пакетов. Кэш отдельного PR не доступен другим независимым PR.

### Содержание и примеры

Согласовывайте [краткое руководство](index.md), [содержание](reference-map.md)
и `docs/DoxygenLayout.xml`. Краткое руководство описывает текущее использование;
заметки о версиях, проектные эскизы и датированные измерения сохраняют свой
исторический контекст и ссылаются на действующие контракты.

Используйте относительные Markdown-ссылки, доступные в рабочей копии.
Для примера, подключённого командой Doxygen, добавляйте ссылку на исходник для
читателей GitHub. Соберите `portals_docs` и выполните `check_links.py`, как описано
в [справке по инструментам](developer-tools-build.md#tool-documentation-ru).
Осмотрите навигацию сгенерированной справки.

Для схем потоков и владения используйте блоки `mermaid`: один Markdown отображается
на GitHub и в Doxygen. Указывайте `accTitle` и `accDescr`, делайте подписи короткими.
Вертикальные схемы и несколько небольших графов помогают сохранить читаемость.

Сборка требует Mermaid CLI и создаёт SVG локально. Общая тема находится
в `docs/mermaid.json`. Схемы масштабируются по ширине страницы; таблица стилей
адаптирует палитру SVG к светлой или тёмной теме. Проверяйте готовые изображения.
Существующие архитектурные SVG остаются обычными файлами изображений.

### Статусы возможностей

Разделяйте реализованные возможности, принятое направление и предложенный синтаксис.
Для недоступной возможности сохраняйте **TBD**, milestone и задачу-владельца;
если срок не определён, укажите это. Обновляйте пары EN/RU вместе.
Экспериментальные API времени компиляции имеют отдельный маршрут чтения.
Новые примеры показывают код приложения; replay/check/stress-сценарии относятся
к тестам. Проектный эскиз должен быть явно обозначен как предложение.

### Языки и обновление переводов

Английский исходник находится в `docs/<topic>.md`, русский перевод —
в `docs/ru/<topic>.md`. Относительный путь темы служит логическим именем страницы.
Сохраняйте существующие ID страниц и ссылки. Каждая переведённая страница
ссылается на ту же тему другого языка. У ссылки на непереведённый материал
указывайте язык, например **English**; не подменяйте её переходом на общую страницу.

Краткое руководство содержит быстрый старт и несколько следующих шагов.
Полный каталог задач храните в [руководствах пользователя](guides.md), а подробные
контракты группируйте в [содержании документации](reference-map.md). Общие ссылки
располагайте в одинаковом порядке в EN/RU и регистрируйте страницы в
`docs/DoxygenLayout.xml`. Его крупные группы могут учитывать маршрут чтения
конкретного языка. Сохраняйте общие исходники учебного примера в `docs/examples/`;
код проверяйте один раз, а ссылки — для каждого языка.

Записывайте исходную редакцию в HTML-комментарии рядом с заголовком перевода.
Пилот — [русское руководство по первому приложению](first-application.md):

```text
<!-- translation-source: docs/first-application.md
source-revision: d6ef4e75340772de254ef7a2d7514856e5f8e7f5
status: current
-->
```

| Состояние | Значение и действие |
|---|---|
| `current` | Перевод сверили с указанной исходной редакцией. При изменении исходника сравните и обновите обе страницы. |
| `outdated` | В исходнике есть непереведённые изменения. Добавьте видимую пометку об отставании и ссылку на более новый исходник; сохраните последнюю проверенную ревизию. |
| Отсутствует | Переведённой страницы нет. Сошлитесь на доступный язык и явно обозначьте его. |
| Не отслеживается | У страницы пока нет комментария с исходной ревизией. Это не подтверждает актуальность; добавляйте комментарий после сверки. |

Перед изменением переведённой темы сравните её исходник с записанной ревизией:

```powershell
git diff d6ef4e75340772de254ef7a2d7514856e5f8e7f5 -- docs/first-application.md
```

Команда учитывает изменения исходника в рабочем каталоге. Проверьте изменённые
объяснения, команды, имена API, условия владения и обработки ошибок, пометки TBD
и майлстоуны. Обновляйте перевод и записанную ревизию вместе. Если исходные правки
ещё не закоммичены, укажите их ревизию после коммита исходника; не помечайте перевод
актуальным относительно коммита, в котором этих правок нет. При изменении исходника
сверка нужна и тогда, когда в комментарии перевода ещё стоит `current`.
Пометка фиксирует проверку и не обнаруживает расхождения автоматически.

Переключатель языка в шапке открывает ту же тему на другом языке. Если у раздела
есть соответствующий явный якорь в обеих версиях, переход сохраняет раздел;
иначе открывается начало страницы. Отсутствие перевода отмечается в переключателе.
Прежние адреса русских страниц перенаправляют в `ru/` с сохранением якоря.
Языковые ссылки в Markdown работают и при чтении на GitHub.

Markdown поддерживается для выбранной ветки. Стабильная HTML-справка соответствует
последнему релизу, HTML из PR служит предпросмотром. Заметки о версиях и измерения
сохраняют область действия своей версии или даты. Перед добавлением другого языка
выберите каталог локали и уникальные ID страниц, добавьте обратные ссылки и
навигацию, затем зарегистрируйте язык в `docs/languages.json` и
`docs/DoxygenLayout.xml`. Сборка создаёт отдельный сайт и поисковый индекс
для каждого языка. Английская версия остаётся в корне, русская — в `ru/`.
Проверьте переходы между языками и прежние URL тестами из `tools/docs/`.

Соберите `portals_docs`, проверьте ссылки и обе темы оформления. Проверьте `lang`
и `xml:lang` корневого элемента HTML, переход на другой язык и обратно, определения
глоссария, ссылки на типы API и поиск учебного примера и нужных контрактов.
У каждого языка свои навигация и поиск. Справка C++ API остаётся английской;
с русского сайта на неё ведёт ссылка «C++ API — English». Эти проверки
относятся и к локальному каталогу HTML без сети.
Состояние перевода хранится в переведённом Markdown; отдельный каталог учёта
или генерация перевода не требуются.
