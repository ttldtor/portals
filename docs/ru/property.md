# Свойства и общее состояние {#property-ru}

[Английская версия](../property.md)

Для формы создайте состояние через `ManagedScene::state`. Сцена управляет его временем жизни и привязками. В примере два текстовых поля используют одно строковое значение: подтверждённая правка в одном обновляет другое. F10 закрывает приложение.

```cpp
#include <portals/ui.hpp>
#include <string>

int main() {
  using namespace portals;

  auto scene = ui::scene([](ManagedScene &owner) {
    return owner.state(std::string("Portals"))
      .transform([](auto model) {
        return ui::vbox(ui::lineEdit(model),
          ui::lineEdit(model));
      });
  });

  return scene
    | ui::onKey("F10", ui::quit)
    | ui::runApp();
}
```

[Полная программа](../examples/docs_state.cpp). Привязки описаны в [руководстве по состоянию и событиям](bindings-guide.md).

<details>
<summary>Создать Property в собственном дереве</summary>

Этот вариант нужен, если приложение само управляет `Scheduler` и `WidgetTree`. Снимок сохраняет прежнее значение после публикации нового.

```cpp
#include <portals/property.hpp>
#include <iostream>

int main() {
  using namespace portals;

  auto scheduler = Scheduler::create();

  if (!scheduler) {
    return 1;
  }

  auto tree = WidgetTree::create(**scheduler);

  if (!tree) {
    return 1;
  }

  auto root = (*tree)->root();

  if (!root) {
    return 1;
  }

  auto count = Property<int>::create(**tree,
    *root,
    0,
    Invalidation::PAINT);

  if (!count) {
    return 1;
  }

  auto before = (*count)->snapshot();
  if (!before) {
    return 1;
  }

  auto update = (*count)->set(1);

  if (!update) {
    return 1;
  }

  std::cout << (*before)->value << " -> "
            << update->snapshot->value << '\n';
}
```

</details>

<details>
<summary>Справка: владение и доставка уведомлений</summary>

`Property<T>` хранит значение на потоке интерфейса и публикует неизменяемые
[снимки](glossary.md) через обычные подписки `Scheduler`. Подключите `<portals/property.hpp>`.

**Создание и чтение**

`Property<T>::create(tree, target, initial, invalidation, options)` заимствует
дерево и его Scheduler: они должны пережить свойство. `target` — проверяемый
`Node<Widget>` этого дерева, получающий запрос перерисовки при изменении.
`Invalidation::LAYOUT` включает отрисовку. `PropertyOptions::max_observers`
ограничивает число наблюдателей; значение по умолчанию — 64.

Все операции и уничтожение выполняются на потоке UI. Вызов с другого потока
возвращает `WRONG_THREAD`; уничтожение с другого потока завершает процесс.
Данные рабочего потока сначала передавайте в UI через издателя Scheduler.

`snapshot()` возвращает проверяемый `expected<shared_ptr<const PropertyChange<T>>, TreeError>`; успешный результат владеет снимком с `value` и
монотонной `revision`, начинающейся с нуля. Снимок сохраняется после замены
значения, удаления источника и уничтожения свойства или дерева. Тип `T` должен
владеть всеми своими данными; изменяемые псевдонимы опубликованного значения
недопустимы. Передача снимка другому потоку допустима, если `T` можно уничтожить
там, где освобождается последний владелец. Возврат в UI из деструктора требует
живого UI-контекста и его потока. Ревизии сравниваются только внутри источника.

`observe(receiver, callback)` возвращает перемещаемый `Subscription`.
Обработчик получает `(W&, shared_ptr<const PropertyChange<T>>)` для `Node<W>`
того же дерева. Начальное значение автоматически не доставляется: прочитайте
`snapshot()` явно. Изменение других узлов в обработчике требует их явной
инвалидации.

**Изменение и доставка уведомлений**

`set(value)` проверяет узел и границу кадра, сравнивает значение и готовит
новый снимок. Равное значение сохраняет ревизию, очередь и запрос кадра.
Изменённое значение фиксируется после запроса инвалидации и до уведомлений.

Возврат `unexpected(TreeError)` означает, что управляемые библиотекой значение,
ревизия, очередь и инвалидация сохранены. Ошибки: `NO_MEMORY` при нехватке памяти,
`CALLBACK_FAILED` при исключении сравнения/копирования/перемещения,
`IDENTITY_EXHAUSTED` при исчерпании ревизий, `STALE_NODE` для удалённой цели,
`WOULD_BLOCK` внутри кадра. Создание аргумента до входа в API и внешние эффекты
пользовательского кода находятся за пределами этой гарантии.

Успешный `PropertyUpdate<T>` содержит снимок, `changed`, счётчики `accepted`,
`rejected`, `cancelled` и первую `notification_error`. Уведомления публикуются
в канал DATA с `SchedulerOverflow::REJECT`, по порядку регистрации. Очередь
может принять уведомление первого наблюдателя и отказать следующему. Значение
и запрос кадра остаются зафиксированы даже при отказе всем наблюдателям.

Счётчики описывают принятие в очередь. Отмена после принятия ещё может подавить
обработчик. Просроченные записи удаляются перед публикацией; `cancelled`
считает записи, закрытие которых обнаружено во время публикации. Автоматического
повтора нет. Повторный `set` равного значения ничего не доставляет. Для
восстановления представления используйте текущий снимок и собственную политику.
Доставка всем наблюдателям при заполненной очереди не гарантируется.

**Передача значений и память**

`create` и `set` имеют перегрузки `const T&` и `T&&`. Первая копирует прямо
в снимок внутри границы обработки исключений; вторая перемещает туда значение
без промежуточного `T`. Путь `T&&` поддерживает типы только с перемещением,
включая `vector<unique_ptr<int>>`. При взятии адреса функции выберите перегрузку.

Для восстанавливаемых ошибок памяти `std::string` передавайте существующую
именованную переменную (lvalue). В Debug STL MSVC перемещение с `noexcept` может выделять память для
итераторов и завершить процесс при ошибке; путь копирования позволяет вернуть
`NO_MEMORY`. Аналогичное ограничение относится к любому типу, завершающему
процесс внутри собственной операции.

Кандидат сравнивается до перемещения. Если снимок создан, но инвалидация дерева
отказала, свойство сохраняется, а переданный аргумент для перемещения (rvalue) уже может быть перемещён.

**Повторный вход и время жизни**

Обработчики запускаются Scheduler между кадрами. Если A обрабатывает ревизию 1
и создаёт ревизию 2, при достаточной очереди порядок для A и B будет
`A1, B1, A2, B2`. `set` не вызывает наблюдателей рекурсивно. Бесконечные
обновления ограничиваются бюджетом DATA и продолжаются в следующей диспетчеризации.

Отключение подписки, закрытие области узла или удаление поддерева предотвращает
следующий запуск. Текущий обработчик сохраняет захваты и заимствованный виджет
до возврата. Уничтожение свойства подавляет ожидающие обработчики через слабое
состояние источника; уже выполняемый обработчик может закончить работу со снимком.
Уничтожайте свойство перед деревом. Из обработчика закрывайте дерево через
`close()`; уничтожать само дерево в активном обработчике запрещено.

Записи наблюдателей очищаются при изменяющем `set` и `observe`.
Выполняемый обработчик занимает слот до освобождения захватов. Предел записей
даёт `NODE_LIMIT`; закрытие источника во время регистрации — `CLOSED`.
Ёмкость Scheduler имеет собственные ошибки.

Конструирование, копирование, перемещение и сравнение значения, а также
конструирование и перемещение обработчика должны обходиться без повторного входа
в UI. Деструкторы не должны бросать исключения и обращаться к уничтожаемому
объекту. Старое значение удерживается до завершения всех попыток публикации;
его деструктор затем может обратиться к живому источнику. Возвращённая квитанция
по-прежнему относится к исходной операции, даже если такой вход создал новую
ревизию. Освобождением захватов управляет Scheduler.

См. [контракт дерева](widget-tree.md) и [Scheduler](scheduler.md).

</details>
