# Инструменты сборки и документации {#developer-tools-build-ru}

[Английская версия](../developer-tools-build.md)

Здесь описаны проверка имён, выбор проверок CI и обработка HTML. Команды
PowerShell выполняются из корня репозитория. Нужен Python 3.10 или новее;
эти Python-скрипты используют стандартную библиотеку. Пути сборки в примерах
можно заменить своими.

## Кэш скачанных APT-пакетов {#tool-apt-cache-ru}

`tools/ci/apt_cache.py DIRECTORY` проверяет одноразовый кэш `.deb` задания naming
на Ubuntu. Нужны `apt-cache` и свежие метаданные подписанных APT-репозиториев.
Архивы без метаданных, с другим пакетом, версией, архитектурой или SHA256 удаляются.
Команда не устанавливает пакеты и не меняет окружение. Сохраняются только обычные
проверенные файлы; символические ссылки удаляются без перехода к цели. Прочие файлы
сохраняются. Запускайте перед установкой, без одновременной записи в каталог кэша.

```powershell
python tools/ci/apt_cache.py --help
python -m unittest discover -s tools/ci -p test_apt_cache.py -v
```

`DIRECTORY` обязателен, должен существовать и не имеет значения по умолчанию.
Вывод содержит число проверенных и удалённых архивов. Коды завершения: 0 — проверка
завершена, 1 — ошибка ввода-вывода или инструмента, 2 — неверные аргументы.
`--help` не требует каталога или APT. Кэш не считается доверенным до проверки
по APT-метаданным и не заменяет проверку подписанных репозиториев. Помощник
предназначен для одноразовых каталогов загрузки CI.

## Exports архитектурных снимков

`tools/docs/architecture.py` создаёт SVG на EN/RU и автономный HTML viewer
из `maps.json` и включённого в репозиторий шаблона. Python 3.10+ со стандартной
библиотекой нужен только автору. Для просмотра exports не нужны сервер или
установка пакетов. См. [процесс сопровождения снимков](architecture.md).

```powershell
python tools/docs/architecture.py --help
python tools/docs/architecture.py
python tools/docs/architecture.py --check
python tools/docs/architecture.py --source docs/architecture/snapshots/m1-968651a/maps.json --check
python tools/docs/architecture_test.py
```

`--source` выбирает существующий UTF-8 JSON manifest; по умолчанию это
`docs/architecture/snapshots/m1-968651a/maps.json` относительно репозитория,
независимо от рабочего каталога. Генерация заменяет только готовые
`<map>-<language>.svg` и `index.html` рядом с manifest. Перед изменением данных
создайте новый каталог, сохранив закреплённые снимки. `--check` проверяет paths,
границы номеров строк и точные bytes exports без записи. Единиц измерения и
параметров нагрузки нет. Код завершения: 0 — успех, 1 — некорректные данные,
ошибка I/O или устаревшие exports, 2 — неверный CLI syntax. `--help`/`-h` не
требует manifest, не запускает работу и ничего не записывает. Exporter не
использует Git или сеть и не проверяет, что строка исходника выражает заявленный
контракт; это дают проверка закреплённой ревизии и fact review.

`architecture_test.py` — внутренний regression driver для команды выше.
Он проверяет справку без побочных действий в пустом каталоге, воспроизводимость,
source references в закреплённой Git-ревизии, геометрию SVG и автономные ресурсы.
Код завершения соответствует unittest; CLI-проверки используют временные
каталоги. Browser-проверка и независимое fact review выполняются отдельно.

## Составить локальный contract check plan

`tools/ci/check_plan.py` читает явный список изменений и сохранённый CTest
inventory, затем печатает JSON plan. Git, tests, build, compiler, сеть и внешние
приложения он не запускает. Python 3.10+ со стандартной библиотекой нужен только
автору. См. [матрицу task/integration/milestone](development.md).
[Реестр контрактов](../../tools/ci/check_contracts.json) сопоставляет точные paths
с CTest registrations, source witnesses и cross-contract focus checks.
Реестр ограничен и не претендует на классификацию всех файлов проекта.
Source witness — существующий исходник теста, обосновывающий сопоставление
контракта и проверки. Hash его bytes фиксирует версию для аудита, но сам по себе
не доказывает прохождение проверки.

```powershell
ctest --test-dir build/windows-msvc-debug --show-only=json-v1 | Set-Content -Encoding utf8 build/check-inventory.json
@'
[{"path":"tools/ci/checks.py","status":"M"}]
'@ | Set-Content -Encoding utf8 build/changes.json
python tools/ci/check_plan.py --changes build/changes.json --inventory build/check-inventory.json
python tools/ci/check_plan.py --changes build/changes.json --inventory build/check-inventory.json --level integration
python tools/ci/check_plan.py --help
python tools/ci/test_check_plan.py
```

Inventory берите из выбранной настроенной сборки. В POSIX сохраните stdout
`ctest --show-only=json-v1` обычным перенаправлением. Принимается UTF-8, в том
числе с BOM. Вход изменений — массив `{path,status}`. Paths нормализованы,
относительны корню репозитория и используют POSIX-разделители даже в Windows.
Только `M` (modified) допускает narrow task preflight. Новые/удалённые/copied
файлы задавайте как `A`/`D`/`C`; для rename укажите оба пути со статусом `R`.
Эти и неизвестные статусы дают full. Planner доверяет полноте списка и заявлению
`M`; Git status он не обнаруживает и не проверяет.

| Аргумент | Значение | По умолчанию |
| --- | --- | --- |
| `--changes FILE` | Существующие UTF-8 JSON change records | Обязателен |
| `--inventory FILE` | Существующий CTest JSON inventory | Без него: full с неизвестным configured test set |
| `--impact FILE` | Необязательный [Ninja receipt](developer-tools-measure.md#tool-change-impact-ru) | Без dependency evidence |
| `--source-root DIR` | Checkout для проверки точных changed paths и source witnesses | Репозиторий, содержащий script |
| `--level LEVEL` | `task`, `integration` или `milestone` | `task` |
| `--output FILE` | Новый JSON file; parent существует, старый файл отклоняется | Только stdout |

Единиц времени и execution parameters нет. Код 0 — plan сформирован, включая
full fallback; 1 — неверные данные/I/O; 2 — неверные аргументы. `--help`/`-h` не
требует рабочих входов и ничего не пишет. Кроме явно запрошенного нового output
file, входы и окружение не изменяются. Source archive не требует `.git` или
приватных workspace data.

`focus_tests` задаёт порядок, с точными source witnesses и byte hashes.
`selected_tests` содержит настоящие registrations переданного inventory.
Без inventory результат null, а не выдуманный пустой набор. Full plan не даёт
CTest filter; documentation-only plan не даёт CTest command. Focused task plan
содержит exact-name regex. Build directory, compiler, configuration и запуск
выбирает вызывающая сторона; plan не является PASS receipt. Policy/inventory
hashes относятся к canonical JSON content, witness hashes — к bytes исходников.

Пилот разрешает narrow task preflight только для явно перечисленных modified
Python tools при наличии registrations и witnesses. Для C++ core, templates,
styles, consumers и runtime сохраняется полный настроенный suite. Include graph
показывает rebuild dependencies, а не semantic test coverage. Missing/stale/
unbuilt/unobserved coverage записывается и не разрешает skip; даже полное
dependency coverage в этом пилоте не обосновывает runtime exclusions.
Unknown/new/deleted/renamed paths, missing witnesses и CTest names также дают full.

JSON сохраняет обязанности integration/milestone и hosted mode из неизменённого
`checks.py`. Узкий Python task preflight по-прежнему требует full hosted checks
для infrastructure changes. Существующий docs-only hosted режим сохранён.
Integration/milestone plans выбирают все настроенные tests; применимость более
широких platform/native/docs checks определяется матрицей. Сокращение hosted
runtime matrix и измеренная экономия времени не заявляются.

[Записанный pilot](../measurements/check-plan-pilot-968651a.json) использует 136
реально зарегистрированных CTest-проверок в Ninja Release: tests включены,
tools/examples/docs выключены. Для 14 гипотетических списков изменений получены
42 CLI-плана трёх уровней: 39 full plans сохраняют все 136 проверок, два Python
task preflight выбирают две и одну зарегистрированные проверки, один docs-only
task plan не даёт CTest command. Неожиданных пропусков относительно этих заданных
ожиданий нет. Runtime-база — `968651a90b6a1542fd3ab2cec159b457e548681f`;
hashes planner/matrix additions рабочей версии записаны отдельно. Dependency
вход покрывает 46 из 51 compile outputs и не обосновывает full-project exclusion.
Pilot выполняет plans, не runtime tests или hosted jobs; улучшение времени не
измерялось.

`test_check_plan.py` — внутренний unittest driver команды выше. Временные
fixtures/source bundles проверяют invalid/new/unknown/stale inputs, cross-contract
closure, сохранение full suite, воспроизводимость, native help, BOM и запрет
перезаписи. Driver работает без `.git`, compiler и runtime tests; код завершения
соответствует unittest. `portals.ci-selection` регистрирует существующие
selector/gate fixtures; `portals.check-plan` — этот driver.

## Выбор команды

| Задача | Команда или цель | Что изменяет |
|---|---|---|
| Проверить имена в C++ | `python tools/check_naming.py <build>` | Запускает clang-tidy без запроса исправлений |
| Определить проверки PR | `python tools/ci/checks.py select --base <base> --head <head>` | Читает Git; при заданных переменных дописывает файлы вывода CI |
| Проверить результаты CI | `python tools/ci/checks.py gate` | Читает `CI_NEEDS` |
| Собрать полный HTML справки | `cmake --build <build> --target portals_docs` | Создаёт и обрабатывает дерево HTML |
| Проверить ссылки HTML | `python tools/docs/check_links.py <html>` | Читает HTML и проверяет локальные пути |
| Проверить выбор режима CI | `python -m unittest discover -s tools/ci -p test_checks.py -v` | Создаёт временные репозитории Git |
| Проверить обработчик HTML | `python -m unittest discover -s tools/docs -p "test_*.py" -v` | Создаёт временные тестовые файлы |

Порядок работы над библиотекой описан в [руководстве разработчика](development.md),
настройка сборки справки и тесты C++ — в [разделе тестирования](../testing.md)
на английском.

## Сборка и запуск тестов без терминала

В Windows используйте x64 Developer PowerShell, в POSIX — окружение совместимого
компилятора C99/C++23. Нужны CMake 3.24+ и Ninja. Команды создают отдельный
каталог сборки Release:

```powershell
cmake -S . -B build/check -G Ninja -DCMAKE_BUILD_TYPE=Release -DPORTALS_BUILD_TESTS=ON -DPORTALS_BUILD_TOOLS=ON -DPORTALS_BUILD_EXAMPLES=ON -DPORTALS_BUILD_DOCS=OFF
cmake --build build/check
ctest --test-dir build/check --output-on-failure -E '^portals\.line-edit\.native$'
```

Исключённый тест требует ввода в настоящем терминале. Native-проверки запускаются
отдельно; см. [терминальные инструменты](developer-tools-measure.md#tool-native-ru).
CTest показывает результаты отдельных проверок и возвращает ненулевой код при ошибке.

## Проверка имён

[Исходник: check_naming.py](../../tools/check_naming.py).

Нужны подготовленный `compile_commands.json`, clang-tidy, совместимый с
компилятором и стандартной библиотекой этой сборки, и файл `.clang-tidy` из
репозитория. Выполняйте команду в окружении компилятора, которым настроена
сборка. Пример при доступном Ninja:

```powershell
cmake -S . -B build/naming -G Ninja -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
python tools/check_naming.py build/naming --clang-tidy clang-tidy
```

| Аргумент | Обязательность / значение по умолчанию | Назначение |
|---|---|---|
| `build` | Обязательный позиционный путь | Каталог с `compile_commands.json`; вычисляется относительно текущего каталога |
| `--clang-tidy EXE` | `clang-tidy` | Имя исполняемого файла в `PATH` или путь к нему |
| `-h`, `--help` | Необязательный | Показать справку и завершиться |

Скрипт выбирает уникальные единицы трансляции из `src`, `tests`, `tools`,
`examples`, `experiments` и `fuzz` текущей копии репозитория. Файлы вне этой
копии пропускаются. Также исключены намеренно некорректные файлы
`tests/fixtures/<fixture>/invalid.cpp`, где `<fixture>` — `static_scene`,
`static_styles` или `ct_pss`. Проверяются только единицы трансляции, включённые
в базу команд компиляции.

Для каждого файла запускается clang-tidy с `-p <build>`, `--quiet` и путём к
`.clang-tidy` репозитория в `--config-file`. Рабочий каталог процесса — корень
репозитория. Опция `--fix` не передаётся. Диагностика выводится в консоль;
последняя строка содержит число проверенных файлов и неудачных запусков.
Файл отчёта не создаётся. Специальных переменных окружения нет; поиск
исполняемых файлов и компилятора зависит от окружения процесса.

Коды завершения: `0` — все запуски успешны; `1` — хотя бы один запуск
clang-tidy завершился с ошибкой; `2` — неверные аргументы или отсутствие
подходящих файлов в базе. Ошибки чтения, некорректный JSON и невозможность
запустить процесс завершают скрипт неуспешно с диагностикой Python.
После ненулевого результата clang-tidy скрипт продолжает проверку остальных
файлов.

## Выбор проверок CI и итоговая проверка результатов

[Исходник: checks.py](../../tools/ci/checks.py). Команды использует
[workflow проверки PR](../../.github/workflows/ci.yml). Они не запускают
сборки, не загружают Git-ссылки, не обращаются к GitHub и не меняют файлы
репозитория.

### Выбрать режим

```powershell
python tools/ci/checks.py select --base origin/main --head HEAD
```

| Аргумент | Обязательность / значение по умолчанию | Назначение |
|---|---|---|
| `select` | Обязательная подкоманда | Выбрать `docs` или `full` |
| `--base REF` | Обязательный; значения по умолчанию нет | Базовая ревизия Git, уже доступная локально |
| `--head REF` | Обязательный; значения по умолчанию нет | Проверяемая ревизия Git, уже доступная локально |
| `-h`, `--help` | Есть у основного парсера и каждой подкоманды | Показать соответствующую справку |

Нужен Git в `PATH`; текущий каталог должен находиться внутри нужной копии
репозитория. Точное сравнение:
`git diff --name-only --no-renames -z <base>...<head> --`. Оно сравнивает
общего предка с проверяемой ревизией. Локально должны быть обе ревизии и
история, необходимая для поиска общего предка. CI загружает полную историю
и передаёт SHA базовой и проверяемой ревизий PR. Команда читает полный diff
Git, без постраничного списка изменённых файлов из GitHub. Разделение путей
нулевыми байтами сохраняет пробелы, нелатинские символы и переводы строк.
Отключённое распознавание переименований включает старый и новый путь;
удалённые файлы тоже участвуют в выборе.

Режим `docs` выбирается только для непустого списка, в котором каждый путь —
один из следующих:

- `README.md` или `ReleaseNotes.md`;
- файл `.md` на любой глубине внутри `docs/`;
- файл `.svg`, `.png`, `.jpg`, `.jpeg`, `.gif` или `.webp` внутри `docs/images/`;
- `docs/diagrams.css`, `docs/DoxygenLayout.xml` или `docs/mermaid.json`.

Сопоставление путей и расширений учитывает регистр. Любой другой путь,
смешанный набор или пустой diff выбирает `full`. Пример C++ внутри `docs/`
и скрипт обработки документации требуют `full`.

| Переменная окружения | По умолчанию | Действие |
|---|---|---|
| `GITHUB_OUTPUT` | Не задана или пуста | При непустом значении дописать `mode=docs` или `mode=full` и перевод строки в этот UTF-8 файл |
| `GITHUB_STEP_SUMMARY` | Не задана или пуста | При непустом значении дописать в этот UTF-8 файл Markdown-заголовок, причину выбора и число изменённых путей |

В стандартный вывод записывается один JSON-объект с полями `mode`, `reason`
и `paths`. Указанные файлы открываются на добавление: повторные вызовы
добавляют повторные записи. Без этих переменных файлы вывода не создаются.
Успешный выбор завершается с кодом `0`, в том числе при выборе `full`.
Ошибки аргументов дают `2`; ошибки Git и доступа к файлам завершают скрипт
неуспешно с диагностикой Python.

### Проверить результаты

У `gate` нет собственных опций. Нужна переменная `CI_NEEDS` с JSON-объектом
в формате `needs` GitHub Actions. Пример успешного результата для режима
документации:

```powershell
$env:CI_NEEDS = '{"changes":{"result":"success","outputs":{"mode":"docs"}},"docs":{"result":"success"},"naming":{"result":"skipped"},"smoke":{"result":"skipped"}}'
try {
  python tools/ci/checks.py gate
} finally {
  Remove-Item Env:CI_NEEDS
}
```

Выполняйте пример в оболочке без ранее заданного `CI_NEEDS`. В workflow
переменная задаётся для шага проверки из `toJSON(needs)`.

| Поле | Допустимое значение |
|---|---|
| `changes.result` | `success` |
| `changes.outputs.mode` | `docs` или `full` |
| `docs.result` | `success` в обоих режимах |
| `naming.result`, `smoke.result` в режиме `full` | Оба `success` |
| `naming.result`, `smoke.result` в режиме `docs` | Каждое — `success` или `skipped` |

Отсутствующий результат, ошибка, отмена или пропуск обязательной проверки
не дают пройти итоговую проверку. При успехе команда печатает
`All selected checks succeeded` и возвращает `0`. Отсутствие `CI_NEEDS`,
некорректный JSON, неверная структура результатов или отклонённые результаты
завершают команду неуспешно с диагностикой Python. Ошибки argparse дают `2`.
Команда не пишет отчёты и не использует `GITHUB_OUTPUT` и
`GITHUB_STEP_SUMMARY`.

### Регрессионные тесты выбора проверок

У [test_checks.py](../../tools/ci/test_checks.py) нет собственных опций проекта.
Используйте unittest discovery из таблицы команд; стандартные опции unittest
управляют подробностью вывода и выбором тестов. Нужны Python и Git в `PATH`.
Тесты вызывают `select` и `gate` на тестовых данных, создают временные
репозитории и задают имя и почту только в локальной конфигурации этих
репозиториев. Конфигурация рабочей копии не меняется; push не выполняется.
Временные каталоги удаляются после завершения. Результаты печатает unittest:
`0` означает успех, `1` — ошибку или падение теста; неверный вызов CLI тоже
завершается неуспешно.

## Проверка ссылок HTML

[Исходник: check_links.py](../../tools/docs/check_links.py). Запускайте после
завершения цели документации:

```powershell
python tools/docs/check_links.py build/documentation/docs/html
```

Единственный аргумент — позиционный путь к существующему каталогу HTML.
Значений по умолчанию и специальных переменных окружения нет.
`--help` и `-h` выводят справку без сканирования файлов. Скрипт рекурсивно читает UTF-8 файлы `*.html`,
собирая атрибуты `href`, `src`, `id` и старый атрибут якоря `name`.
Для локальных ссылок проверяются существование цели и, если цель —
разобранный HTML-файл, наличие фрагмента после декодирования URL.
Внешние URL пропускаются, сетевые запросы не выполняются. Ссылки CSS,
создаваемые JavaScript ссылки и содержимое файлов других форматов не
проверяются. Относительный путь вычисляется от страницы со ссылкой и может
выходить за переданный каталог.

В стандартный вывод записывается JSON с полями `html_files`,
`local_links_checked` и `broken`. Каждая запись `broken` содержит путь
исходной страницы относительно корня HTML, исходную ссылку и причину:
`missing file` или `missing anchor`. HTML не изменяется. Код `0` означает,
что битых локальных ссылок нет; `1` — битые ссылки, неподходящий каталог
или отсутствие HTML-файлов; `2` — неверный синтаксис аргументов. Ошибки чтения
также завершают скрипт неуспешно с диагностикой Python.

## Завершение сборки HTML

Обычная сборка документации выполняет обработку автоматически:

```powershell
cmake -S . -B build/documentation -DPORTALS_BUILD_DOCS=ON
cmake --build build/documentation --target portals_docs
python tools/docs/check_links.py build/documentation/docs/html
```

Для конфигурации нужны CMake 3.24+, набор инструментов C/C++ проекта,
Doxygen 1.18+ и Mermaid CLI (`mmdc` или `mmdc.cmd` в `PATH`); CMake находит
Python 3.10+. `PORTALS_BUILD_DOCS` по умолчанию выключен (`OFF`). Успешная
цель создаёт `<build>/docs/html` и `<build>/docs/portals.tag`, без публикации.

### Обработка HTML и подсветка CMake

[Исходник: finalize_html.py](../../tools/docs/finalize_html.py). Для диагностики
сгенерированной копии полный вызов имеет вид:

```powershell
python tools/docs/finalize_html.py build/documentation/docs/html build/documentation/docs/portals.tag --language-sites ru=build/documentation/docs/portals-ru.tag
```

| Аргумент | Обязательность / значение по умолчанию | Назначение |
|---|---|---|
| `html` | Обязательный позиционный путь | Существующий каталог HTML Doxygen, который будет изменён |
| `tag_file` | Обязательный позиционный путь | XML-файл тегов Doxygen от той же сборки документации |
| `--language-sites CODE=TAG ...` | Необязательный; без него обрабатывается один сайт | Обработать настроенные языковые версии: основной файл тегов и по одному для каждого дополнительного языка |
| `-h`, `--help` | Необязательный | Показать справку и завершиться |

Пути вычисляются от текущего каталога. Специальных переменных окружения нет.
Сохраняйте скрипт внутри рабочей копии: он ищет исходники относительно
собственного файла. Обработка изменяет сгенерированное дерево на месте;
для экспериментов используйте отдельный каталог сборки.

Скрипт обрабатывает главную страницу и страницы руководств из файла тегов:

- добавляет ссылки у имён классов, структур и concepts во встроенных фрагментах кода,
  если файл тегов разрешает их однозначно; сохраняет существующие ссылки
  и блоки кода;
- разрешает поддерживаемые относительные Markdown-ссылки и копирует
  исходники по ссылкам в `html/source/<путь-в-репозитории>` для чтения без
  сети; копируемые файлы должны находиться внутри рабочей копии;
- включает локальный поиск для распознанного варианта Doxygen без элемента конфигурации; при наличии элемента сохраняет штатную инициализацию;
- задаёт корневые `lang` и `xml:lang` по языку сайта; при диагностике одного сайта сохраняется определение по именам страниц;
- раскрашивает распознанные неокрашенные фрагменты CMake классами CSS Doxygen;
- добавляет заголовки руководств до третьего уровня в дерево навигации и
  пересоздаёт индексные части навигации размером до 250 записей, сохраняя
  записи API.

Подсветка CMake распознаёт выбранные сигнатуры команд и применяет простые
построчные правила для команд, `${переменных}`, строк в кавычках и
комментариев `#`. Полного разбора CMake нет: bracket-строки и
bracket-комментарии не распознаются как многострочные конструкции.
Неоднозначные короткие имена типов остаются без ссылок. Обработчик не
проверяет внешние URL и все результирующие ссылки; после него запускайте
проверку ссылок.

Скрипт перезаписывает HTML руководств, `navtreedata.js` и сгенерированные
`navtreeindex*.js`, распознанный общий `search/search.js`, копирует исходники по ссылкам. В стандартный вывод
пишется JSON с `guide_pages` и `unambiguous_types`. Успех даёт код `0`,
ошибки CLI — `2`. Некорректный XML, отсутствующие данные навигации и ошибки
чтения или записи завершают процесс неуспешно с диагностикой Python.
Отката частично обработанного дерева нет; после ошибки пересоздайте справку.

### Подготовка языковых сборок

[Исходник: prepare_languages.py](../../tools/docs/prepare_languages.py) вызывается
при конфигурировании CMake:

```powershell
python tools/docs/prepare_languages.py docs/languages.json docs/DoxygenLayout.xml --output build/documentation/languages
```

Позиционный аргумент `docs/languages.json` задаёт сведения о
языках, `docs/DoxygenLayout.xml` — навигацию каждого языка, `--output` —
каталог создаваемой конфигурации. Все три пути обязательны и вычисляются от
текущего каталога. `--help` доступен без входных данных и ничего не изменяет.
Утилита записывает `languages.cmake` и `layout-<код>.xml`, заменяя прежние файлы.
Она не запускает Doxygen и не обращается к сети. Коды завершения: `0` — успех,
`1` — некорректные данные или ошибка ввода-вывода, `2` — ошибка синтаксиса CLI.

Doxygen также вызывает внутренний режим фильтра с аргументами `manifest`,
`--filter-language CODE`, `--source-root ROOT` и `--filter-input FILE`. Фильтр
выводит исходный текст в stdout, преобразуя ссылки на другой язык в HTML-ссылки
для последующей обработки. Исходные Markdown-файлы и блоки кода сохраняются.
Этот режим не записывает файлы конфигурации. Специальных переменных окружения
нет в обоих режимах.

Внутренний [language_site.py](../../tools/docs/language_site.py) вызывается
обработчиком HTML после сборки всех языков. Он читает манифест, файлы тегов и
HTML, исправляет языковые ссылки, добавляет переключатель страниц и создаёт
перенаправления прежних адресов переводов. Ошибка входных данных или ввода-вывода
прерывает сборку; после неё пересоздайте сайт. Отдельного CLI нет.

### Регрессионные тесты обработчика

[test_finalize_html.py](../../tools/docs/test_finalize_html.py) использует
unittest без собственных опций и переменных окружения проекта. Команда
discovery из таблицы проверяет переносимые ссылки на исходники, ссылки у
типов, неоднозначные имена, языковые метаданные, защищённую инициализацию поиска, сохранение текста CMake и повторяемость
навигации на временных данных. Doxygen и Mermaid не нужны; настоящее
дерево документации не обрабатывается. Нужен доступный для записи системный
временный каталог; тестовые каталоги удаляются после проверки. Результаты
печатает unittest; `0` — успех, `1` — ошибка или падение теста.

## Внутренние помощники CMake

Эти файлы реализуют настроенные цели сборки. Вызывайте соответствующую цель;
их внутренние переменные не являются самостоятельными опциями CLI.
Специального интерфейса через переменные окружения у них нет.

| Помощник | Кто вызывает и что передаёт | Результат и ошибки |
|---|---|---|
| [FinalizeDocumentation.cmake](../../cmake/FinalizeDocumentation.cmake) | Команда после сборки `portals_docs` задаёт `HTML_DIR` равным `<build>/docs/html`; значения по умолчанию нет | Подключает обработку схем, копирует исходники и лицензии по ссылкам, исправляет известные дефекты индексов и ссылок Doxygen на месте. Отсутствующий/неподходящий `HTML_DIR` и неизвестная структура индекса дают фатальную ошибку CMake. Исходники ищутся относительно рабочей копии самого помощника. |
| [FinalizeDiagrams.cmake](../../cmake/FinalizeDiagrams.cmake) | Подключается из `FinalizeDocumentation.cmake` и получает его `HTML_DIR` | Просматривает HTML верхнего уровня и заменяет SVG-объекты Mermaid на изображения с адаптивным размером. У SVG должны быть распознаваемый `viewBox` и доступный заголовок `title`; отсутствие размеров или заголовка прерывает сборку. Меняются затронутые HTML-файлы; сами SVG сохраняются. |
| [TestProcesses.cmake](../../cmake/TestProcesses.cmake) | Подключается при конфигурации, только если истинны `WIN32` и `PORTALS_BUILD_TESTS`. CMake вызывает `portals_configure_test_processes(directory)` с текущим каталогом исходников; у `directory` нет значения по умолчанию | Рекурсивно обходит уже определённые исполняемые цели каталога и его подкаталогов, добавляя исходник настройки тестового процесса. Меняет состав исходников целей; они компилируются при обычной сборке. |

Настройка Windows реализована в [тестовом исходнике](../../tests/support/no_dialogs.cpp).
Она отключает интерактивные системные окна и диалоги CRT, направляет
фатальные сообщения CRT в стандартный поток ошибок и завершает затронутый
тестовый процесс. В основную библиотеку этот исходник не входит. После
сборки Windows-конфигурации с тестами проверьте поведение через CTest:

```powershell
ctest --test-dir build/windows-msvc-debug -C Debug -R '^portals\.test-processes$' --output-on-failure
```

Тайм-аут этого теста в CTest — 40 секунд. Вспомогательная программа и
[драйвер CMake](../../tests/no_dialogs.cmake) принадлежат тестам;
поддерживаемая точка запуска — CTest. Успешный помощник CMake возвращает
успех вызывающей стороне; фатальная ошибка прерывает конфигурацию или сборку.
