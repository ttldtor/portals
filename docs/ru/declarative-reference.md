# Справка по сценам и рецептам {#declarative-reference-ru}

[Расширенная английская справка](../declarative-reference.md) · [Руководство](declarative-ui.md)

Здесь собраны контракты подготовки, времени жизни, событий и ошибок.

## Именованные ссылки и стили по Ref

`Scene::get(id)` возвращает `DynamicRef`; `get<T>(id)` и преобразование в `Ref<T>`
проверяют публичное наследование Widget через RTTI. Отложенное преобразование ждёт
исходный динамический слот. После публикации оно проверяет его исходный NodeId,
даже при переименовании или повторном использовании ID; новый поиск имени не выполняется.
Запрос владеет ID и местом вызова, сохраняя слабый anchor сцены. Слоты только
наблюдают; виджетами и регистрациями владеет сцена.

Очередь запросов отдельно ограничена `SceneOptions::maxConfigurations`. Они разрешаются
между полным mount рецепта и отложенной конфигурацией. Первичная startup-ошибка
фиксируется до observer callback и уведомляется один раз. Отложенные преобразования
того же имени сохраняют её без повторного уведомления. Ошибки immediate lookup
восстанавливаемы, кроме действующего checked setup/configuration scope. Создание
аргументов и захватов до admission может бросать исключения; внутренние ошибки после
admission отображаются в BIND/NO_MEMORY или CALLBACK_FAILED.

`ui::style(ref, bytes)` и `styleFile(ref, path)` используют полный строгий PSS v0.
Необязательный `StyleSheet::scope` фильтрует точный NodeId перед прежними селекторами,
не меняя их специфичность и порядок tier. Metadata-preview `resolveStyle` не имеет
живого NodeId и игнорирует этот фильтр; StyleEngine проверяет его для реальных bindings.
Координаты селекторов и деклараций исходного документа сохраняются. Metadata для
ранее не стилизованного контейнера/custom widget публикуется атомарно со слоем;
отклонение не публикует ни один из них. Прежние глобальные sheets регистрируют
тот же набор целей, что и раньше.

Область исключает потомков и отвергает Ref другой сцены, stale, closed и wrong-thread
цели до публикации. Равные sheets сохраняют прежние no-op и invalidation гарантии.
Смена theme-слота сохраняет независимые scoped-слои APPLICATION и USER. Чтение файла
отложено до admission и использует существующие пределы, ошибки файлов и parser
с источником; watcher и loader не добавлены. См. [полный пример](declarative-ui.md)
и [installed consumer](../../tests/package_consumer/named_scoped.cpp).

## Запуск и результат

`Scene::runApp()`, `ui::runApp(scene)` и `scene | ui::runApp()` синхронно
запускают сцену, пытаются восстановить терминал и очистить сцену, затем
сообщают результат. Успех даёт код 0, типизированная ошибка — 1.
Допускаются токен остановки и заимствованный ApplicationTerminal с собственным транспортом или воспроизведением ввода.
Заключительный runApp заимствует именованную или временную сцену на вызов.
`scene.run()` и `scene | ui::run()` возвращают владеющий
`expected<ApplicationStats, ManagedError>` для собственной обработки.
Типизированный run не вызывает заключительный обработчик отчёта и не печатает в stderr.

Создание описания, захватов, аргументов и [стадий UI](glossary.md#glossary-ui-stage-ru) до входа в runApp может бросать
обычные исключения C++. Перегрузка `ui::runApp(factory, setup)` помещает создание
описания в проверяемую границу; вычисление её аргументов остаётся снаружи.
При необходимости охватите предварительное создание обычным try/catch.

## Завершение и текущая сцена

`ui::quit()` запрашивает завершение текущей сцены. Его можно передать прямо
в `onKey` или `onClick`. `SceneRef::quit()` и `ui::quit(scene.ref())` используют
явную наблюдаемую ссылку. Без текущей живой сцены команда void ничего не делает.
Во время живой сцены запрос доступен только в UI-потоке и идемпотентен.

Контекст текущей сцены определяет, к какой сцене обращается `ui::quit()` без аргументов. Он устанавливается на время выполнения рецепта, методов setup/configure/run и обработчиков
управляемой сцены: клавиш, кнопок, текста, валидации, CheckBox, собственных событий
и подготовки. Доставка свойства использует слабого владельца фасада.
Независимое вложенное выполнение временно приостанавливает внешний контекст;
возврат и исключение восстанавливают его. Очистка, заключительный отчёт и
освобождение захватов не открывают внешнюю сцену. Контекст переживает перемещение
фасада и отзывается до очистки. Произвольный низкоуровневый обработчик вне этих границ
должен использовать явный SceneRef.

Quit до подготовки ждёт полного успешного монтажа и конфигурации, включая
привязки. Текущий обработчик заканчивается до очистки. Вход во время уведомления,
закрытия или отчёта даёт WOULD_BLOCK; закрытая/перемещённая сцена — CLOSED,
другой поток — WRONG_THREAD. Предварительный quit сохраняет путь открытия
и восстановления системного терминала. Наблюдаемые ссылки сцену не удерживают.
При взятии адреса перегруженной ui::quit явно выберите тип указателя функции.

## Ошибки и заключительный отчёт

runApp доставляет один SceneReport после попытки закрытия терминала и очистки.
`failure` сохраняет основную ошибку, независимые причины runner/restoration
и очистки. Исключения Widget::unmount сейчас передаются только обработчику ошибок дерева;
результат очистки управляемой сцены их не возвращает. Подключите этот обработчик
при использовании собственных методов жизненного цикла.

По умолчанию reportToStderr печатает категории, места вызова и системные коды
без выделения памяти C++. При ошибке восстановления это попытка доступного вывода.
Повторный заключительный вызов отчёт не дублирует. Другой поток, перемещённый
фасад и вложенный вызов возвращают 1 без отчёта; причину читайте через checked/run.

onError наблюдает ошибки в момент операции и не отменяет их.
reportOnError выбирает обработчик заключительного отчёта независимо от onError:

```cpp
scene.onError([](const ManagedDiagnostic &diagnostic) {
  // React to the operation failure without terminal output
  // during the live run.
}).reportOnError([](const ui::SceneReport &report) {
  // Forward the final structured report to an application
  // logger after cleanup.
  ui::reportToStderr(report);
});
```

Сцена хранит копируемый обработчик с сигнатурой `void(const SceneReport&)`;
заимствованные сервисы должны пережить runApp. reportOnError() или ({}) выбирает
стандартный обработчик отчёта. Во время доставки отчёта доступно только чтение:
повторный вход в жизненный цикл даёт WOULD_BLOCK, регистрация и изменение
через цепочки вызовов не выполняются. Замена активного обработчика отклоняется.
Если он бросает исключение, стандартное форматирование вызывается один раз
с исходным отчётом.
Успех с восстанавливаемыми ошибками сохраняет код 0 и сообщает ограниченные
счётчики сохранённых/потерянных записей. Детали доступны через diagnostics().
Успех без сообщений остаётся тихим.

## Создание, подготовка и конфигурация

Функция формы может вернуть ленивую `ui::Scene`, как
`gallery::form(ui::opts(options))` в [галерее](../../examples/gallery/fluent_form.hpp).
`ui::opts` принимает только lvalue и предоставляет чтение без копии; объект
настроек должен пережить синхронный запуск. `ui::applicationOptions(provider)`
вызывает поставщика настроек после успешного разбора CLI и до монтажа.
Заключительный `ui::runApp(argc, argv, parser)` захватывает аргументы и окружение,
затем вызывает парсер. Справка, версия или ошибка разбора завершают запуск
до фабрики сцены и захвата терминала. [Командная строка](cli.md) описывает
`ui::lyra::cli`, владеющие сообщения, коды завершения и снимки процесса.

Создание описаний, этапов, захватов и аргументов до входа в runner может бросать
исключения вне его границы. Ленивая фабрика, конфигурация и обработчики выполняются
внутри соответствующих проверяемых границ; это не распространяется на более раннее
вычисление аргументов C++.

Scene принимает описание или фабрику с `ManagedScene&`. Фабрика один раз при
подготовке возвращает описание или `expected<Description<T>, ManagedError>`
и может создать состояния/модели. lineEdit(string_view) сразу копирует строку;
TextValue хранит литерал, формат или ресурс с явным TextResolver и разрешается
при монтаже под политикой ширины сцены. ManagedState<string> позволяет общую модель.

SceneOptions содержит ApplicationOptions, ManagedOptions, заимствованные часы
и maxConfigurations, по умолчанию 64. До подготовки сохраняется последняя тема
и observer; configure/key выполняются после полного монтажа по регистрации.
Этапы prepare/configure/onError/reportOnError вызывают те же методы.
Для именованной сцены (lvalue) конфигурационный этап возвращает Scene&;
для временной или явно перемещаемой сцены (rvalue) перемещает неактивный фасад. Для намеренного потребления именованного владельца используйте std::move.
Применение может потребить захваты этапа. Неизменяемые фасады и композиция этапов между собой
не поддерживаются. run(terminal, stop) потребляет сцену; runApp заимствует её.
prepare монтирует без терминального I/O. Повторная prepare — пустая операция.

prepareChecked/checked показывают подготовку и сохранённую ошибку; managed()
наблюдает уже подготовленного владельца; diagnostics() копирует записи ограниченного
сборщика ошибок. Первая ошибка прекращает последующие стадии. Каждый принятый run
закрывает сцену, включая отказ открытия терминала. Частичная prepare/configure
также очищает владельца. Опубликованные `Ref` становятся устаревшими или закрытыми.
Сцена после успешного выполнения или close не монтируется заново; close идемпотентен.

Конфигурация возвращает void или ровно `expected<void, ManagedError>`.
Ошибка короткой записи текста в конфигурации или подготовке останавливает дальнейшие стадии
и открытие терминала. Текущая void-лямбда выполняет оставшиеся инструкции;
для раннего выхода верните ошибку явно. Ранее выполненные эффекты сохраняются.
Пустая или устаревшая `Ref` также останавливает активную подготовку. Ошибка обработчика, выполняемого в контексте другой сцены, не изменяет состояние настройки вызывающей сцены.
Очистка и отчёт изолируют область ошибок. Произвольные низкоуровневые вызовы `reportError`
и проигнорированные `expected` остаются ответственностью вызывающего кода.
Undo/Redo и регистрация click сохраняют собственные проверяемые результаты.

Возврат той же короткой ошибки через expected сохраняет квитанцию коллектора
и предотвращает повторное сообщение. Свежая равная ошибка и явное
reportError(error) с последующим unexpected — самостоятельные события.
ManagedError хранит исходный phase, operation, execution, operationOrigin
и setupStopped; причины восстановления и очистки независимы. checked только
читает состояние. Это не обещание стабильного ABI.

onError получает исходную ошибку и не может отменить её. Не доставленная ошибка до создания
владельца приходит поздно подключённому наблюдателю один раз. Ошибка наблюдателя сохраняется
отдельно. Внутренние передачи темы/обработчиков входят в проверяемую границу;
аргументы вызывающего кода могут бросать раньше. Цепочки вызовов выполняются только на UI.
Перемещение сохраняет владельца и поток; перемещающее присваивание отсутствует.
Перемещение/уничтожение активной сцены, уничтожение внутри кадра или на чужом
потоке завершает процесс. Для обработчиков, сохраняемых после перемещения, захватывайте
SceneRef; адрес фасада должен оставаться неподвижным.

## Обработчики кнопки

<a id="reference-pipe-click-handlers-ru"></a>

ui::onClick(ref, callback) регистрирует обработчик после монтажа. Ref<Button>
должен принадлежать этой сцене; устаревшая ссылка, чужая сцена и неполный монтаж дают
типизированную ошибку. `hbox`/`vbox` — другие имена `row`/`column` с теми же перегрузками.
Несколько обработчиков, добавленных оператором `|`, выполняются по порядку регистрации.
Следующие две стадии заменяют один обработчик в [первом примере руководства](declarative-ui.md);
`add` и `message` — ссылки из этого примера:

```cpp
ui::onClick(add, [message](ui::ClickParams &params) {
  if (params.mods.has(key::SHIFT)) {
    message.text() += "HELLO!";
    params.stop();
  }
})
```

```cpp
ui::onClick(add,
            [message] {
              message.text() += "Hello!";
            })
```

Без Shift первый обработчик пропускает действие, второй дописывает Hello!.
С Shift первый дописывает HELLO! и останавливает цепочку. Терминал может оставить
Shift+mouse для выделения и не передать его приложению.

| ClickParams | Смысл |
| --- | --- |
| target | Наблюдаемый Node<Button>; может стать устаревшим |
| mods | has(key::SHIFT/ALT/CTRL), без левой/правой физической стороны |
| source | KEYBOARD, MOUSE, PROGRAMMATIC |
| event | Собственное исходное RoutedEvent |
| stop()/stopPropagation() | Прекращает оставшиеся обработчики этого вызова |
| propagationStopped() | Читает флаг конкретного контекста |

Публичные метаданные доступны для чтения. Обработчик заимствует ClickParams&
до возврата. Копия сохраняет событие, но её stop не влияет на текущую цепочку.
Для optional используйте emplace: const-метаданные запрещают полное присваивание.
Кнопка уже отвечает HANDLED, поэтому предки не получают активацию.

Обработчик возвращает `void`, `expected<T, TreeError>` или EditorCommandResult.
Успешное значение expected игнорируется и уничтожается до выхода из обработчика.
Успешный `false` по-прежнему означает обработанное действие, а не передачу ввода дальше.
Адаптер не проверяет поля успешного значения; нужную квитанцию доставки уведомлений
или другой успешный статус приложение должно проверить до возврата из обработчика.
Прямой возврат undo()/redo() сохраняет квитанцию ранее сообщённой ошибки;
извлечение result() её теряет. Первая ошибка/исключение прекращает цепочку.
Короткая запись в обработчике без возвращаемого результата во время работы
сцены сама не прерывает его инструкции;
для зависимого следующего действия используйте проверяемый return или stop.

Удаление, скрытие, отключение цели/предка или close останавливает цепочку
перед следующим обработчиком. Текущий обработчик переживает очистку до возврата.
Добавление к действующей цепочке во время доставки действует со следующего
события; создание новой ActionBinding во время диспетчеризации даёт WOULD_BLOCK.
Отдельных токенов отключения обработчиков цепочки `|` нет.

maxClickHandlers = 256 на сцену, maxClickHandlersPerNode = 64, оба положительны;
переполнение даёт NODE_LIMIT, память — NO_MEMORY, старые обработчики сохраняются.
maxConfigurations = 64 независимо ограничивает отложенные этапы до prepare.
Ref<Button>::onClick, recipe.onClick и ManagedScene::onClick хранят одиночную
привязку и отклоняют повтор. Их вариант без аргументов принимает немодифицированную
активацию; параметризованный — модифицированную. Цепочка `|` принимает оба вида активации.
Смешивание одиночной привязки и цепочки отклоняется.

## Клавиатура

<a id="reference-short-key-bindings-ru"></a>

```cpp
scene
  | ui::onKey(key::F10, ui::quit);
scene
  | ui::onKey(key::ALT + key::Q, ui::quit);
scene
  | ui::onKey({key::F10, key::ALT + key::Q}, ui::quit);
scene
  | ui::onKey("F10 | Alt + Q", ui::quit);
```

Выберите одну форму для действия. Альтернативы создают одного владельца обработчика;
повторная альтернатива вызывает его один раз. Имена ASCII регистронезависимы;
модификаторы совпадают точно. Последняя подходящая регистрация выигрывает;
неподходящая передаёт ввод предыдущей, затем виджетам.
Строковый Shortcut принимает PRESS; фазы задаются repeat/release/pressRepeat
или keyActions. Сырой ui::key/KeyEvent принимает PRESS+REPEAT.
Подробности последовательностей и возможности терминала — в [справке по вводу](input.md).

parseShortcut возвращает expected с типизированной причиной и смещением байта с отсчётом от нуля. Бюджеты по умолчанию: 4096 байтов, 32 альтернативы, 8 шагов.
ShortcutOptions меняет их явно. Ошибка регистрации сохраняет прежние привязки
и ожидание. Таймер последовательностей использует keySequenceTimeout; отказ его запуска
идёт через фатальную ошибку ввода и очищает ожидание.
maxKeyHandlers = 64 ограничивает композицию. Прямой onInput заменяет цепочку.

## Описания и ссылки

Описание перемещается и используется один раз. Описание хранит конфигурацию
и может быть создано заранее; передавайте его в ui::mount через std::move.
Ошибки копирования аргументов возможны до монтажа. Монтаж поддерева — общая
транзакция: при ошибке новые узлы, привязки, диапазоны и захваты удаляются.
Существующие соседи и состояния сохраняются; исходная причина и ошибка очистки
различимы. ManagedScene::remove сразу отзывает идентичности; повторный вход в управляемую сцену
даёт WOULD_BLOCK. Если внешний tree.edit/withScope ещё удерживает узел,
его уничтожение и unmount ждут освобождения этого заимствования.
Отложенные методы жизненного цикла могут удалить другие узлы; их внешние эффекты не откатываются.
Ссылки на виджеты публикуются после полного успеха; до этого пусты. Повторное использование
занятого слота или двукратная привязка отклоняются. NodeRef<T> открывает node();
Ref<T> добавляет [текстовые свойства](text-property.md).

Составные представления используют ту же форму объявления, но сохраняют свои
команды, а не получают искусственные операции виджета:

| Роль | Объявление | Фабрика | Команды |
|---|---|---|---|

| Диалог | `ui::Ref<Dialog>` | `ui::dialog` | `open()`, `dismiss()` |

| Селектор тем | `ui::Ref<ThemeSelector>` | `ui::themeSelector` | Проверяемые `open()`, `apply()`, `cancel()`, `closeKeepingPreview()`, `lastApply()` |
| Поверхность уведомлений | `ui::Ref<Overlay>` | `ui::notifications` | Наблюдение за настоящим узлом поверхности |

Имена приведены для `using namespace portals`. Ссылка передаётся первым аргументом
фабрики. `MessageDialog` и `ThemeSelector` обозначают существующие составные фасады:
новые ссылки разделяют их наблюдения, не создавая второго слота или владельца.
Прежние handles `ui::MessageBox` и `ui::ThemeSelectorRef` сохраняются. Копии
наблюдают одну идентичность; перемещение передаёт наблюдение. Создание холодной
ссылки по-прежнему может завершиться ошибкой выделения памяти.
Имя `MessageDialog` не конфликтует с макросом Win32 `MessageBox`; подключение
заголовков Windows не меняет имя класса исходного фасада.

У ссылок `MessageDialog` и `ThemeSelector` нет `node()`, `text()` и `focus()`.
Для доступа к настоящему виджету диалога задайте отдельный `ui::Ref<Dialog>` через `.reference(view)` рецепта.
Проверяемые команды остаются проверяемыми: верните результат команды селектора
из обработчика, чтобы передать ошибку обычной границе runner. `lastApply()`
сохраняет документированный владеющий результат после удаления представления,
но не удерживает сцену.

`ThemeSelectionRef` наблюдает за моделью тем, `NotificationCenter` служит для
публикации уведомлений. Их роли сохраняются. `ToastMessage` описывает сообщение;
публикация возвращает прежнюю квитанцию, а не ссылку на виджет.

Ссылку на виджет можно передать первым аргументом фабрики или через .reference(ref).
.id(value) копирует регистрозависимое имя селектора. Поздняя .style с пустым id
его сохраняет, с непустым — заменяет. scene.id меняет только id; scene.style
заменяет полные метаданные. Ошибка памяти сохраняет прежние данные и запрос кадра.

Ref<Button>::onClick можно вызвать после монтажа/prepare до run.
Сцена удерживает обработчик после уничтожения Ref. Повтор даёт INVALID_ARGUMENT;
пустая/закрытая Ref — CLOSED, удалённый виджет — STALE_NODE, чужой поток — WRONG_THREAD.
Отказ памяти оставляет свободную кнопку для повтора. Ошибки регистрации
записываются без остановки работающей сцены. Отложенное описание до монтажа
не принимает обработчики через Ref.
ClickEvent владеет исходным событием и хранит модификаторы и кнопку-получателя,
включая передачу от дочернего узла, в который попала мышь. Enter преобразуется в ActionEvent,
Space и нажатие мыши сохраняют тип. Отпускание, движение мыши и вставка не вызывают обработчик нажатия.

## Настройка контролов и виртуальных представлений

Стандартные фабрики хранят привязки, стили и синхронизацию.
Обработчик прикладного действия вызывается после стандартного действия; проверка LineEdit
может отклонить фиксацию до него. LineEditConfig именует результат, параметры,
размеры, буфер обмена и проверку. Ошибочный текст сохраняет TextError и смещение.
.style, .onEvent и .onPrepare настраивают поведение; .setup получает сцену
и типизированный узел с результатом `expected<void, ManagedError>`.
Пользовательские аргументы и захваты следуют владению C++; заимствованные
объекты должны оставаться живыми.

Настоящий default-catalog constructor также принимает `.themeCatalogSettings({...})` и `ui::themeCatalogSettings({...})`. Фабрика ресурса явно открывает эти свойства через `ui::controlPropertySchema("ThemeSelectorCatalog")`. Selector существующей модели отклоняет catalog-only свойства; метаданные не превращают его в owning catalog.

Для настоящего каталога порядок начальных настроек: defaults `ThemeSelector`, defaults `ThemeSelectorCatalog`, цепочка именованного варианта, явные значения экземпляра. Прежние view-derived варианты и ресурсные регистрации `ThemeSelector` совместимы. Старые метаданные вида по-прежнему отклоняют явный `themeCatalog.*` до вызова фабрики. Если фабрика возвращает настоящий каталог, его defaults вычисляются из исходного разреженного ввода с сохранением источников. Дополнительный бюджет проверяется после возврата фабрики, до установки модели; уже выполненные пользовательской фабрикой эффекты не откатываются.

Незаданные настройки сохраняют захваченные options, варианты и callbacks. Начальный выбор использует существующие preview/commit и не вызывает `onCommitted`. Необязательные бюджеты слоёв проверяет штатный engine при preview: несовпадение с уже установленными бюджетами даёт `INVALID_ARGUMENT`. Это начальные настройки, а не перенастройка смонтированного selector или перебазирование внешней модели.

### Начальные свойства контролов и загрузка ресурсов {#initial-control-properties-ru}

[ControlContext](../../include/portals/ui_control_context.hpp) и загруженная сцена хранят разреженные начальные значения. Если значение не задано, используется значение фабрики; явные `false` и `0` сохраняются и переопределяют наследованную настройку. Эти значения не перенастраивают уже смонтированный виджет. Для runtime-изменений используйте существующие типизированные API виджетов.

| `themeCatalog.layers.enabled/maxLayers/maxRules/maxDeclarations/maxOwnedBytes` | Необязательные лимиты слоёв первого preview. Числовые поля включают захваченные/default options, если нет явного отключения; заданные лимиты положительны. Активный набор требует минимум два слоя. `false` очищает optional. | Нет значения: установленные бюджеты engine либо defaults `16`, `1024`, `6144`, `1048576`. |

Настройки экземпляра `id`, владеющий список разделённых пробелами `classes`, `visible` и `enabled` хранятся отдельно от скалярных `ControlSettings`. Их методы и pipe-модификаторы сохраняют настоящий тип контрола. Видимость и отключение следуют существующим правилам дерева и ввода.

У встроенного ScrollArea `horizontal` и `vertical` означают политики прокрутки. Выравнивание его размещения в родительском Grid задаётся отдельно существующим `.gridItem(...)`. Зарегистрированные пользователем типы сохраняют собственную схему и прежний синтаксис размещения Grid. Применимый `frame{...}` является группой свойств, пока имя `frame` не занято зарегистрированным дочерним типом; при совпадении `frame{...}` остаётся ребёнком, а `frame={...}` явно выбирает группу свойств.

У отступов один канонический путь для каждой стороны; Grid и VBox/HBox используют ту же запись. В `CONFIGURATION` имя `placeHolder` является алиасом `placeholder` и нормализуется до проверки дубликатов; нового свойства оно не добавляет. Первые четыре поля агрегата `ControlPropertyDescriptor` сохраняют порядок `path`, `kind`, `depth`, `enumNames`; необязательный список алиасов идёт после них. В `SceneResourceArguments` существующий aggregate prefix `text`, `id`, `width`, `height`, `flex`, `gap`, `checked` также сохранён; `settings`, `visible` и `enabled` добавлены после него. Схема `ControlContext::registerType` выбирает подмножество этих канонических свойств, а не добавляет произвольные имена. См. объявления [`TextLimits`](../../include/portals/text.hpp), [`LineEditOptions`](../../include/portals/line_edit.hpp), [`LinearOptions`](../../include/portals/layout.hpp) и [`GridOptions`](../../include/portals/grid.hpp): именно они задают значения по умолчанию и контракты получателей.

Message-диалоги сохраняют native-правила: обязательны `MODAL` и отмена через Esc. Проверенная внутренняя панель не наследует обычные defaults `Dialog` повторно. Обычный `Dialog` не принимает message-настройки.

Ресурсная привязка требует настоящий захваченный message facade. Существующий fluent-коллектор регистрации принимает каноническую семантическую схему; ошибки сохраняются для `prepareChecked()` / `runApp()`, без ручной проверки регистрации:

```cpp
ui::Ref<MessageDialog> question;
ui::SceneResourceOptions options;
options.format = ui::SceneResourceFormat::CONFIGURATION;
options.control<Dialog>("Prompt", [question](ui::SceneResourceArguments) {
  return ui::confirmDialog(question, "Continue?", "Apply these settings?");
}, ui::controlPropertySchema("MessageBox"));
```

Реестр читает метаданные схемы только при регистрации и сохраняет собственный конечный выбор. Неполная или чужая схема отвергается. Фабрика должна вернуть настоящий native message recipe, в том числе после стирания типа; обычный Dialog отвергается при проверяемой подготовке. Ресурс `Prompt` может заменить захваченные title/body и настройки; callbacks и `question.open(...)` остаются в коде. Явная локализация фабрики приоритетна; resolver ресурса — только синхронный fallback конструктора для этой явной привязки.

Уведомления используют `.notificationSettings({...})` или `ui::notificationSettings({...})`; незаданные листья сохраняют захваченные `NotificationOptions`. Явные defaults `Notifications` действуют на эту семантическую композицию. Посторонние обычные defaults `Overlay` её по-прежнему не переопределяют. Размеры и раскладка Overlay сохраняют identity настоящей поверхности и приоритет ресурса над фабрикой.

Существующий явный native-вариант `.variant("MyOverlay")`, производный от `Overlay`, остаётся способом задать только стилевую identity: сохраняются исходная визуальная identity и локальные настройки фабрики, без наследования настроек этого варианта, обычных defaults `Overlay` или новых defaults `Notifications`. Для наследования настроек конструктора используется семантический вариант, производный от `Notifications`.

Ресурсная фабрика захватывает настоящий центр и полное тело и явно выбирает `ui::controlPropertySchema("Notifications")`. Это не добавляет несвязанный ресурсный конструктор и не сериализует отдельные команды toast. Resolver ресурса заимствуется только при подготовке сцены и не сохраняется центром; для будущих публикаций явно задаётся `NotificationOptions::textResolver`.

`ToastOptions` относится к запросу во время работы: severity по умолчанию `INFO`, duration — 5000 миллисекунд (`nullopt` означает постоянное уведомление), ключ дедупликации пуст, `dismissOnAction=true`. Необязательный индикатор по умолчанию выключен: glyph `!`, без чередования фона, белый передний план, красный сигнальный фон, период 500 миллисекунд. Это настройки существующего C++ API публикации.

Семантическая схема `ThemeSelector` настраивает настоящий вид как для существующей модели той же сцены, так и для существующего default-catalog constructor. По умолчанию `title=Themes`; незаданные листья сохраняют фактические захваченные options. Вид остаётся модальным и отключает немедленное закрытие через Esc. Внутренний Dialog не наследует обычные defaults Dialog повторно; default-catalog constructor применяет настройки вида один раз перед внутренним делегированием.

Зарегистрированная фабрика предоставляет настоящий selector facade и модель/каталог и явно выбирает `ui::controlPropertySchema("ThemeSelector")`; обычный Dialog не получает эту capability из метаданных. Ресурсный узел не принимает внешних дочерних тел: choices, status и actions создаёт native-вид. Собственная локализация приоритетна; resolver ресурса — только синхронный fallback подготовки, который не сохраняется в будущих callbacks. `onCommitted`, фабрики вариантов и identity модели/engine остаются в коде.

#### Поддержка ресурсов для 20 текущих семейств

`KeyHints{help="guide"}` связывается с экземпляром HelpView с ID `guide` в том же ресурсе; ссылка может указывать вперёд. Без `help` нужен ровно один объявленный экземпляр с возможностями HelpView. Для фабрик со стёртым типом `Widget` требуется явный ID; фактическую цель проверяет существующий финализатор создания. Отсутствующая, неоднозначная или неверная цель даёт typed setup error с откатом ожидающих ссылок. `help` — метаданные привязки экземпляра, не скаляр `ControlSettings`. Эти ресурсные контролы используют те же канонические регистрации клавиш, что и штатные C++-фабрики.

Встроенный реестр ресурсов содержит восемь обычных фабрик. Для Grid, Border, Gauge, ScrollArea, ScrollBar, Overlay, HelpView, KeyHints, DataStateView, OverlayHost и Dialog также предусмотрены локальные fallback-фабрики `CONFIGURATION`: они не резервируют имена вопреки явной регистрации и не меняют legacy-реестр. Таблица фиксирует текущую поддержку и пропуски загрузчика; отсутствие скалярного или декларативного свойства не означает постоянный контракт «только C++». У регистрации точного типа `add<VirtualList<T>>` или `add<VirtualTable<T>>`
схема по умолчанию включает соответствующие листья. Существующая обёртка
автоматически применяет эти значения ресурса; фабрике не нужно вручную
передавать `arguments.settings`. Явно заданная прежняя узкая схема остаётся
узкой и отклоняет новые листья. Произвольные пользовательские подклассы
эту схему не наследуют. Методы и pipes, например `.rowHeight(2).overscanRows(0)`
и `ui::rowHeight(2)`, сохраняют модель, formatter, policy и provider.

Настройки Dialog/OverlayHost применяются при создании. Методы и pipes, например
`.maximumPanelSize({42, 9})` и `ui::maxLayers(2)`, сохраняют фактические параметры
фабрики, не заданные переопределением. `.frame(BorderOptions{...})` меняет рамку
самой панели Dialog; для pipe используйте `ui::dialogSettings({.frame={...}})`.
Существующий `ui::frame(...)` по-прежнему оборачивает рецепт в Border.

Ресурсный OverlayHost принимает один обычный body, затем ноль или больше слоёв
Dialog. Каждый Dialog принимает один полный body; заголовок берётся из `title`
экземпляра/defaults/definition. Host сначала привязывает body, затем регистрирует
слои. Загруженный Dialog открывается через существующий `ui::Ref<Dialog>::open()`;
`opened()` и `dismiss()` сохраняют обычный управляемый жизненный цикл. Фабрика слоя
из кода должна создавать настоящий managed Dialog: один `custom<Dialog>` без
регистрации диалога не становится таким слоем автоматически.

Группы `dialog { maximumPanelSize { width=42, height=9 } }` и `dialog.frame { ... }`
различаются с Chart mode и размещением ScrollArea. Если имя группы принадлежит
зарегистрированному дочернему типу, используйте явную форму `dialog={...}`.

Фабрика точного типа `add<DataStateView>` автоматически применяет настройки к
реальной конфигурации, сохраняя её модель, retry и resolver. При `showStatus=false`
подписи не разрешаются, строка состояния и её таймер не создаются. При включённом
статусе `labels.retry` используется только при наличии retry action. Остальные
скалярные настройки проверяются и при отключённом статусе. В C++ необязательные
подписи задаются выражениями: `.labels({.loading = text("Fetching...")})`.

Локальная ресурсная фабрика DataStateView принимает один полный body, в том числе
вложенный layout/Grid. Например: `DataStateView { showStatus=false Label{"body"} }`.
Группа `labels { loading=i18n("loading") }` сохраняет выражение до создания
контрола; неиспользуемые подписи не вызывают resolver. Если зарегистрированный
дочерний тип называется `labels`, группу свойств выбирает запись `labels={...}`.
Ресурсный resolver применяется только при создании встроенного DataStateView;
явно заданный resolver фабрики имеет приоритет.

Регистрация точного типа `add<Chart<T>>` также автоматически применяет шесть
листьев Chart. Прежняя явная узкая схема — `{text}`; расширенная добавляет эти
шесть листьев. Текст остаётся метаданными фабрики из кода, а не подписью Chart.
Метод `.yRange(ChartRange{90, 120})` и `ui::yRange(...)` задают обе границы;
`.yRange(std::nullopt)` убирает фиксированный диапазон. В ресурсе это
`yRange { enabled=true, minimum=90, maximum=120 }`. Если имя `yRange` принадлежит
зарегистрированному дочернему контролу, явно выберите группу свойств через
`yRange={...}`.

`ControlContext` независимо проверяет каждое объявление defaults/definition.
Объявление с обратными границами и отсутствующим `enabled` или значением `true`
недопустимо, даже если последующий экземпляр отключил бы его. Чтобы сохранить неактивные конечные границы, укажите
`enabled=false` в самом объявлении. Переданные неконечные границы всегда
недопустимы. Повторный явный запрос подготовки может снова вычислить строки
Chart, как и native API; простаивающий event loop не запрашивает дополнительной
подготовки или перерисовки только из-за наличия этих настроек.

`ui::overlay` принимает обычные дочерние рецепты, необязательные `OverlayOptions`/`SizePolicy` и форму с Ref первым аргументом. Методы и pipes используют те же начальные настройки layout. Существующая композиция `ui::notifications` также принимает эти локальные модификаторы Overlay, сохраняя прежнюю обёртку без наследования контекста. Поэтому несвязанное пользовательское объявление `Overlay` не переопределяет и не ломает композицию уведомлений. Настройки самого сервиса уведомлений остаются отдельными.

#### Идентичность и состояние экземпляра

`#id` идентифицирует один узел ресурса. ID не является настройкой типа и не наследуется. Булевы свойства экземпляра `visible` и `enabled` также находятся вне скалярных листьев `ControlSettings`: по умолчанию оба равны `true`, они применяются локально после фабрики. Скрытый узел исключается из layout, paint и input; отключённый сохраняет layout/paint, но меняет input/style поведение. Состояние предков ограничивает дочерние узлы. `visible` и `enabled` недопустимы в definitions и defaults.

C++-рецепт задаёт это начальное состояние через `.visible(bool)` и `.enabled(bool)` или pipe-этапы `ui::visible(...)` и `ui::enabled(...)`. Для runtime-чтения и изменения используйте существующие API `WidgetTree`. Текст, callbacks, модели, resolver, providers и захваты фабрик остаются в C++; неизвестные свойства ресурса отклоняются до вызова text resolver или фабрики.

#### Эквивалентный C++ и загружаемый ресурс

Этот C++-пример задаёт разреженные значения по умолчанию для VBox и варианта редактора, а отдельной кнопке задаёт начальное состояние disabled:

```cpp
#include <portals/ui.hpp>

int main() {
  using namespace portals;

  ui::ControlContext controls;
  controls.defaults("VBox", {
      .gap = 1,
      .grid = {.paddingLeft = 1, .paddingRight = 1},
      .linear = {.mainAlign = LayoutAlign::CENTER}})
    .defaults("LineEdit", {
      .limits = {.maxInputBytes = 64, .maxClusterBytes = 16,
                 .maxGraphemes = 48, .maxCells = 48}})
    .define("CompactEdit", "LineEdit", {
      .limits = {.maxGraphemes = 32}});

  auto scene = ui::scene(
    ui::vbox(ui::label("Search"),
             ui::lineEdit("").variant("CompactEdit"),
             ui::button("Find").enabled(false)),
    {.controls = controls});
  return scene | ui::runApp();
}
```

Тот же ресурс использует существующую грамматику `CONFIGURATION`. Вложенный `scene` содержит один корневой узел; настройки типа находятся в `definitions` или `defaults`, а `enabled` — у конкретного экземпляра:

```cpp
#include <portals/ui.hpp>

int main() {
  using namespace portals;

  ui::SceneResourceOptions resource;
  resource.format = ui::SceneResourceFormat::CONFIGURATION;
  auto scene = ui::scene(R"(
definitions {
  CompactEdit = LineEdit { limits { maxGraphemes = 32 } }
}
defaults {
  VBox {
    gap = 1
    padding { left = 1; right = 1 }
    mainAlign = CENTER
  }
  LineEdit {
    limits {
      maxInputBytes = 64
      maxClusterBytes = 16
      maxGraphemes = 48
      maxCells = 48
    }
  }
}
scene {
  VBox {
    Label { text = "Search" }
    CompactEdit#query { text = "" }
    Button#find { text = "Find"; enabled = false }
  }
}
)", resource);
  return scene | ui::runApp();
}
```

`CONFIGURATION` нужно выбрать явно; формат `LEGACY` по умолчанию сохраняет старую грамматику с одним корневым узлом. Новые вложенные свойства линейных контейнеров (`padding`, alignment/overflow) и LineEdit `limits` доступны в `CONFIGURATION`; `visible` и `enabled` принимаются у экземпляров узлов в обоих форматах.

Пример настраивает только начальные значения. Он не сериализует все поля `LinearOptions`, `LineEditOptions` или других публичных options structs. Храните callbacks, модели и providers в C++; синтаксиса ресурса для них нет. [`SceneResourceOptions`](../../include/portals/ui_scene_resource.hpp) задаёт формат, контекст и явный реестр фабрик.
scene.model<T>(snapshot) создаёт общую модель. Передайте слабую ссылку на модель потока UI
virtualList/virtualTable/chart этой сцены. Таблица сразу копирует колонки,
заголовки и объекты форматирования; диапазон открывается при монтаже. Сцена владеет обработчиками;
объекты, захваченные по ссылке, остаются заимствованными. prepared получает общий заимствованный снимок
и необязательный владеющий ModelRequest в порядке регистрации, включая повторные проходы.
Для полностью доступного снимка обработчик поставщика не нужен;
ожидающие загрузки данные без него дают INVALID_ARGUMENT.
Политику запросов, кеша и диспетчеризации задаёт приложение.
Ошибка монтажа сохраняет прежнюю модель. .onEvent не заменяет стандартные
привязки списка/таблицы. Скрытие отменяет ожидающую работу диапазона; отключение меняет ввод.

| Фабрика | Настройки | Поля |
| --- | --- | --- |
| virtualTable | VirtualTableConfig<T> | options, policy, prepared |
| virtualList | VirtualListConfig<T> | options, policy, prepared |
| chart | ChartConfig<T> | options, first, prepared |

Значения по умолчанию совпадают с позиционными фабриками. Для инициализации полей по именам укажите тип конфигурации явно; пустое {} у chart означает ChartOptions.

tableColumn объединяет получение значения из const T& и его форматирование
в собственный GraphemeText.
Поддерживаются поля, const-методы и лямбды через std::invoke. Ограничения шаблонов отклоняют
несовместимый вызов и результат с заимствованным текстом или std::string. Для фиксированной схемы tableColumns
назначает локальные ID по порядку; динамическая схема задаёт ID явно через
TableColumnOptions, сохраняя их при замене/перестановке. Заголовки проверяются,
ширины положительны. Форматируются только видимые готовые ячейки, по одному
вызову функции получения значения на ячейку. Обработчики копируемы, не сохраняют заимствования,
не выполняют I/O и не меняют модель/дерево. Конструирование может бросать;
подготовка возвращает типизированные ошибки, прямой column.format передаёт исключения.

Рецепт создаёт дерево один раз. Согласование дерева (reconciliation) и динамическая
замена описания дерева этой моделью API не предоставляются.
