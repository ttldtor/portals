# Кадр для собственного цикла приложения {#render-ru}

[Английская версия](../render.md)

[`renderFullFrame`](../../include/portals/render.hpp) превращает собственные команды
текста и заполнения во владеющую сетку терминальных ячеек. Это подходит для
встраивания в свой цикл, слоя счёта/мира терминальной игры или backend, уже
управляющего вводом и временем. Для приложения из контролов начните с
[Application](application.md): он размещает и рисует дерево виджетов.

Полная программа создаёт кадр со счётом. Терминальный I/O не выполняется;
результат `CellBuffer` готов к передаче коду отображения приложения.

```cpp
#include <portals/render.hpp>

#include <array>

int main() {
  using namespace portals;

  const CellSize viewport{20, 2};
  auto text = GraphemeText::from("Score: 10");
  auto clip = CellRect::from({0, 0}, viewport);

  if (!text || !clip) {
    return 1;
  }

  const std::array<RenderCommand, 1> commands{
    TextCommand{{1, 0}, *text, *clip}};
  auto frame = renderFullFrame(viewport, commands);

  if (!frame) {
    return 1;
  }

  // The owning frame is ready for the host's presentation code.
  return 0;
}
```

Соберите [исходник](../examples/guide_render.cpp) с `portals::core` по
[руководству пакета](package.md). Размер задан в терминальных ячейках. Текст
и команды живут до возврата `renderFullFrame`; кадр владеет байтами и стилями
и может пережить оба входных объекта.

## Подключение к игре или внешнему циклу

После изменения состояния соберите команды с общей политикой ширины и вызовите
`renderFullFrame(viewport, commands)`. Проверьте результат до отображения.
Каждый вызов начинает с пустого буфера: передавайте полную желаемую сцену.
Приложение управляет частотой обновления, вводом, симуляцией и изменением размера.

Для терминала передайте владеющий буфер в `FrameWriter::submit`, затем обслуживайте
`flush` вне отрисовки: [разностный вывод](diff.md), [транспорт](terminal.md).
Пока вывод ожидает завершения, сохраняйте его транзакцию и не отправляйте новый кадр.
`FrameWriter` обрабатывает частичную передачу и меняет подтверждённое состояние
лишь после полной согласованной передачи. Для другого backend читайте ячейки
[`CellBuffer`](cell-buffer.md) и преобразуйте глифы, стиль и ширину в его примитивы.
Portals предоставляет содержимое ячеек; пиксельный renderer реализует приложение.

Для дерева виджетов во внешнем цикле также нужны dispatch UI-планировщика,
проверяемые кадры дерева, размещение и потребление заимствованных paint-команд
до окончания кадра. Образец интеграции — [реализация Application](../../src/runtime/application.cpp).
Не вкладывайте `Application::run` в свой цикл. Специальные viewport/camera и публикация
ограниченного снимка поверхности — **TBD — M6**. Для экранного HUD и свободного
размещения отдельный этап не назначен: [план возможностей](planned-features.md).

**Команды**

`RenderCommand` содержит `TextCommand` или `FillCommand`. Геометрия задаётся в [ячейках](geometry.md). Меньшие значения `z` рисуются первыми, равные сохраняют входной порядок. Порядок входа не изменяется. Неявных слоёв и сохраняемого состояния сцены нет.

`TextCommand` содержит начало, ссылку на `GraphemeText`, область отсечения, стиль и `z`. Каждая графема продвигает горизонтальную позицию на измеренную ширину, включая отсечённые графемы. Неподдерживаемые кластеры отображаются как `?`; перевод строки и табуляция не перемещают курсор. Полная политика ширины должна совпадать с кадровой даже у пустого или невидимого текста.

`FillCommand` заполняет `area ∩ clip ∩ surface` стилизованными ASCII-пробелами. Это ведущие записанные ячейки; незатронутые ячейки остаются пустыми.

**Отсечение**

Новая графема должна целиком помещаться в область отсечения и поверхность. UTF-8 и широкие пары не разделяются. Отрицательное начало допустимо; продвижение использует `int64_t`, а сужение выполняется после проверки всей области графемы.

При наложении действует правило [`CellBuffer`](cell-buffer.md): запись поверх продолжения удаляет старую ведущую ячейку. Например, после широкой графемы в столбцах 0–1 и узкой записи в столбец 1 столбец 0 станет пустым. Очистка старой графемы может выйти за область отсечения. Заполнение применяет то же правило.

**Владение, лимиты и ошибки**

Массив команд и текст заимствуются до возврата из вызова; всё это время они должны оставаться живыми и неизменными. Результат владеет байтами и стилями. Компонент не сохраняет указатели, не меняет вход и не вызывает обработчики. Привязки к терминальному или UI-потоку нет. Независимые вызовы и совместное чтение неизменяемых входов допустимы; изменения входа синхронизирует вызывающий код. Представления результата следуют правилам изменений и перемещения `CellBuffer`. Согласованность ревизий модели и стилей обеспечивает приложение.

`RenderLimits` ограничивает число команд, суммарные исходные байты текста и единицы работы. Повторный текст считается повторно. Работа включает все графемы, даже отсечённые, и видимые ячейки заполнения. Ограничения задают объём учитываемой работы. Длительность пользовательского кода ими не ограничивается. Сцена отклоняется целиком без частичного результата. При нулевых лимитах принимается только вход с нулевой учитываемой стоимостью. Сортировка ограничена числом команд, поиск одинаковых глифов и стилей — явными пределами буфера.

Переполнения сумм/произведений проверяются до выделения памяти. Ошибки буфера возвращаются как `buffer_error` с `CellBufferError`; временные выделения — `ALLOCATION_FAILURE`. Смена политики ширины требует пересоздания текста и обновления размещения/отрисовки вызывающим кодом.

Для сравнения кадров используйте байты глифов, стиль, роль и ширину ячейки. ID глифов и стилей локальны конкретному буферу.
