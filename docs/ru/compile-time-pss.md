# Строки PSS при компиляции и выполнении {#compile_time_pss-ru}

Экспериментальный compile-time раздел. Для обычного приложения начните
с [runtime PSS и декларативного UI](styling-guide.md). Этот API уже реализован;
экспериментальный статус не означает TBD.

[English original](../compile-time-pss.md)

Подключите `<portals/style_pss.hpp>` для ограниченного строкового интерфейса C++23
и метаданных источника, владеющих своими данными. Оба интерфейса используют один
парсер PSS v0 и существующий [каскад стилей (EN)](../styles.md). Материализация и монтирование
по-прежнему выполняются во время работы программы; отдельного рендерера,
планировщика или реактивной системы здесь нет.

## До: проверяемая настройка с ручным управлением `Scene`

Этот полный нативный клиент C++23 создаёт сцену, устанавливает слой `APPLICATION`,
регистрирует сообщения об ошибках и обработчик выхода, затем вызывает нативный
запуск. Описание PSS компактно, но клиент по-прежнему координирует каждый шаг
и самостоятельно обрабатывает исключения при создании.

~~~cpp
#include <portals/style_pss.hpp>
#include <portals/ui.hpp>
#include <cstdio>
#include <exception>

namespace ui = portals::ui;
namespace sc = portals::style::ct;

inline constexpr auto STYLES = sc::pss(R"pss(
  #message { min-width: 24; }
  #append { bold: true; }
)pss", "native-demo.pss");

/** @return Zero on success, one on setup, input, runner or cleanup failure. */
int main() {
  try {
    ui::Ref<portals::LineEdit> message;
    auto scene = ui::scene(ui::column(
      ui::label("Portals | F10: quit"),
      ui::lineEdit(message, "Hello").id("message"),
      ui::button("Append", [message] {
        message.text() += portals::text(" {}", "Portals");
      }).id("append")));

    scene.theme(portals::modernTheme())
      .styleLayers()
      .styleLayer(portals::StyleTier::APPLICATION, "demo", sc::materialize(STYLES))
      .onKey(ui::key(portals::InputKey::F10), [&scene] {
        (void)scene.quit();
      });

    scene.reportOnError();

    return scene | ui::runApp();
  } catch (const std::exception &error) {
    std::fprintf(stderr, "Setup failed: %s\n", error.what());

    return 1;
  } catch (...) {
    std::fputs("Setup failed: unknown exception\n", stderr);

    return 1;
  }
}
~~~

## После: создание через фабрику со стационарной настройкой

Этот полный клиент передаёт проверяемое создание, настройку, сообщения об ошибках,
запуск и очистку `runApp`. Настройка получает стационарную `Scene` по ссылке;
`ui::quit` использует текущий контекст сцены, поэтому обработчик не захватывает
адрес фасада. Этап установки стиля включает слои до подключения любого живого слоя.

~~~cpp
#include <portals/ui_style.hpp>

namespace ui = portals::ui;
namespace sc = portals::style::ct;

inline constexpr auto STYLES = sc::pss(R"pss(
  #message { min-width: 24; }
  #append { bold: true; }
)pss", "native-demo.pss");

/** @return Zero on success, one after a reported construction, setup, input or cleanup error. */
int main() {
  return ui::runApp(
    [] {
      ui::Ref<portals::LineEdit> message;

      return ui::column(
        ui::label("Portals | F10: quit"),
        ui::lineEdit(message, "Hello").id("message"),
        ui::button("Append", [message] {
          message.text() += portals::text(" {}", "Portals");
        }).id("append"));
    },
    [](ui::Scene &scene) {
      scene.theme(portals::modernTheme());
      scene | ui::style(STYLES, {.name = "demo"}) | ui::reportOnError()
            | ui::onKey(ui::key(portals::InputKey::F10), ui::quit);
    });
}
~~~

Для уже созданной обычной сцены краткий эквивалент —
`scene | ui::style(STYLES) | ui::runApp()`. Метод `scene.style(source, options)`,
свободная функция `ui::style(scene, ui::style(source, options))` и pipe-форма
используют один и тот же этап, владеющий данными. Именованная `Scene` остаётся
на месте благодаря lvalue-перегрузкам метода и pipe; временные цепочки используют
поглощающую перегрузку.

Создание этапа стиля, включая разбор байтов или копирование документа, происходит
до вызова принимающей `Scene`. Поэтому исключения выделения памяти или создания
аргументов могут возникнуть до проверяемой границы ошибок этого фасада.
`runApp(factory, setup)` вызывает фабрику описания внутри своей проверяемой границы
и преобразует ошибки фабрики, настройки и запуска в обычное сообщение и код выхода.
Создание вызываемых объектов и аргументов, переданных в `runApp`, всё равно
происходит до вызова и остаётся вне этой границы. Фабрика возвращает описание сцены,
никогда не `Scene`.

## Скалярные правила в виде данных

Короткие селекторы сохраняют существующую семантику конъюнкции:
`sc::all()`, `sc::id<"action">()`, `sc::type<"Button">()` и
`sc::className<"primary">()`. Для комбинаций используйте существующий
`selector<Type, Id, Classes...>(state)`. `fg` и `bg` — короткие помощники деклараций.

```cpp
inline constexpr auto TYPED = sc::compactSheet(std::array{
  sc::flatRule(sc::all(), sc::bg(sc::rgb(24, 28, 36))),
  sc::flatRule(sc::id<"action">(), sc::fg(sc::rgb(255, 210, 70)),
               sc::bold(true), sc::minWidth(std::int32_t{8}))
}, "application.typed");
```

`flatRule(parameters, selector, declarations...)` вычисляет значения типизированных
параметров по умолчанию и создаёт скалярный снимок. Проверки имён и типов сохраняются.
Интерфейс массива хранит количество правил как данные: его публичный тип результата
содержит числовые ёмкости, а не тип каждого правила и выражения. Он владеет одной
общей текстовой ареной. Промежуточные представления селекторов ссылаются только
на имена со статическим временем жизни в шаблонах; итоговое описание копирует их.
`FlatRule`, созданный по умолчанию, — универсальное пустое правило.

Снимки не содержат выражений живых параметров. Для реактивных параметров используйте
существующий [CT-002 `LiveTheme`](compile-time-styles.md); он по-прежнему работает
в одном движке с постоянными PSS-переопределениями приложения и пользователя.
Переменные, цветовые выражения и расширенные селекторы строкового PSS не входят в v0.
Из повторных текстовых деклараций побеждает последняя; прежняя проверка
типизированных правил по-прежнему отклоняет повторные назначения одного свойства.

## Разбор при выполнении и происхождение данных

`parsePssDocument(bytes, sourceName)` возвращает `expected<PssDocument, PssError>`.
Он копирует селекторы, идентификатор источника и все вхождения деклараций, включая
перекрытые значения. После вызова буферы вызывающего кода можно уничтожить.
Парсер не выполняет файловый ввод-вывод. `sourceName` — заданное вызывающим кодом
обозначение источника, а не команда открыть файл.

`sc::materializeDocument(description)` возвращает такой же владеющий документ
через типизированную границу выделения памяти. `sc::materialize(description)`
возвращает только `StyleSheet`, намеренно отбрасывает метаданные и может выбросить
исключение при выделении памяти, как и существующий типизированный материализатор.

`PssDocument::sheet` хранит итоговые правила в порядке источника. `origins` связывает
каждое правило с местоположением селектора и диапазоном деклараций. `declarations`
сохраняет каждое вхождение, его свойство, скалярное значение и местоположение;
`effectiveDeclaration` выбирает последнее вхождение для каждого свойства.
`originKind` отличает исходные байтовые координаты PSS от синтетических порядковых
номеров типизированного описания, которые не являются координатами файла C++.
Смещения считаются с нуля; строки и байтовые столбцы — с единицы; LF переводит
на следующую строку. Принятый начальный BOM остаётся частью смещений.

Установка `document.sheet` через низкоуровневый API целой таблицы отбрасывает сведения
о происхождении. `ui::style(document)` сохраняет владеющий документ вместе со слоем
приложения или пользователя; он доступен через `ManagedScene::styleSources()`.
Полный инспектор, объясняющий победившее правило для каждого свойства, — последующая
работа. Изменения только метаданных не добавляют периодическую перерисовку или
выделение памяти под трассировку на каждом кадре.

## Политики входных данных и ограничения

Новые документный интерфейс и интерфейс времени компиляции проверяют UTF-8 во всём
объёме входа, отклоняют встроенный NUL и принимают один начальный UTF-8 BOM.
Идентификаторы и имена свойств и состояний остаются ASCII. `parsePss(bytes)` сохраняет
прежнюю политику принятия байтов, включая произвольные байты комментариев и отказ
при начальном BOM; тип результата `expected<StyleSheet, StyleError>` не изменён.

| Ресурс | Интерфейс времени компиляции | Документ времени выполнения |
| --- | --- | --- |
| Входные байты | 16 KiB | 1 MiB |
| Правила | 256 | 1024 |
| Предикаты классов во всём описании | 1024 | Логический бюджет документа |
| Вхождения деклараций | 1536 | Логический бюджет документа |
| Общий текст в собственном хранилище | 16 KiB | Логический бюджет документа |
| Идентификатор источника | 512 байт | 4096 байт |
| Полезные данные описания/документа | Граница описания 128 KiB | Логические данные 4 MiB |

Логические данные времени выполнения включают собственный текст, записи правил
и классов и все записи происхождения. Это не ограничение на служебные данные
аллокатора, ёмкость векторов или временные копии. Именованные ошибки принятия
данных — `INVALID_ARGUMENT`; ошибки выделения памяти — `NO_MEMORY`. Частичный
документ наружу не возвращается. Прежний адаптер `parsePss` не получает новые
ограничения идентификатора источника или объёма документа.

## Диагностики компилятора

Удобная перегрузка для литерала сохраняет весь размер массива, включая NUL.
Для структурированной диагностики с кодом, смещением, строкой и столбцом используйте
поставщик без захватов, возвращающий `string_view` с явной длиной:

```cpp
using namespace std::literals;
// Intentionally invalid: an unknown property at offset 4, line 1, column 5.
constexpr auto INVALID = sc::pss([] { return "* { missing: true; }"sv; });
```

Первый assertion сообщает фиксированную категорию, например `Unknown PSS property`;
ограниченный носитель `PssFailure` даёт координаты и предмет ошибки. GCC и MSVC
оформляют это по-разному. MSVC показывает символы предмета ошибки числовыми
значениями; `PssError::subjectView()` времени выполнения предоставляет читаемый
предмет ошибки в собственном хранилище. Диагностики прямого литерала дают именованную
категорию ошибки и место вызова в C++. C++23 не может превратить обычные аргументы
функции в динамический текст assertion или координатные аргументы шаблона.
Тип поставщика позволяет не помещать всю таблицу стилей в аргумент шаблона.
Поставщики сырых указателей отклоняются: они потеряли бы байты после встроенного NUL.
Уже усечённый вызывающим кодом `string_view` не может восстановить потерянные байты.

Предмет ошибки владеет максимум 64 байтами ASCII и явным флагом усечения;
для не-ASCII байтов используется безопасный заменитель. Ошибки времени выполнения
не сохраняют заимствованный идентификатор источника. Низкоуровневый вызывающий код
задаёт этот контекст сам; граница загрузки в сцену сохраняет ограниченную метку
в собственном хранилище `ManagedError::styleSource`.

## Полные клиенты установленного пакета

Три формы используют общее переключение тем, живые параметры, сбор ошибок стилей
и очистку. Тест владения метаданными — отдельная нагрузка.

\include{lineno} ct_pss_before.cpp
\include{lineno} ct_pss.cpp
\include{lineno} ct_pss_flat.cpp
\include{lineno} ct_pss_support.hpp
\include{lineno} ct_pss_metadata.cpp

При измерении полного объёма клиентского кода учитывайте также
`style_layers_support.hpp`, `static_styles_support.hpp`, терминал воспроизведения
и стартовый код теста Windows. Подсчёт лексических токенов C++ считает сырую строку
PSS одним литералом: также проверяйте её байты и смысловое количество правил
и деклараций. Перенос синтаксиса в строку не делает её содержимое бесплатным
и сам по себе не доказывает удобство чтения.
