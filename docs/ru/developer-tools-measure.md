# Инструменты измерения и проверки терминала {#developer-tools-measure-ru}

[Английская версия](../developer-tools-measure.md) · [Каталог инструментов](developer-tools.md)

## Собрать исполняемые файлы

Нужны CMake 3.24+, Ninja и набор инструментов с поддержкой C99/C++23.
В Windows используйте x64 Developer PowerShell. Команды создают отдельную
Release-сборку, без публикации:

```powershell
cmake -S . -B build/tools -G Ninja -DCMAKE_BUILD_TYPE=Release -DPORTALS_BUILD_TOOLS=ON -DPORTALS_BUILD_TESTS=OFF -DPORTALS_BUILD_EXAMPLES=OFF -DPORTALS_BUILD_DOCS=OFF
cmake --build build/tools
```

Ниже приведены пути исполняемых файлов Windows. В POSIX уберите `.exe`.
Для генератора с несколькими конфигурациями выберите Release при сборке
и используйте соответствующий подкаталог. Перед запуском измерений создайте
каталог вывода. Файл, указанный в `--output`, может быть перезаписан;
для сохранения наблюдений выбирайте новый путь.

<a id="tool-compactness-ru"></a>
## Сравнить исходные файлы

`portals_compactness` читает явно выбранные файлы C++, исключает повторения
канонических путей с каждой стороны и пишет отчёт в стандартный вывод.
Исходники не изменяются, поведение программы не проверяется.
[Исходник](../../tools/compactness/report.cpp),
[определения метрик](../compactness.md) (на английском).

| Аргумент | Назначение | По умолчанию |
| --- | --- | --- |
| `--before FILE` | Обязательный исходный файл; повторите для включения вспомогательных файлов | Нет |
| `--after FILE` | Обязательный файл проверяемого варианта; повторите для включения вспомогательных файлов | Нет |
| `--format json\|markdown` | Формат вывода; можно задать не более одного раза | `json` |
| `--help` | Показать справку; используйте отдельно | Выключено |

```powershell
./build/tools/portals_compactness.exe --before docs/examples/docs_basic.cpp --after docs/examples/docs_events.cpp --format markdown
```

Код `0` означает, что отчёт или справка выведены; `1` — неверный аргумент,
ошибку чтения, анализа или вывода. Пример сравнивает разные программы;
полученные числа не подтверждают эквивалентность поведения.

<a id="tool-benchmarks-ru"></a>
## Запустить измерение производительности

Все пять программ ниже собираются при `PORTALS_BUILD_TOOLS=ON`. Терминал
открывает только режим MVP `--transport native`. Остальные работают внутри
процесса. Ни у одной из этих программ нет `--help`; неизвестные опции
завершают с ошибкой managed-, style-layer-, PSS- и MVP-программы.
Компактный бенчмарк не разбирает аргументы.

### Создание управляемых объектов и слои стилей

[managed.cpp](../../tools/benchmarks/managed.cpp) сравнивает три API создания
объектов. [style_layers.cpp](../../tools/benchmarks/style_layers.cpp) измеряет
изменения стилей с одинаковым результатом, перекрытые изменения и видимые
изменения у видимых, скрытых и находящихся за пределами экрана контролов.
У программ одинаковый CLI:

| Аргумент | Допустимые значения | По умолчанию |
| --- | --- | --- |
| `--rows N` | `1..1024`; одно число строк для managed, одно число контролов для слоёв стилей | Отдельные запуски для `32,128,512` |
| `--samples N` | `1..200` сохраняемых измерений на сценарий | `30` |
| `--warmup N` | `0..50` прогревочных запусков без измерения времени на сценарий | `5` |
| `--output FILE` | Путь JSON в существующем каталоге | Стандартный вывод |
| `--check` | Конечная проверка корректности; заменяет rows/samples/warmup на `2,8` / `3` / `1` | Выключено |

```powershell
./build/tools/portals_managed_benchmark.exe --check
./build/tools/portals_style_layers_benchmark.exe --check
./build/tools/portals_managed_benchmark.exe --rows 128 --samples 30 --warmup 5 --output managed.json
```

Код `0` означает успех; `1` — неверные опции, нарушение проверяемого
инварианта или ошибку экспорта. Программы используют фиксированные нагрузки;
[руководство по производительности управляемого API](../managed-performance.md)
(на английском) объясняет границы интерпретации результатов.

### Разбор PSS

[pss.cpp](../../tools/benchmarks/pss.cpp) измеряет семь сценариев разбора
во время выполнения.

| Аргумент | Допустимые значения | По умолчанию |
| --- | --- | --- |
| `--samples N` | `1..10000` сохраняемых измеряемых пакетов на сценарий | `100` |
| `--warmup N` | `0..1000` прогревочных пакетов без измерения времени | `10` |
| `--batch N` | `1..1024` отдельно измеряемых разборов, усредняемых в каждом пакете | `16` |
| `--reverse` | Обратный порядок сценариев | Выключено |
| `--check` | Проверить результаты без измерения времени | Выключено |
| `--output FILE` | Файл JSON в существующем каталоге | Стандартный вывод |

```powershell
./build/tools/portals_pss_benchmark.exe --check
./build/tools/portals_pss_benchmark.exe --samples 100 --warmup 10 --batch 16 --output parse.json
```

Код `0` означает успех, `1` — ошибку аргументов, проверки корректности или
экспорта. Процентили относятся к средним значениям пакетов. Уничтожение
успешного результата не входит в измеряемый интервал; очистка после частичной
ошибки и накладные расходы часов входят.

### Компактное создание объектов

[compact.cpp](../../tools/benchmarks/compact.cpp) не разбирает аргументы.
Запустите `./build/tools/portals_compact_benchmark.exe`; JSON поступает в
стандартный вывод. Программа выполняет три прогревочных запуска и 30
измерений. Код `0` означает успех, `1` — перехваченную ошибку.
Измеряются фиксированные сценарии сцен и колонок; исходники приложения
пользователя не анализируются. См. [методику измерений](../../tools/benchmarks/README.md)
(на английском).

### MVP-приложение и кодирование

[mvp.cpp](../../tools/benchmarks/mvp.cpp) запускает dashboard через
`Application`. Выходной файл обязателен, в том числе при измерении только
кодирования.

| Аргумент | Допустимые значения / назначение | По умолчанию |
| --- | --- | --- |
| `--output FILE` | Обязательный файл JSON; родительский каталог должен существовать | Нет |
| `--transport headless\|native` | Транспорт внутри процесса или настоящий терминал | `headless` |
| `--rate N` | `0..1000000` запрошенных тиков в секунду | `1000` |
| `--seed N` | Беззнаковое 64-битное начальное значение для воспроизводимого входа | `42` |
| `--rows N` | `1..1000000000` строк модели | `1000000` |
| `--fps N` | `1..1000`, ограничение частоты кадров | `30` |
| `--warmup-ms N` | `0..3600000` миллисекунд прогрева | `5000` |
| `--duration-ms N` | `1..3600000` миллисекунд наблюдения без учёта прогрева | `30000` |
| `--delay-ms N` | Беззнаковая 64-битная задержка поставщика в миллисекундах | `0` |
| `--sample-capacity N` | `1..1000000` сохраняемых значений на ряд | `65536` |
| `--diagnostics enabled\|disabled` | Сбор диагностики во время выполнения | `disabled` |
| `--ascii` | Использовать текст нагрузки в ASCII | Выключено |
| `--ansi16` | Использовать 16 цветов ANSI | Выключено |
| `--encoding-only` | Конечное воспроизведение для измерения полного и разностного кодирования | Выключено |

```powershell
./build/tools/portals_mvp_benchmark.exe --transport headless --warmup-ms 200 --duration-ms 500 --output mvp.json
```

Код `0` означает полное успешное наблюдение; `2` — штатное раннее завершение
с неполными данными; `1` — ошибку. Режим кодирования использует собственное
конечное воспроизведение вместо измеряемого запуска приложения. Нативный
режим потребляет ввод терминала и временно меняет его режимы. Не запускайте
его с дескрипторами, которые использует другой интерфейс.
[Методика](../../tools/benchmarks/README.md) (на английском) описывает размер
видимой области, прогрев, исходные измерения и требования к повторным
запускам. Короткая команда выше проверяет работоспособность и не задаёт
базовый результат производительности.

### Драйверы тестов измерительных программ

`tools/benchmarks/check.cmake` — внутренний драйвер CTest
`portals.mvp-measurement`. CMake передаёт `PROGRAM` и `OUTPUT_DIRECTORY`;
драйвер пишет три файла `mvp-*.json` и даёт каждому дочернему процессу
20 секунд. `check_managed.cmake` — драйвер `portals.managed-measurement`:
CMake передаёт `PROGRAM`; тайм-аут основной проверки дочернего процесса —
30 секунд. Также проверяются вывод и неверные аргументы. Запускайте их
через CTest в сборке с включёнными тестами и инструментами. Это проверки
корректности, без сбора базовых результатов. Ошибки CMake дают ненулевой
код завершения.

<a id="tool-readability-ru"></a>
## Собрать показатели читаемости

`tools/quality/readability.cmake` требует CMake 3.24+, установленный совместимый
clang-tidy и базу команд компиляции Ninja, созданную с
`CMAKE_EXPORT_COMPILE_COMMANDS=ON`. Скрипт создаёт новый каталог результатов,
запускает clang-tidy, сохраняя исходники и настройки компилятора.

| Переменная CMake | Назначение | По умолчанию |
| --- | --- | --- |
| `BUILD_DIR` | Обязательный каталог с `compile_commands.json` | Нет |
| `FILES` | Обязательный список единиц трансляции из базы через точку с запятой | Нет |
| `OUTPUT_DIR` | Обязательный новый каталог результатов; не должен существовать | Нет |
| `HEADERS` | Явно включаемые в область анализа и хеши заголовки | Пусто |
| `CLANG_TIDY` | Абсолютный путь к исполняемому файлу | Поиск в `PATH` |
| `TIMEOUT_SECONDS` | Целое число `>=1`, на каждый дочерний процесс | `120` |
| `EXTRA_ARGS` | Аргументы компилятора через точку с запятой | Пусто |
| `ENABLE_FUNCTION_SIZE` | Добавить установленную проверку размера функций | Выключено |
| `ENABLE_MAGIC_NUMBERS` | Добавить установленную проверку магических чисел | Выключено |

```powershell
cmake "-DBUILD_DIR=$PWD/build/tools" "-DFILES=$PWD/tools/compactness/scanner.cpp" "-DOUTPUT_DIR=$PWD/readability-run" -P tools/quality/readability.cmake
```

Для примера нужна совместимая база команд компиляции в указанной сборке.
Результат включает `status.json`, конфигурацию, хеши входных файлов,
журналы и YAML по единицам трансляции. Код `0` означает завершённый запуск
`REPORTED`. Недоступный или неуспешный анализ возвращает ненулевой код и
сохраняет свидетельства `NOT_RUN` или `FAIL`, если удалось создать каталог
результатов. Положительная когнитивная сложность отображается при пороге `0`;
предельное допустимое значение не задаётся. См.
[интерпретацию и область анализа](../quality.md) (на английском).

<a id="tool-performance-ru"></a>
## Архивировать и сравнить производительность

`tools/quality/performance.cmake` обрабатывает готовый JSON, без запуска
измерительной программы. Нужен CMake 3.24+.

| Переменная CMake | Где обязательна | Назначение |
| --- | --- | --- |
| `MODE` | В обоих режимах | `record` или `compare` |
| `KIND` | `record` | `managed`, `compact`, `mvp` или `pss`; адаптера JSON слоёв стилей нет |
| `RAW_FILE` | `record` | Существующий JSON исходных измерений |
| `METADATA_FILE` | `record` | Существующий JSON происхождения данных по схеме, указанной ниже |
| `OUTPUT_DIR` | `record` | Новый каталог архива; не должен существовать |
| `BEFORE_DIR` | `compare` | Базовый архив, созданный `record` |
| `AFTER_DIR` | `compare` | Архив проверяемого варианта, созданный `record` |
| `OUTPUT_FILE` | `compare` | Новый JSON сравнения; не должен существовать |

У всех перечисленных переменных нет значений по умолчанию.
[Руководство по качеству](../quality.md) (на английском) содержит схему
метаданных и полный пример записи. Сохраняйте вместе с исходными измерениями
сведения о наборе инструментов, конфигурации, машине, нагрузке и выполненной
команде.

```powershell
cmake -DMODE=record -DKIND=managed -DRAW_FILE=managed.json -DMETADATA_FILE=metadata.json -DOUTPUT_DIR=history/managed-before -P tools/quality/performance.cmake
cmake -DMODE=compare -DBEFORE_DIR=history/managed-before -DAFTER_DIR=history/managed-after -DOUTPUT_FILE=history/comparison.json -P tools/quality/performance.cmake
```

Первая команда предполагает корректный `metadata.json`, вторая — два
совместимых сохранённых запуска. `record` пишет `raw.json` и `record.json`.
`compare` пишет разности со знаком и отношения только после проверки
совместимости и хешей. Код `0` означает завершение; неверные, несовместимые
или неполные входные данные дают ненулевой код. Ухудшение результата
проверяемого варианта требует повторных измерений и само по себе не
доказывает причину изменения.

<a id="tool-probe-ru"></a>
## Исследовать терминал

`portals_terminal_probe` печатает строки `key="value"` с экранированием.
[Полное руководство](terminal-probe.md) описывает ограничения запросов
и восстановления состояния.

| Аргумент | Допустимые значения / назначение | По умолчанию |
| --- | --- | --- |
| `--help` | Показать справку | Выключено |
| `--no-query`, `--headless` | Исследовать без чтения ввода и изменения режимов | Выключено |
| `--timeout-ms N` | `1..10000`, время одного окна запросов | `250` |
| `--max-bytes N` | `1..65536`, предел сохраняемого ввода | `4096` |
| `--width-policy narrow\|wide` | Рекомендуемая политика ширины неоднозначных символов | `narrow` |

```powershell
./build/tools/portals_terminal_probe.exe --headless
```

При перенаправлении ввода или вывода запросы автоматически пропускаются.
Нативный режим запросов потребляет ввод и восстанавливает временно
изменённые режимы перед возвратом. Код `0` означает завершённое наблюдение,
включая пропущенные запросы и запросы без ответа; `1` — ошибку ввода-вывода,
восстановления или вывода; `2` — неверные опции. Отсутствие ответа не
подтверждает отсутствие возможности.

<a id="tool-native-ru"></a>
## Проверить восстановление нативного терминала

Эти скрипты запускают готовые supervisor и дочернюю программу в отдельном
терминале, собирают журналы и проверяют очистку. Соберите
`portals_terminal_cleanup` и выбранный пример в конфигурации
с тестами; см. [тестирование](../testing.md) (на английском). Скрипты создают
процессы и файлы журналов и могут отправлять тестовый ввод.

### Скрипт Windows

[tools/native_windows.ps1](../../tools/native_windows.ps1) требует Windows
PowerShell, по умолчанию Windows Terminal, а также собранные supervisor
и дочернюю программу.

| Параметр | Назначение | По умолчанию |
| --- | --- | --- |
| `-Supervisor PATH` | Обязательный исполняемый файл supervisor | Нет |
| `-Child PATH` | Обязательный исполняемый файл дочерней программы | Нет |
| `-LogDirectory PATH` | Обязательный новый каталог; не должен существовать | Нет |
| `-ChildArguments ARRAY` | Аргументы для дочерней программы | Пусто |
| `-Drive none\|dashboard` | Сценарий ввода supervisor | `none` |
| `-HostWheel` | Отправить событие колеса однозначно определённому тестовому окну | Выключено |
| `-ExpectedExit N` | Ожидаемый код дочерней программы | `0` |
| `-DeadlineMs N` | Лимит времени supervisor в миллисекундах | `15000` |
| `-QuitMs N` | Время запланированного выхода в миллисекундах | `4500` |
| `-Terminal PATH` | Исполняемый файл терминала | `wt.exe` |

```powershell
powershell -NoProfile -File tools/native_windows.ps1 -Supervisor ./build/tests/portals_terminal_cleanup.exe -Child ./build/tests/portals_gallery.exe -LogDirectory ./native-run -Drive dashboard
```

Пути предполагают, что программы уже собраны в `build/tests`. У скрипта нет
собственного блока справки. Целочисленные интервалы принимаются без
проверки диапазона в самом скрипте; их проверяет supervisor. Создаются
`supervisor.log`, `runtime.json`, `baseline.json`, `hashes.json`, `after.json`, `launch.json`
и при необходимости `host-input.json`. Код `0` требует успеха supervisor,
завершения тестовых процессов и сохранения ранее запущенных процессов
терминала; неудачные проверки дают `1`. Исключения при подготовке тоже
означают ошибку. Принудительная очистка считается свидетельством ошибки.
Сама отправка колеса не подтверждает обработку события приложением.

### Скрипт xterm для POSIX

[tools/native_xterm.sh](../../tools/native_xterm.sh) использует POSIX shell.
Передайте восемь позиционных аргументов в указанном порядке, затем
необязательные аргументы дочерней программы:

```sh
sh tools/native_xterm.sh xterm ./build/tests/portals_terminal_cleanup ./native-run 15000 0 dashboard 4500 ./build/tests/portals_gallery
```

| Позиция | Назначение | По умолчанию |
| --- | --- | --- |
| 1 `XTERM` | Исполняемый файл xterm | Нет |
| 2 `SUPERVISOR` | Исполняемый файл supervisor | Нет |
| 3 `LOGDIR` | Новый каталог журналов | Нет |
| 4 `DEADLINE_MS` | Десятичный лимит времени supervisor в миллисекундах | Нет |
| 5 `EXPECTED_EXIT` | Ожидаемый код дочерней программы | Нет |
| 6 `DRIVE` | `none` или `dashboard` | Нет |
| 7 `QUIT_MS` | Время запланированного выхода в миллисекундах | Нет |
| 8 `CHILD` | Исполняемый файл дочерней программы; остальные аргументы передаются ей | Нет |

По умолчанию `PORTALS_NATIVE_VISIBLE=0` запускает изолированный сервер Xvfb
с собственной Xauthority. Нужны `Xvfb`, `xauth`, `xterm` и стандартные утилиты оболочки, используемые скриптом: `realpath`, `sha256sum`, `od`, `sed`, `grep`, `mktemp`, `date`. Передайте пути к исполняемым файлам xterm и supervisor.
`PORTALS_NATIVE_VISIBLE=1` использует существующий дисплей и допускает
только `DRIVE=none`. Другие значения режима видимости отклоняются. `PORTALS_XVFB` задаёт исполняемый файл сервера (по умолчанию `Xvfb`); `PORTALS_XVFB_WORKDIR` при необходимости меняет его рабочий каталог. `TMPDIR` задаёт родительский каталог временных файлов (по умолчанию `/tmp`). Видимый режим использует `DISPLAY` и `XAUTHORITY` вызывающего процесса. Скрипт сохраняет состояние
запуска, стандартные потоки вывода и ошибок xterm и вывод supervisor,
завершает собственные созданные процессы и частный сервер. Код `0` означает
успех; `1` — неудачную завершённую проверку; неверные аргументы могут дать
`2`, ошибки оболочки и подготовки дают ненулевой код. Режима `--help` нет.
