# Диагностика {#diagnostics-ru}

[Английская версия](../diagnostics.md)

Начните со стандартного поведения: завершите fluent-цепочку сцены этапом
`| ui::runApp()`. Он проверяет ошибки подготовки и запуска, пытается очистить
сцену и восстановить терминал, затем печатает ошибку в stderr и возвращает 1.
Восстановимые ошибки действий сохраняются; успешный запуск может вывести
ограниченную сводку таких ошибок и при этом вернуть 0.

## Вывод ошибок в stderr

Добавьте `| ui::reportOnError()`, чтобы явно выбрать стандартный вывод итогового отчёта:

```cpp
#include <portals/ui.hpp>

int main() {
  using namespace portals;

  ui::Ref<Button> exit;

  return ui::scene(ui::button(exit, "Exit"))
    | ui::reportOnError()
    | ui::onClick(exit, ui::quit)
    | ui::onKey("F10", ui::quit)
    | ui::runApp();
}
```

Получатель вызывается после попыток восстановления терминала и очистки сцены.
Чистый запуск без сохранённых ошибок его не вызывает. `ui::runApp()` использует
этот получатель по умолчанию, поэтому явная стадия необязательна. Если установлен
собственный получатель, `ui::reportOnError()` возвращает стандартный вывод в stderr.

<a id="diagnostic-symptoms-ru"></a>
## Найдите причину по симптому

В [первом приложении](first-application.md) стандартная обработка ошибок уже
включена через `ui::runApp()`. Для начала отдельный перехватчик не нужен.

| Что произошло | Что проверить | Следующее действие |
|---|---|---|
| Сцена не открылась, приложение вернуло 1 | Прочитайте итоговый отчёт в stderr: операцию, источник и причину ошибки | Исправьте указанную настройку или файл. Для собственного журнала подключите [получатель итогового отчёта](#diagnostic-final-report-ru) |
| Кнопка не вызывает действие | Получает ли она фокус по Tab, доступна ли она, передана ли её ссылка в `ui::onClick` | Сравните регистрацию с [шагом 2 первого приложения](first-application.md). Попробуйте Enter на кнопке в фокусе; порядок обработки описан в [фокусе и маршрутизации](focus.md) |
| Обработчик вызван, но экран не изменился | Меняется ли значение, тот ли контрол обновляется. Повторное присваивание равного значения может не требовать кадра | Проверьте значение и цель присваивания. Если этого недостаточно, включите [причинную диагностику](#diagnostic-action-trace-ru) для пути действия |
| Сочетание или отпускание клавиши не приходит | Не перехватывает ли сочетание сам терминал; предоставляет ли используемый ввод нужную фазу | Сначала проверьте обычное нажатие F2. Выберите поддерживаемую клавишу или фазу по [руководству по вводу](input.md); условия среды смотрите в [таблице терминалов](terminal-probe.md#terminal-observations-ru) |
| Стиль не меняет контрол | Совпадают ли тип, ID и состояние селектора; не перекрывает ли правило слой с большим приоритетом | Сверьте [селектор и свойства PSS](styling-guide.md), затем [приоритеты слоёв](style-layers.md). Для `styleFile` проверьте путь относительно рабочего каталога процесса |
| Доступ через `Ref` возвращает `CLOSED`, `STALE_NODE` или `WRONG_THREAD` | Жива ли сцена и целевой контрол, выполняется ли операция в UI-потоке | Используйте ссылку на существующий контрол в потоке сцены. Проверяйте возвращённый `expected` у явных операций чтения; подробности — в [ссылках на контролы](text-property.md) |
| Ошибка не появилась в файле журнала | Подключён ли свой получатель и была ли вообще ошибка; чистый запуск не вызывает `reportOnError` | Добавьте файловую запись в [итоговый получатель](#diagnostic-final-report-ru). Для наблюдения во время работы используйте [onError](#diagnostic-live-errors-ru); вывод в терминал отложите до завершения UI |
| После выхода остались изменённые режимы терминала | Сообщил ли runner об ошибке восстановления; не был ли процесс завершён принудительно | Сохраните отчёт и откройте новую сессию терминала для дальнейшей проверки. При обычном повторном запуске сравните [восстановление режимов](terminal-probe.md#terminal-observation-checklist-ru) |

Запускайте `portals_terminal_probe` отдельно, после закрытия приложения.
Он проверяет среду и ответы DA/CPR; это не средство проверки доставки всех клавиш.
[Как прочитать результат пробы](terminal-probe.md#terminal-probe-result-ru).

<a id="diagnostic-final-report-ru"></a>
## Собственный получатель итогового отчёта

`ui::reportOnError(sink)` принимает функцию с параметром
[`const ui::SceneReport &`](../../include/portals/ui_scene.hpp). В этом обработчике
можно сразу писать в файл или журнал приложения. Вызов `ui::reportToStderr(report)`
здесь тоже допустим: попытки восстановления терминала и очистки уже выполнены.
Эту функцию можно передать напрямую:

```cpp
    | ui::reportOnError(ui::reportToStderr)
```

`ui::reportOnError(sink)` заменяет итоговый получатель; пустой `sink` возвращает
стандартный stderr. Доставка выполняется один раз после попыток восстановления
и очистки. Исключение получателя вызывает резервный вывод исходного отчёта в stderr.
Отчёт заимствуется только на время вызова; для хранения скопируйте его.
Не изменяйте и не запускайте сцену повторно из этого обработчика.

<a id="diagnostic-live-errors-ru"></a>
## Наблюдение во время работы UI

`ui::onError([](const ManagedDiagnostic &error) { ... })` устанавливает наблюдатель
отдельных типизированных ошибок в UI-потоке. Он не заменяет итоговый получатель
и не отменяет ошибку. Сохраняйте ограниченные данные приложения или меняйте своё
состояние; не пишите в stdout/stderr при активном терминале. Вложенные сообщения
не вызывают рекурсивных уведомлений; исключения наблюдателя учитываются отдельно
от исходной причины. `ManagedScene::diagnostics()` возвращает владеющий снимок,
`drainErrors()` передаёт накопленную историю. Поля и пределы описаны в
[`managed_diagnostics.hpp`](../../include/portals/managed_diagnostics.hpp).

Низкоуровневые результаты `expected` по-прежнему нужно проверять. Исключения
в документированных callback-границах runner и managed API преобразуются в ошибки.
Создание аргументов, захватов и кадра корутины может бросить до входа в эти границы.
Для проверяемого входа с фабрикой описания используйте `ui::runApp(factory, ...)`
из [`ui.hpp`](../../include/portals/ui.hpp).

Автоматического постоянного журнала, ротации и фонового logging-сервиса нет.
Эта интеграция — **TBD**, milestone в текущем [плане](planned-features.md) не назначен.
Доступная точка расширения — итоговый получатель отчёта.

<a id="diagnostic-action-trace-ru"></a>
## Почему действие не изменило экран

[`Diagnostics`](../../include/portals/diagnostics.hpp) записывает ограниченные причинные
метаданные. По умолчанию запись выключена. Она отделена от истории managed-ошибок
и logger приложения. Передайте общий recorder в `SchedulerOptions::diagnostics`
(для сцены — `ui::SceneOptions::application.scheduler.diagnostics`), включите его
проверяемым вызовом `enable`, а после запуска выключите, получите снимок и экспорт.
`exportDiagnostics` возвращает текст в памяти; файловый вывод и ошибки принадлежат приложению.

<details>
<summary>Справка recorder: контекст, пределы и экспорт</summary>

Portals записывает ограниченные метаданные прохождения действия: от ввода
до обработчика, изменения свойства и вывода кадра. Символы ввода, вставка,
буфер обмена, значения свойств, сообщения исключений, адреса и VT-байты
не записываются. Формат диагностики имеет собственную версию; семантический
replay использует PORTALS-TRACE 1.

**Подключение**

По умолчанию диагностика выключена. Отключённые точки записи проверяют указатель
и при наличии регистратора его состояние; они не форматируют текст, не читают
часы, не выделяют кольцо и не исследуют данные. В очереди есть фиксированный
токен. `enable` резервирует кольцо; запись памяти не выделяет. Номера
последовательности задают порядок наблюдений. Часы и метрики Scheduler сохраняют
своё назначение.

Scheduler и его каналы публикации совместно владеют регистратором; дерево заимствует
Scheduler, writer удерживает регистратор. DiagnosticScope заимствует регистратор,
остаётся на создавшем потоке и завершается раньше него. Вложенный контекст
восстанавливается при обычном возврате и исключении.

**Путь действия**

На границе декодированного ввода создавайте токен до публикации, включая
события, которым очередь впоследствии откажет. Установите результат
`trace->beginInput(DiagnosticInput::KEY)` в `DiagnosticScope` вокруг публикации.

Scheduler удерживает токен в публикации и устанавливает его при вызове.
Router, фокус, действие, начало/возврат обработчика, Property и инвалидация
используют общий контекст. Прямой dispatch/invoke создаёт контекст при его
отсутствии. Другой поток может установить скопированный токен; токен не даёт
доступа к UI. Новый beginInput внутри контекста записывает родителя.

После диспетчеризации потребите запрос кадра, нарисуйте дерево и передайте
его токен writer. Несколько инвалидаций объединяются в один frame ID;
каждая причина записывается отдельно. Токен кадра указывает первую записанную
причину. Инвалидация рисования от компоновки относится к текущему кадру.
Записи writer отражают настоящий diff, submit и flush.
output_accepted подтверждает согласованное принятие транспортом;
физическое отображение на экране этим не подтверждается.

**Интерпретация**

Enter на Button с присваиванием равного значения Property может дать:

```text
input input=key
queue_accepted queue=control
queue_dispatch queue=control
action action=1
target stableNodeId=<tree-session>:<slot>:<generation>
handler_started
property reason=value_unchanged
handler_returned reason=value_unchanged
frame_not_requested reason=frame_not_requested
completed reason=value_unchanged
queue_returned reason=outcome_unknown queue=control
```

value_unchanged относится к наблюдаемой операции Property. Без таких сведений
результат пользовательского обработчика остаётся outcome_unknown даже при
нормальном возврате. Поздний handler_failed сохраняет ранее записанное изменение.
frame_not_requested означает отсутствие нового запроса внутри данного scope;
старый ожидающий кадр мог уже существовать.

Причины: queue_full, replaced, cancelled, no_target, target_disabled,
stale_target, unbound_action, unhandled, handler_failed, value_unchanged,
outcome_unknown, frame_not_requested, diff_empty, output_failed.
Записывается реально выбранная маршрутизатором цель; восстановление фокуса
может выбрать другой узел. Session/slot/generation экспортируются без адресов
и действуют в пределах жизни дерева/регистратора. Замена публикации записывает
отмену старой и связь с новой. Причину отсутствия ввода до инструментированной
границы экспорт установить не может.

**Ёмкость и неполные цепочки**

enable начинает новый интервал и очищает кольцо/потери; счётчики идентичности
и последовательности сохраняются без переполнения. disable сохраняет интервал.
Токен через границу интервала считается неполным. Исчерпание идентичности
навсегда останавливает приём с identity_exhausted.

Заполненное кольцо заменяет старейшую запись и увеличивает dropped_overflow.
Производитель пробует блокировку один раз: конкуренция учитывается как
dropped_contention. Копирование снимка держит блокировку; форматирование и I/O
выполняются отдельно. Память снимка ограничена ёмкостью. Анализ полноты в худшем
случае квадратичен по ёмкости; снимок берите между кадрами.

Экспорт содержит границы интервала, диапазон последовательностей, оба счётчика
потерь, насыщение, состояние и incomplete. Известная потеря помечает все цепочки
неполными. Также учитываются отсутствующие начало/завершение, ожидающие публикации
и вывод, токены другого интервала. Каждая принятая публикация требует собственной
queue_returned или queue_cancelled. Исключение обработчика даёт
queue_returned reason=handler_failed. Отсутствие записи не доказывает
отсутствие действия. Для выключенных точек полнота не учитывается.

**Экспорт**

exportDiagnostics(snapshot) возвращает текст в памяти. Приложение выбирает
файл и обрабатывает ошибки. Снимок и сериализацию выполняйте между кадрами
или после восстановления терминала. Выводить экспорт в stdout/stderr во время
работы интерфейса в системном терминале нельзя.

Создание снимка и форматирование могут бросить bad_alloc, включая служебные данные отладочных итераторов. Возврат использует ограниченную копию вне блокировки.
Проверяйте открытие, запись и закрытие файла. validateDiagnosticVersion
проверяет заголовок версии до чтения полей; парсер воспроизводимых сценариев имеет отдельный API.

</details>
